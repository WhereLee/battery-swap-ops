## P0（决定"能不能用"）

### P0-1 集成测试进 CI（Testcontainers）

**为什么**：被问"你 CI 跑什么"时目前只能答"单测+覆盖率门槛"；零超卖、对账零差异、坏网络
这些最强结论全部来自人工 PowerShell 剧本，不在流水线，回归靠纪律不靠门禁。

**现状证据**：
- `.github/workflows/ci.yml` 仅 `mvn -B -ntp verify`（单测）；CI 无中间件。
- `@SpringBootTest` 全仓仅 1 处（`ContextLoadsTest.java:19`），无 Testcontainers 依赖
  （swap-server pom 依赖清单核实）。
- 29 个剧本脚本、31 份输出为人工执行产物。

**交付物**：
1. swap-server 增加 `testcontainers-bom` + `mysql` + `junit-jupiter` 依赖（参照
   `inteink-faster/pom.xml`，该仓已含 testcontainers-bom；IT 样例见
   `inteink-faster/reason-main/src/test/java/com/reason/modules/device/mq/DeviceEventMqIT.java`
   与 `.../sys/AuthIT.java`）。
2. `maven-failsafe-plugin` 跑 `*IT`；surefire 排除 IT。**关键约束：本地 Windows 无 Docker
   （服务器连接文档 §六），必须保证 `mvn clean test` 不碰容器、`mvn verify` 才跑 IT**，
   否则本地全绿基线被破坏。
3. 最小集成集（3 条）：
   - IT-1 换电主链路：MySQL+Redis 容器，下单→分配（真实 Lua）→取电→还电→计费断言；
   - IT-2 对账检出：造不一致数据→14 组不变量命中预期组；
   - IT-3 并发零超卖：20 并发抢有限库存（Redis 真实竞争 + DB 条件更新兜底）。
4. CI 里 `mvn verify` 自动带上 IT（ubuntu-latest 自带 Docker，无需改 workflow 结构）。

**验收**：CI 绿且包含 3 条 IT；本地 `mvn clean test` 无 Docker 仍 375/375 全绿；
IT 失败能红 CI（故意造一条失败验证一次）。

**估算**：1-2 天。**风险**：容器启动耗时抬 CI 时长（预计 +2~4 分钟，可接受）；MySQL 容器
需执行 db/00-15 迁移脚本，注意与手工迁移口径一致。

### P0-2 水平扩展：分片保序 + 双实例演练

**为什么**：面试必问"你这设计怎么水平扩展"。当前事件通道是"单 topic 单队列 + 消费并发=1"
（保序换吞吐的天花板），多实例互斥有设计但从未双实例跑过。

**现状证据**：
- 契约：`plans/S0.3-设备协议v1.md:115`（topic 1 队列保序）。
- 消费：`device/mq/DeviceEventMqConsumer.java`（并发度=1、单线程 receive→处理→ack）。
- 发送：`swap-sim/.../reporter/MqEventReporter.java:29-38`（单发送线程 + 队首持留）。
- 多实例基建：`common/lock/JobLockService`、`common/delay/DelayScheduler.java:13-15`
  （ZREM 原子竞争）、`common/id/WorkerIdRegistry`（Redis 租约）。

**交付物**：
1. 技术验证 spike：RocketMQ 5 gRPC 客户端 FIFO message group 通道（发送端按 cabinetNo 设
   group → 同柜事件同队列；消费端按队列并行）。**保序不变量从"全局"降级为"每柜"**，序守卫
   本就按 (cabinetNo,bootId) 判定，语义不变。
2. 若 spike 不可行，退路：多 topic（按柜 hash 路由）+ 平台多消费组；文档如实记录取舍。
3. 分片版剧本：N 柜事件乱序/重放注入，断言跨代重放仍被拒、每柜序单调。
4. 双实例演练：同库同 Redis 起两份 server（端口/workerId 不同），连续 30 分钟跑对账/
   延迟任务/工单 SLA/调拨，断言任务不重复执行、无锁冲突雪崩；证据落档。

**验收**：① 分片剧本 PASS；② 双实例 30 分钟零重复执行；③ 文档更新契约 §7 与 architecture。

**估算**：2-3 天（含 spike）。**风险**：gRPC 客户端可能不暴露队列选择能力，spike 失败走退路，
预算 +1 天；双实例需第二套端口/日志目录，注意本机内存。

### P0-3 容量工程（读路径复测 + 写路径 + 量级换算 + JVM 故事）

> **状态（2026-09-16）：a-e 已全部完成**（批次16 + 批次17）：读路径方法论复测 **3,230~3,526/s、0 错误、p99 16~84ms**
> （旧 465.5/s 为压测端端口耗尽假象，已更正）；资源画像与量级换算落地（`knowledge/capacity-model.md`）；
> 写路径两档 **0 错/零超卖/计费恰一次**（`批次17-P0-3d-e写路径容量与JVM故事.md`）；JVM 故事 96m vs 512m
> （吞吐 -21.5%、GC 暂停 20.8×；`fixes/jvm-gc-pressure-96m.md`）。**台账孤占 follow-up 已闭合（批次18）**：
> 两阶段 reset 收敛修复 + T2 孤儿柜退役 + `batch18` 防回归剧本——**对账 total 18→0**（详见 `pitfalls/dev-reset-nonconvergent-orphans.md`）。

**为什么**：写路径无数据；且**读路径已有数据的方法论也不合格**——`_load_out.txt` span=5.156s，
无预热、无稳态窗口、无梯度、无资源画像、未声明拓扑，属冒烟级数字，作为"容量结论"发出去反而会被反问。
容量话题在中小厂的考点是方法论（预热/稳态/观测口径），比数字本身重要。

**现状证据**：
- `scripts/verify/batch7/_load_out.txt`：20 线程×30 循环×4 接口、2400 样本、465.5/s、5.156s、GC 16 次/68.5ms。
- `scripts/verify/batch7/jmeter/swap-ops-load.jmx`：TestPlan 名称 "read path"，仅 4 个只读采样器。
- 全仓 grep `日均/QPS/峰值/容量规划` = 0 命中：无业务量级换算。

**交付物（一份工作，四个产出）**：
1. **方法论基线**：预热段 + ≥5 分钟稳态段；梯度 20/50/100（读、写各跑）；每份结果带元数据
   （拓扑/堆/限流开关/数据基数/通道）与原始 jtl；统计入 `_out.txt`，原件归档 `diag-archive/`。
2. **读路径复测一档长窗口** + **写路径 `write-path.jmx`**（登录→下单→取/还→查账单）：
   断言零超卖（订单数/`lock_order_id`）、计费恰一次（payment_record 计数）、5xx=0；
   前置数据：加大种子电池数或分轮补货（`POST /admin/ops/rebuild-alloc` 已有）。
3. **资源画像**：L1/L2 命中率（`/admin/cache/stats`，厘清 465/s 里多少打在缓存、多少到 DB）、
   Hikari 活跃连接、Redis QPS、Tomcat 线程占用、GC；拓扑声明（同机压测=保守口径；
   或分离压测：本机压云上/云上压本机，二选一由用户拍板）。
4. **业务量级换算一页**：10~15 站 × 每站柜数 × 仓数 × 日均换电次数（假设须标注"行业锚点"或"自设"）
   → 峰时 QPS → 当前余量倍数。
5. **JVM 排障故事（可复现）**：借压测制造信号（或调小堆/加大并发放大 GC 压力）→ `jmap`/`jstat`/GC log
   定位 → 修复或参数调整 → 前后对比，产出 story-card 素材（对冲"pitfalls 无 JVM 排障"的空缺）。

**验收**：读/写各三档、读路径含 ≥5 分钟稳态；资源画像齐全；量级换算一页；JVM 故事含前后数字。

**估算**：1.5-2 天。**风险**：同机压测资源互抢（口径必须写明）；写链路依赖 sim 状态推进；
需区分"预期失败（无库存）"与"异常失败（5xx/超时）"；RocketMQ 未上云，写路径在本地跑。

> **状态（2026-09-16）：已完成** —— 批次20：prometheus 端点（admin 鉴权保护，health/info 公开）+ 6 项业务指标

**为什么**："线上怎么监控"是高频追问。当前有 actuator（依赖在）、告警、9 任务看护和业务
看板，但没有指标暴露与时间序列。

micrometer-registry-prometheus。

（resources 无 logback-spring.xml，yml 无 `logging.pattern.*`）——TraceIdFilter 写入的 MDC `traceId`
在默认 pattern 下不落日志文本（MQ property/HTTP 头透传本身正常）。随本项一并补 `%X{traceId}` 或结构化日志。

**交付物**：
1. `micrometer-registry-prometheus` + `management.endpoints.web.exposure`（放内网/鉴权保护）。
2. 关键业务指标打点：MQ 消息滞后、延迟任务积压（`DelayQueueService` 可读）、分配失败率、
   对账 violations（复用 `ReconcileService` 的 CheckResult）、工单 SLA 超期数、Hikari/Redis 指标。
3. 本地 Grafana（或截图）一组面板证据 + runbook 补"监控接入"一节。

**验收**：`curl /api/actuator/prometheus` 可见 ≥5 个业务指标；面板/截图留档。

**估算**：1 天。
