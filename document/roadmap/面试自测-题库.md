## 一、分配引擎（4 题）

**Q1. 换电分配为什么用"Redis Lua + DB 条件更新"双层？只用一层会怎样？**
- 考点：并发安全的双层设计动机。
- 要点：Redis 集合 `SPOP` 弹仓 + `SET NX EX` 打仓锁在**一段 Lua 内原子完成**——同刻并发只有一个调用者拿到同一候选（快、无锁竞争风暴）；DB `lock_order_id IS NULL` 条件更新是**最终判官**（Redis 丢数据/主从切换/时钟问题时兜底）。只有 Redis：数据丢失即超卖；只有 DB：高并发下大量条件更新失败重试，DB 成为瓶颈。
- 位置：`order/service/AllocationService.java` — `ALLOC_SCRIPT`、`allocate`。
- 数字：`MAX_ALLOC_TRY=5`（弹到脏候选继续弹）；preempt TTL=120s；实测 20 并发抢 6 仓 → 恰好 6 成功/14 拒/零重复（IT-3 + `_c28`）。
- 失败模式：候选仓状态失效（电池被取走/柜转维护）→ 回滚锁 + 继续弹；5 次耗尽 → 抛"暂无可换的满电电池"。

**Q2. 弹到"脏候选"（仓已不满足条件）怎么处理？为什么不直接失败？**
- 考点：集合与 DB 的最终一致，重试而非失败。
- 要点：分配后立刻校验内容（full 路径要求 cell OCCUPIED + battery FULL + 双向绑定一致；empty 路径要求 cell EMPTY 且无电池）；不通过则 `unlockAndDeleteLock`（条件解锁 + 删 Redis 锁 + 刷新集合）后**继续弹下一个**，最多 5 次。直接失败会把"集合短暂滞后"这种正常现象变成用户可见错误。
- 位置：`AllocationService.allocate` 校验段、`unlockAndDeleteLock`、`refreshByCellId`。
- 数字：MAX_ALLOC_TRY=5；集合由事件/管理态变更驱动同步（`onBatteryOut`/`onBatteryIn`/`onBatteryFull`/`refreshByCellId`），启动 `rebuildFromDb` 全量重建。

**Q3. Redis 整个丢了（RDB 回退/被清），分配还能工作吗？怎么恢复？**
- 考点：降级与重建路径。
- 要点：集合空 → 分配失败（快速失败，不超卖）；恢复靠 `rebuildFromDb()`（按 DB 真值全量重建：只重建"可分配"——未锁定、柜可用 status≤2、状态匹配），混沌剧本已实测"恢复后对账回基线"。DB 始终是权威，Redis 只是加速器 + 原子竞争点。
- 位置：`AllocationService.rebuildFromDb` / `syncCellInto`；`POST /admin/ops/rebuild-alloc`。
- 数字：`_c21` Redis 停机剧本 11/11 PASS；恢复后 rebuild → 对账 total 回 0。

**Q4. 取电/还电事件如何驱动集合与锁的变化？为什么"锁必清"是无条件的？**
- 考点：事件驱动的资源回收。
- 要点：`onBatteryOut`/`onBatteryIn` = `clearLockIfAny`（无条件清 lock_order_id + 删 Redis 锁）+ `refreshByCellId`（按新状态重挂集合）。无条件是因为**事件到达即订单已推进**（设备事实优先），此时锁若还在就是泄漏；而"候选失效回滚"路径用的是**条件解锁**（仅本订单持锁才清），两者语义不同不可混用。
- 位置：`AllocationService.clearLockIfAny` vs `unlockAndDeleteLock`；`DeviceEventService.apply` BATTERY_OUT/BATTERY_IN 分支。

## 二、序守卫与重放（4 题）

**Q5. 设备事件的"序守卫"具体怎么实现？为什么是单条条件 UPDATE 而不是"先查再写"？**
- 考点：原子守卫，避免检查-写入竞态。
- 要点：一条 UPDATE 同时完成"守卫 + 推进基线"：`SET last_boot_id=?, last_event_seq=? WHERE cabinet_no=? AND (last_boot_id IS NULL OR last_boot_id<>? OR (last_boot_id=? AND last_event_seq<?))`。rows=0 即拒绝（幂等丢弃）。先查再写在并发下两个请求都能通过检查（TOCTOU）。
- 位置：`device/service/DeviceEventService.handle` 序守卫段。
- 数字：拒绝时 log.info（同代际旧序/重放，幂等丢弃）并打印已受理 last=bootId/seq；`_c28` 实测注入旧序 → 台账不回退。

**Q6. bootId 变化一律接受，会带来什么漏洞？怎么补？**
- 考点：跨代重放（历史事件借"新代际"过关）。
- 要点：序守卫对 bootId 变化放行（设备重启后 seq 从头，必须接受新代际）；漏洞=攻击者/重投把**历史代际**的事件重放，借"bootId 不同"绕过序守卫。补法=`DeviceBootGenerationGuard`（Redis 记录已见代际；历史已见代际再来即拒），两层互补：DB 守同代际乱序/重复，Redis 守跨代重放。
- 位置：`DeviceEventService.handle` 的 `bootGenerationGuard.isReplay(...)`（在序守卫**之前**）+ 序守卫通过后 `register(...)`；`device/config/DeviceBootGenerationGuard.java`。
- 数字：`_c28` S2 实测——旧 bootId 携更大 seq 注入 → 台账与当前代际均不变（WARN 拒绝行留痕）。

**Q7. 为什么代际登记放在"序守卫通过之后"而不是之前？**
- 考点：状态推进的顺序正确性。
- 要点：若先登记再守卫，被序守卫拒绝的旧序事件也会把代际登记进去 → 后续同代际合法事件被误判为重放。先守卫（确认可推进）再登记，保证"登记的都是被受理的代际"。
- 位置：`DeviceEventService.handle`（`register` 在 `rows>0` 之后）。

**Q8. 分片保序（P0-2）后，保序不变量变成了什么？为什么业务语义没变？**
- 考点：从全局序到每柜序的降级论证。
- 要点：发送端按 `cabinetNo` 设 FIFO message group（同柜同队列、柜内严格 FIFO 投递）；消费端按柜 hash 到固定 worker（同柜串行、跨柜并行）。不变量从"全局单调"降为"**每柜单调**"——而序守卫本来就按 `(cabinetNo, bootId)` 判定，跨柜事件之间本来就没有顺序语义，所以业务不变。
- 位置：`device/mq/DeviceEventMqConsumer`（`dispatch`/`shardKey`/`workerIndexFor`）、`swap-sim .../MqEventReporter.buildMessage`（`setMessageGroup`）。
- 数字：spike 实测（`scripts/verify/batch24/_spike_fifo_out.txt`）——同柜到达序 [1,2,3,4,5]×3 柜；**服务端只保证投递序、不 hold 未 ack 的同柜后续** → 柜内串行必须由消费端保证；workers=4/batch=16/invisible=30s；`_c28` 15/15 PASS（含 worker-0 与 worker-3 并行处理证据）。

## 三、幂等双线（3 题）

**Q9. 下单幂等做了哪两层？为什么一层不够？**
- 考点：应用层查重 + DB 唯一索引兜底。
- 要点：① `idem_key` 查重（同用户同键返回既有单，读多写少时挡住绝大多数重试）；② DB 唯一索引 + `DuplicateKeyException` 捕获（并发同时插入时只有一个成功，失败方回查返回既有单）。只有①：并发双插；只有②：每次重试都打到 DB 异常路径（代价高、日志噪音）。
- 位置：`order/service/SwapOrderService.create`（`byIdemKey` → insert → catch DuplicateKey → 回查）。
- 细节：回查仍无本人订单 = 该幂等键被他人占用 → 拒绝（防跨用户幂等键劫持）。

**Q10. 除了幂等键，下单还有哪两道"活跃态"防线？**
- 考点：业务态防重（与幂等键正交）。
- 要点：① 同用户存在进行中订单（PENDING_OPEN/OPENED/TAKEN/OVERDUE）→ 拒；② 电池持有一致性——TAKE 时已持有电池 → 拒（提示改用 SWAP/RETURN），非 TAKE 时未持有 → 拒。幂等键挡"同一请求重试"，活跃态挡"不同请求但业务上不该并存"。
- 位置：`SwapOrderService.create` 的 ACTIVE_STATUSES 查询 + holder 查询。
- 数字：ACTIVE_STATUSES = 4 态；`battery.holder_user_id` 唯一索引兜"一人一电"。

**Q11. 指令侧的幂等/会话关联是怎么做的（commandSeq）？**
- 考点：指令与事件的会话绑定，重复事件吸收。
- 要点：下发时 `prepareOpen` 生成 commandSeq 并落指令台账 + 写入订单 `open_command_seq`；设备事件回带同一 commandSeq → 订单域用 `(cabinetId, openCommandSeq, status)` 精确定位订单并 CAS 推进；重复事件在 CAS 上自然吸收（第二次 rows=0）。指令台账侧 `markArrivedBySeq` 未命中只 debug 不抛（事件可先于台账到达）。
- 位置：`OrderEventService.findBySeq` / `cas`；`device/service/CommandLogService.markArrivedBySeq`；`SwapOrderService.sendOpenCommand`。
- 数字：IT-1 用 bindSeq(90001/90002) 驱动全链，重复投递不产生二次计费。

## 四、对账 14 组（4 题）

**Q12. 14 组不变量大致分哪几类？举 5 组名字。**
- 考点：对账体系的覆盖面。
- 要点：订单/时序类（stale-active-orders、completed-has-payment）、设备台账类（cell-battery-consistency、holder-consistency、escaped-batteries、battery-counters）、指令类（aging-pending-commands）、资金/结算类（arrears-integrity、settlement-conservation、statement-consistency、settlement-coverage）、运营类（transfer-ledger、stale-agent-actions、coupon-consistency）。
- 位置：`reconcile/ReconcileService.run`（14 个 check 方法清单）。
- 数字：`totalViolations()>0` → 触发 RECONCILE_ERROR 告警；归零 → `markRecovered` 自动关闭。

**Q13. "电池-仓双向一致"这组怎么查？为什么两个方向都要查？**
- 考点：双向引用的断链检测。
- 要点：正向 cell→battery（cell.battery_id 指向的电池存在且其 cell_id 指回本仓）；反向 battery→cell（battery.cell_id 指向的仓存在且其 battery_id 指回本电池）。只查一个方向会漏"半写悬挂"（例如电池已被取走但仓仍引用它，或电池记着仓但仓已清空）。
- 位置：`ReconcileService.checkCellBatteryConsistency`（样本前缀 `cell→battery:` / `battery→cell:`）。
- 数字：IT-2 注入 `battery_id=999999999` → 该组 violations 恰好 +1、样本含 `cell→battery`、总数 +1；恢复后回基线。

**Q14. 对账发现差异后怎么处置？会自动改数据吗？**
- 考点：只读核查 + 人工/告警闭环。
- 要点：对账是**只读**核查（不改业务数据），产出 CheckResult（name/violations/samples）+ 告警（RECONCILE_ERROR，附摘要）+ 报告落库；修复走明确路径：能自愈的走 rebuild（分配集合）、设备侧走 QUERY_STATE 主动对账、资金侧走人工/客服流程。自动改数据会把"检测"与"修复"耦合，风险不可控。
- 位置：`ReconcileService.run`、`DailyReconcileTask.runAndStore`、`MonitorReconcileTask`（指令重试超限 → 转人工 + 订单 EXCEPTION）。
- 数字：monitor 巡检间隔 15s、单轮上限 100；stale-margin 3600s、window 24h、sample-limit 200。

**Q15. 为什么"活跃单卡滞"判定要加 stale-margin，而不是直接用业务超时阈值？**
- 考点：避免与在途延迟任务打架（误报）。
- 要点：业务超时（preempt 120s/pickup 120s/overdue N 小时）由延迟任务负责推进；对账若用同一阈值会在"任务还没来得及跑"的瞬间误报。加 stale-margin（3600s）= 只报"超时后仍长期无人处置"的真卡滞。
- 位置：`ReconcileService.checkStaleActive`（preemptDeadline/pickupDeadline/overdueDeadline 都加 margin）。
- 数字：`swap.reconcile.stale-margin-seconds=3600`。

## 五、延迟任务与看护（4 题）

**Q16. 自研延迟任务器怎么实现？多实例为什么安全？**
- 考点：Redis ZSET 时间轮 + 原子领取。
- 要点：ZSET（score=执行时刻，member=taskId）当时间轮 + HASH 存载荷与重试计数（ZSET member 要短小稳定）；领取 = 按分数范围取到期集合 → 逐个 `ZREM`，**ZREM 返回 1 才算本实例领到**（原子竞争，无需额外锁）；取消 = ZREM + HDEL；成功 = 清载荷；失败 = 计数 +1 + 退避重排；超上限 → 死信 HASH。语义 at-least-once（领取后实例崩溃则本轮丢失，由业务扫描任务兜底，处理器需幂等）。
- 位置：`common/delay/DelayQueueService`（`claim`/`complete`/`fail`）、`DelayScheduler.poll`（@Scheduled fixedDelay 1s，遍历已注册 topic 的 handler）。
- 数字：poll 间隔 1s、批量由 `swap.delay.batch` 控制；Redis 抖动时本轮跳过（任务留队列下轮再领）。

**Q17. 为什么不用 Quartz？什么情况下该换？**
- 考点：选型取舍（ADR-5）。
- 要点：本项目的"延迟"是**大量短周期、业务态驱动**的一次性定时（preempt 120s、pickup 120s、overdue N 小时），不是 cron 计划任务；Quartz 的 JDBC JobStore 行锁在这种量级下是负担，且 misfire 语义与业务超时语义不匹配。ZSET 方案 30 行核心逻辑、天然多实例安全、任务载荷即业务键。该换的信号：需要 cron 日历/复杂依赖编排/任务历史与重跑治理/跨数据中心调度。
- 位置：ADR `document/knowledge/decision-records.md` §5；对照范例项目 `inteink-faster` 用 Quartz（cron 型任务）。

**Q18. 定时任务看护（watchdog）怎么判"任务卡住"？为什么不会启动即误报？**
- 考点：以"最近成功时刻"为数据源的心跳看护。
- 要点：每个任务成功执行后 `beat(name)` 写最近成功时刻；看护扫描发现"超过登记周期 × N 倍未见心跳" → 报 JOB_STALLED，恢复自动关闭。首次未见时刻 = 注册基线（给一个周期宽限），避免启动瞬间误报。看护自身也被锁保护（多实例只有一个在扫）。
- 位置：`alarm/service/TaskWatchdog`（JOBS 登记表 + `beat` + `doScan` 走 `runWithLock("task-watchdog", ...)`）。
- 数字：全仓 `watchdog.beat(` 9 处（9 个被看护任务）。

**Q19. 多实例下"同一扫描任务只在一个实例执行"靠什么？锁失效会怎样？**
- 考点：租约锁语义与降级取向。
- 要点：`JobLockService.runWithLock(jobName, task)` = `SET NX PX`（TTL 60s 短租约）+ Lua 比对持有者 token 释放（防误删他人锁）；未抢到返回 false（跳过本轮＝正常多实例行为）。**Redis 故障时选择"宁可双跑不可停扫"**（降级直接执行）——因为所有扫描任务本身幂等，停扫的代价（漏处置）大于双跑（重复检查）。
- 位置：`common/lock/JobLockService`；11 处调用（offline-scan / task-watchdog / battery-health-scan / monitor-reconcile / refund-compensation / order-sweep / outbox-relay / channel-recon(-io) / daily-reconcile）。
- 数字：lock TTL 60s；任务须在 TTL 内完成（超时自动释放，下一轮补扫兜底）。

## 六、缓存一致性（4 题）

**Q20. 两级缓存的读路径与三道防护（穿透/击穿/雪崩）分别怎么做？**
- 考点：标准缓存形态的完整落地。
- 要点：读 = L1(Caffeine) → L2(Redis JSON) → 回源，回填两级；**穿透** = 空值短 TTL 缓存（Caffeine 不允许 null → 显式 NULL 哨兵）；**击穿** = 进程内 per-key 单飞锁 + Redis `SETNX` 跨实例重建锁（未抢到 → 200ms 重读 L2 → 再降级回源）；**雪崩** = L2 TTL 加随机抖动（不同键错峰过期）。
- 位置：`common/cache/TwoLevelCacheService`、`LocalCacheInvalidator`（L1 持有者 + Pub/Sub 接收端）、`common/cache/CacheKeys`（一 key 一常量）。
- 数字：重建锁键 `swap:cache:lock:{key}`、数据键 `swap:cache:data:{key}`；运维读指标 `GET /admin/cache/stats`（命中/回源/降级计数）。

**Q21. 写路径怎么保证一致性？Pub/Sub 消息丢了怎么办？**
- 考点：失效广播 + 兜底 TTL + 延迟双删。
- 要点：写路径 evict = 删 L2 + 本地 L1 失效 + Redis Pub/Sub 广播其他实例失效；**广播可能丢**（Redis 无持久化的 pub/sub）→ 由 L1 TTL 兜底（最终一致窗口 = L1 TTL）；另有**延迟双删**（守护线程延时二删，只补删 L2）防"旧值在删后被并发读回填"。原则："谁改谁清"——失效只由业务写路径触发，缓存运维端点只读（可审计）。
- 位置：`TwoLevelCacheService`（`delayedEvictExecutor`）、`CacheAdminController`（只读 stats，`@PreAuthorize('admin:cache:read')`）。

**Q22. Redis 挂了缓存层会怎样？为什么这是"fail-open"？**
- 考点：读路径降级取向。
- 要点：Redis 异常**不抛错**——跳过 L2 直读 DB（只降性能不降正确性）。前提是缓存只承载"展示/字典类读"（套餐目录、站点元数据、看板总览），DB 能扛住降级期的读压力；若把资金/库存放进来，fail-open 就等于把正确性押在 DB 上，风险不可接受。
- 位置：`TwoLevelCacheService` 降级分支；红线注释（仅展示/字典类读；资金、库存、订单状态禁止经此缓存）。
- 数字：`_c21` Redis 停机剧本——DB 路径（admin reconcile）停机期间仍可用。

**Q23. 看板总览为什么要"受限身份绕缓存"？**
- 考点：缓存与数据权限的交叉（P1-8）。
- 要点：`dashboard:overview` 缓存的是**全局**聚合；站点范围管理员若命中该缓存就会看到越域数据。所以受限身份（`stationIdsOrNull() != null`）直接走 `compute()` 现算（按数据范围过滤），不读也不写全局缓存；非受限身份才享受缓存。
- 位置：`admin/service/DashboardService.overview`（受限绕缓存）+ `compute`（三处 apply：batteries 经 scopeCellIds、stations、orders）。

## 七、资金与欠费化（4 题）

**Q24. 计费顺序是什么？为什么套餐优先于余额？**
- 考点：计费策略与用户利益取向。
- 要点：TAKE/SWAP 计费 = 有可用套餐 → 扣次（payType=PLAN，流水 PLAN_DEDUCT）；无套餐 → 余额扣单次费（balance-fee-fen）；余额不足 → **不硬失败**，转欠费单（见 Q26）。套餐优先因为用户已付费购买（先消耗已购权益符合直觉与合规），余额是兜底。RETURN 不收服务费，只退押金（DEPOSIT_REFUND）。
- 位置：`order/service/BillingService.charge`；`SwapOrderService.create` 的资格校验（无套餐且余额 < 单次费 → 拒；TAKE 且押金 0 且余额 < 押金 → 拒）。
- 数字：deposit=9900 分、balance-fee-fen=300 分；IT-1 实测套餐 5→4 + PLAN_DEDUCT 流水 + RETURN 押金 9900→0 + feeFen=0。

**Q25. 押金的"缴"与"退"分别在哪条路径？为什么人工退款不能再退押金？**
- 考点：资金口径唯一（历史真实缺陷）。
- 要点：缴 = TAKE 完成时（押金不足则拒单）；退 = **RETURN 还电完成**时 `WalletService.refundDeposit`（押金转余额 + DEPOSIT_REFUND 流水）。缺陷史：`RefundService.REFUNDABLE_TYPES` 曾含 DEPOSIT → 人工退款按 payment_record 里的 DEPOSIT 流水再退一次 = **二次退款**。修复：REFUNDABLE_TYPES 移除 DEPOSIT（押金退回只能由 RETURN 触发）+ 人工退款加状态约束（COMPLETED 单拒绝、可退金额 0 拒绝）+ 状态矩阵单测。
- 位置：`fixes/deposit-double-refund.md`；`order/service/RefundService`、`admin/controller/AdminRefundController`。

**Q26. "计费硬失败欠费化"解决了什么问题？欠费单的生命周期？**
- 考点：可用性与资金安全的平衡（ADR-8）。
- 要点：还电时若超时费 > 余额，原设计会让**计费失败阻塞还电**（用户还不掉电池、仓一直被占）。改为：计费不足额 → 生成欠费单（同订单唯一，在计费事务内累加）+ 订单照常完成；门槛 = TAKE/SWAP 存在 OPEN 欠费**拒单**，RETURN **放行**（防逼停归还，越堵越还不掉）；结清 = 余额补缴（CAS 扣款同事务）或客服减免 → 自动关 ORDER_ARREARS 告警 + 站内信。
- 位置：`user/service/ArrearsService`（`hasOpenArrears`）、`SwapOrderService.create` 欠费门槛、`user/controller/UserArrearsController`（`POST /user/arrears/{id}/pay`）。
- 数字：`fixes/resilience-patch.md`（G1）；对账组 `arrears-integrity` 守欠费台账自洽。

**Q27. 资金类写操作为什么普遍用 CAS（条件更新）而不是事务加锁？**
- 考点：并发资金安全（ADR-1）。
- 要点：钱包/套餐次数/订单状态都用"条件 UPDATE + 判 rows"实现乐观并发：`balance >= amount` 才扣、`status=from` 才迁移、`holder_user_id IS NULL` 才绑定持有人。好处=无锁等待、天然幂等吸收重复请求、失败即业务拒绝（不是死锁/超时）；代价=高冲突下重试增多（本项目冲突率低：单用户串行操作）。悲观锁（SELECT FOR UPDATE）会在热点行上排队并放大死锁面。
- 位置：`user/service/WalletService`（CAS 资金操作）、`OrderEventService.cas`、`OrderEventService.assignHolder`（holder 唯一索引兜"一人一电"）。
- 数字：单测"钱包（CAS 资金操作）"6 用例；IT-1/写路径剧本断言"计费恰一次"。

## 八、RBAC 与审计（3 题）

**Q28. 管理端鉴权是几轨并存？break-glass 是什么、为什么保留？**
- 考点：身份体系与应急通道收编。
- 要点：① 账号密码登录（BCrypt + JWT，`admin_user` 表，角色 SUPER/OPS/AGENT 等）；② 静态 token（`X-Admin-Token`，环境变量注入、仓库零明文）——即 break-glass：账号体系/DB 出问题时仍能进管理端处置，但**收编**在统一过滤器与权限码体系内（不是绕过后门），并全程留审计。未配置 token 则启动失败（fail-fast，不允许空密钥放行）。
- 位置：`admin/security/`（AdminAuthFilter / AdminContext / AdminSecrets）、`admin/config/AdminSecurityConfig`（securityMatcher 仅 `/admin/**`）。
- 数字：ADR-9；密钥红线（`.local/*.txt` gitignored，env 注入）。

**Q29. 数据权限（DataFilter）怎么做到"fail-closed"？漏接一个接口会怎样？**
- 考点：数据范围的解析、生效与自检（P1-8）。
- 要点：登录期解析 `data_scope`（ALL/STATION）+ `scope_station_nos` → 放入 AdminContext；查询侧用 `DataScopeSupport.applyStation/applyIds`（类型安全 `.in()/.eq()`，不拼 SQL 字符串）；**fail-closed**：解析异常 → 视为空集；空集 → `eq(列, -1)` 恒假（宁可看不到，不可看多了）；无归属资源操作（在途电池/无站资源）→ 403。漏接自检：`@DataFilter` 注解 + 切面在受限身份执行后检查"是否真的 apply 过"，未 apply → WARN 告警（0 漏接是验收项）。
- 位置：`admin/data/DataScopeSupport`（applyStation/applyIds/cabinetIdsOrNull/cellIdsOrNull/requireStationAccess/requireUnrestricted）、`DataScopeGuard`、`DataFilterAspect`、`AdminAuthFilter`（finally 清 context）。
- 数字：`_c27` 24/24 PASS（6 类列表过滤 + 越域详情/写入 403 + 无副作用复查）；单测 +15（371→372 含分片）。

**Q30. 操作审计留了什么？谁写、写在哪、能否被业务绕过？**
- 考点：可追溯性。
- 要点：`@AdminLog` 注解 + 切面记录管理端写操作（操作人/角色/动作/目标/结果/耗时/traceId）落 `admin_op_log`；设备侧留痕走指令台账（command_log）与事件台账；traceId 经 MDC 贯穿日志与 MQ property/HTTP 头。业务代码不手写审计（注解声明式），绕过路径=不加注解 → 由"管理端点注解覆盖守卫"单测钉住（端点必须有权限码/审计注解）。
- 位置：`admin/annotation/AdminLog` + 切面、单测"管理端点注解覆盖守卫"、`common/filter/TraceIdFilter`。
- 数字：批次20 起 traceId 落日志 pattern（`%X{traceId}`）；Prometheus 6 项业务指标 + 告警出站 webhook（RAISED/HANDLED/RECOVERED，HMAC 验签）。

## 九、管理台与 BFF 视图层（S8，3 题）

**Q31. 管理台为什么要 BFF 聚合层，而不是前端直接调各域接口？**
- 考点：前后端边界与"一次请求拿到一个页面所需"的设计。
- 要点：域接口是**写模型视角**（工单/订单/柜/结算各自为政），页面是**读模型视角**（工单详情要"工单 + 流转日志 + 关联告警 + 可执行动作"）。若前端拼装：① N 次往返、页面 loading 碎片化；② 组装逻辑散在前端，规则一变要改多个页面；③ 前端要理解内部枚举与关联关系，等于把领域知识漏给浏览器。BFF 收口为 **11 个 `/admin/view/**` 聚合端点**：后端一次查全、一次算好 `allowedActions` 能力位、并把内部列（`idemKey`/柜 `secret`/`eventKey`）挡在响应之外。
- 位置：`web/view/controller/AdminViewController`（11 端点）、`web/view/service/{AdminObservationViewService, AdminWorkflowViewService, AdminFinanceViewService}`、`web/view/AdminViews`（VO 定义）。
- 数字：`_c32` 54/54（视图聚合 + 权限码 37 + 能力位逐态）、`_c34` 59/59（8 页端点形状 + 前端 `types.ts` 字段镜像 + 内部列不外泄）；OpenAPI 101→109 paths。

**Q32. 按钮的可用性由谁决定？为什么不让前端自己判断状态？**
- 考点：能力位（capability bits）与服务端权威。
- 要点：前端只渲染，**不推理**：后端按资源当前状态算 `allowedActions`（工单五步链 OPEN→…→CLOSED、订单退款 vs 冲正二选一、结算单 GENERATED→confirm / CONFIRMED→paid / PAID→none），前端用 `v-access` + 能力位决定按钮显示与禁用。若前端自己判断：状态机一改就要发版、且前后端判断可能不一致（前端允许点、后端拒绝＝难看的 4xx）。另外菜单与路由也由后端下发的权限码过滤（37 个码），页面拿不到码就不可路由。
- 位置：`common/action/ActionsSupport`、`web/view/service/*ViewService` 的能力位计算、前端 `src/directives/access.ts`、`src/router/index.ts` 的 `meta.codes`。
- 数字：`_c34` 的能力位逐态断言（工单 5 态 / 订单 refund-vs-reversal / 结算 3 态）；`_c35` B04 菜单 6 项按身份过滤。

**Q33. 同源部署解决了什么问题？CORS 方案被否决的理由？**
- 考点：部署形态与安全边界。
- 要点：nginx 同时托管 `dist/` 与反向代理 `/api` → 浏览器只与一个源通信：① 不需要 CORS（不需要 `Access-Control-Allow-Origin` 白名单，也就没有配错就放开全站的常见事故）；② 不需要前端配置后端地址（`baseURL` 恒为 `/api`，本地 `vite preview` 用同样的代理规则，本地/线上形态一致）；③ Cookie/token 不受跨站策略限制。代价：前后端必须同域部署，独立 CDN 分发要另做。
- 位置：`scripts/cloud/nginx-swap.conf`、`swap-web/vite.config.ts`（server.proxy 与 **preview.proxy** 两份，后者常被漏）。
- 数字：`_c35` 走 `vite preview` 构建产物（等价 nginx 形态）31/31；云上 `probe-web.sh` 冒烟 16/16（含安全响应头）。

## 十、界面质量与可访问性（批次38/39，3 题）

**Q34. "界面看起来对不对"这件事，你是怎么验证的？**
- 考点：验证手段的分层与各自的盲区。
- 要点：三层，各管一段：① **能否渲染**——真实浏览器走查（`_c35`，零依赖 CDP + 本机 headless Chrome，31 项）；② **布局/对比度对不对**——DOM 测量探针（`_c38`，10 条路由 × 7 条硬门禁：横向溢出/裁切/表头错列/表头截断/标签与全部文字对比度/零尺寸元素）；③ **像不像给面试官看的东西**——视觉模型逐张复核（`deepseek-v4-flash-vision-exp`）。关键纪律：视觉模型只是**疑点生成器**——它报的定量主张一律回落到 DOM 测量结案；它对 12px 小字不可信（会把"读不出"说成"没渲染"），但对"某处空/缺"有提示价值。实测：三轮视觉复核 18 个 agent，其中"表头整体错位一列"被 DOM 否掉（89 列 `deltaLeft=0`），而"分账流水只截到第 12 行"是**真的**（我的"整页截图"实际只截一屏）。

## 十一、索引与访问路径（批次40，3 题）

**Q37. 你怎么证明"这条查询有索引可用"？为什么要打流量？**
- 考点：数据库侧证据链的取法。
- 要点：三层，缺一层就不算证明：① **审计**——问服务器而不是读代码：`performance_schema.events_statements_summary_by_digest` 记录每类语句的执行次数、`SUM_NO_INDEX_USED`、`SUM_ROWS_EXAMINED`；用"表大小 + 每次扫多少行"过滤噪音（10 行柜表全扫是正常设计，5,000 行表每次扫 4,000 行才是缺陷）。② **计划**——`EXPLAIN` 断言 `type≠ALL` 且 `key≠NULL`，外加**索引前导列存在性**的 schema 断言（这条不依赖优化器当下选择，正是本次缺陷的形状）。③ **因果**——计数器是**自 MySQL 启动以来累计**，含修复前历史，**不能直接当判据**；正确做法是"读计数器 → 打真实 HTTP 流量 → 再读"，断言"执行数涨、无索引次数不涨、每次扫行数塌到约等于返回行数"。实测：`payment_record WHERE order_id = ?` **8,090 → 1 行/次**；告警"全部"页签 **4,032 → 20 行/次**（=LIMIT）。
- 位置：`scripts/verify/batch40/_c39_index_audit.ps1`（15 项，全程只读）、`db/19-index-audit-fixes.sql`、`document/pitfalls/dropped-index-also-served-read-path.md`。
- 数字：审计 666 条 digest；修前该语句 5,068 次无索引、累计扫 40,641,477 行只返回 6,629 行；门禁 `_c39` 15/15。

**Q38. 有没有遇到"改了 A 结果 B 坏了"，而且是数据层？**
- 考点：索引的双重职责与迁移的隐性影响。
- 要点：有，而且是本仓库自己造成的。为修"同一订单第二笔部分退款台账漏记"（AUD-6），把 `uk_order_type(order_id, payment_type)` 换成生成列唯一键 `uk_payment_idem`——**那个唯一键担了两个职责**：①资金动作幂等闸（唯一性）②`WHERE order_id = ?` 的**唯一**访问路径（可访问性）。改 ① 时 ② 被静默删掉：查询结果依然正确，没有任何测试会红（单测/契约/浏览器/覆盖率四层全绿）。旁证很有说服力：同形状但走索引的另一支 digest `LAST_SEEN=2026-09-17 10:26`，此后只剩全表扫那一支——访问路径消失的时间线看得见。修法：补**非唯一** `idx_order_id`——"恢复访问路径"与"恢复唯一约束"是两件事，重建唯一键等于把 AUD-6 退回来。
- 位置：`db/18-payment-ledger-idem.sql`（制造者）、`db/19-index-audit-fixes.sql`（修复）、`document/roadmap/独立审计发现与处置.md` AUD-6/AUD-12。
- 数字：54,647 次执行 / 5,068 次无索引 / 每次 ~8,090 行；修复后 `type=ref key=idx_order_id rows=1`。

**Q39. 除了"慢"，还有什么数据库侧的隐患值得加门禁？**
- 考点：从个案到类别的抽象能力。
- 要点：**无界读**——`SELECT` 既无 `WHERE` 又无 `LIMIT` 就是结构上无界，随表增长必然出事。批次40 的审计发现一条未归属语句（`SELECT <全部列> FROM swap_order ORDER BY create_time DESC`，6 次、每次返回 5,832 行），三处搜索（Java 源码/`scripts/`/`.local/`）都定位不到调用方——对一条**已经停止**的语句继续考古是错的取舍，正确做法是加**守类**判据：应用 schema 里既无 WHERE 又无 LIMIT 且每次返回 >500 行的 SELECT，最近 30 分钟内出现即 FAIL、更早记 INFO。首跑就报出**两条**（swap_order 与 alarm 各一条，形状一致、最后出现都在同一个 02:00–03:00 窗口）。判据不依赖"它是谁发的"，一旦回来立刻显形。
- 位置：`scripts/verify/batch40/_c39_index_audit.ps1` §4、`document/block-records/批次40-索引访问路径审计.md` §八。
- 数字：`_c39` 15/15（0 active / 2 historical 无界读）；两条语句分别为 5,832 行/次与 3,854 行/次。

## 十二、交付与部署（批次37 + 云上，3 题）

**Q40. 别人拿到仓库怎么跑起来？容器化路径验证到什么程度？**
- 考点：交付门槛与"可复现"的证据。
- 要点：compose 起中间件（MySQL/Redis，`./db` 挂进 initdb ⇒ **全量 20 个迁移在首次启动自动执行**，实测建 33 张表）→ 构建镜像（非 root uid 10001、`HEALTHCHECK` 打与 systemd 部署同一端点、`-XX:MaxRAMPercentage=70` 让堆跟容器限额走、**零密钥烘焙**全部环境变量注入）→ `--network host` 起平台 → 容器内外登录并调用 BFF 视图端点。这条路径**每次 push 由 CI 的 `docker` job 真跑一遍**（约 1 分半），不是文档承诺。取舍如实说：冒烟用 `--network host`（不验证"容器网络 + 服务名解析"那条更贴近生产的路径）；镜像未做漏洞扫描、未按 digest 固定基础镜像。
- 位置：`Dockerfile`、`.dockerignore`、`scripts/cloud/ci-container-smoke.sh`、`.github/workflows/ci.yml` 的 `docker` job。
- 数字：CI run 35441007154 `docker` job 1m24s；compose 建表 33 张；`admin login ok after 2 attempt(s)`。

**Q41. 健康检查返回 UP 就代表服务可用吗？**
- 考点：就绪与存活的区别。
- 要点：不代表。容器冒烟首跑失败（`FATAL admin login failed`）时，日志显示 Tomcat 已启动、`/actuator/health` 返回 UP，但 **DevSeeder 仍在逐柜播种**（日志里 1→10 号柜"联调种子就绪"逐条刷出），而**引导管理员账号是种子流程的最后一步**——一次性登录与种子赛跑，拿不到 token。修法：登录改为每 3s 轮询、最多 20 次（低于登录限流 5 次/5s），实测第 2 次成功。结论：**等待条件应对齐"业务可用"而不是"端口可连"**；任何"启动即预热/迁移/回填"的服务都有同类窗口（生产 `swap.dev.enabled=false` 无种子问题，但迁移/回填同理）。
- 位置：`scripts/cloud/ci-container-smoke.sh`（轮询登录）、`document/block-records/批次37-容器化路径与CI容器冒烟.md` §四。
- 数字：健康 UP 与业务可用之间实测相差约 3–6 秒（2 次轮询成功）。

**Q42. 云上是怎么部署的？为什么公网不放行？**
- 考点：部署形态与安全取舍。
- 要点：云上 **systemd 跑平台 + nginx 同源站点**（托管 `dist/` 并反代 `/api`），不是容器（容器路径服务于"别人 5 分钟跑起来"）。公网**不放行** 8400/8500，ufw 仅 22：管理端与资金接口在公网需先过一轮渗透，而演示用 SSH 隧道即可（`ssh -L 80:127.0.0.1:80`）。限制级证据：`probe-web.sh` 冒烟 16/16（含安全响应头——注意 nginx 的 `add_header` **不会继承进声明了自己 add_header 的 location**，要在每个这样的 location 重复声明）。部署脚本可重复执行（web 产物发布 + nginx 站点 + 过期站点退役）。
- 位置：`scripts/cloud/{deploy-web.ps1, rollout-web.sh, probe-web.sh, nginx-swap.conf, retire-stale-nginx-sites.sh}`、工作区根《服务器连接文档.md》。
- 数字：`probe-web.sh` 16/16；健康轮询 ≤80s（修过"固定 sleep 10 秒"导致的假 FAIL + 502）。
- **补充（批次42/43）：怎么证明线上跑的就是仓库里的这版？** "200 OK"区分不了新旧包——这正是"repo 修好了、演示站点还是旧的"能发生的原因。
  批次42 用**人工**比三重指纹（资产同名 / 令牌值 / 覆盖顺序）；批次43 把它升级成**部署脚本的硬断言**：
  `deploy-web.ps1` 把本地构建 css 的 **md5** 当参数传给远端 `rollout-web.sh`，**先验后发**——staging 里的 md5 不匹配就在
  快照/迁移/换 jar/重启**之前**退出（一个字节都不动）；发布后再校验"线上字节 == staging 字节"且"`index.html` 确实引用该资产"
  （防"200 的 HTML + 404 的 bundle"这种任何 uptime 检查都读成"站点正常"的形态）。实测三方一致
  `index-DS8f1Y5V.css` md5 `c82cc305f20a54dc376bc308a86c9c97`。**并给这条断言做了负控**：传错误 md5 → 拒绝，
  且三个不变量都没变（线上 CSS 字节 / 服务启动时间 / 库 schema）。边界也要说：断言验的是"**推上去的 == 构建出来的**"，
  不是"构建的是最新源码"——忘了 `npm run build` 会推出**旧的正确产物**而断言通过。

## 十三、验证手段自身的可信度（批次43，4 题）

**Q43. 你的门禁报了"0 个问题"，我怎么知道它真的看了东西？**
- 考点：门禁的**自检**——"沉默型"失败（测了个空集，所有计数为 0，读起来和干净页面一模一样）。
- 要点：三层自检，每层都配负控：① **作用域非空**——`probeExpression` 返回值里加 `scopeElements`（量到多少元素：标签+文字+对齐列+裁切格+表+空列），
  为 0 判 FAIL（弹窗作用域是按表达式解析的，表达式写错就会永远测一个空子树且持续报绿）；
  ② **作用域指纹**——"非空"只是必要条件：指到页面里另一个非空但无关的子树照样报绿。所以页面作用域必须含 `.page-title`，
  弹窗作用域的 `innerText` 签名必须含该弹窗自己的标题（用 `titleAny` 容纳退款/冲正这类动态标题）；
  ③ **最紧余量**——新增 `worstText`（本次测量中比值最低的文字元素），页面级/校验态/变体矩阵各报一次 + 全轮汇总，
  实测 `4.7:1 (needs 4.5) "::placeholder \"订单号（模糊）\""`。**"0 个不达标"不含余量信息，"最紧 4.7:1"才含**。
- 位置：`scripts/verify/batch31/_c38_ui_probe.mjs`、`document/block-records/批次43-门禁可红性实证.md` §七/§8.1/§8.7。
- 数字：`every measurement scope matched its fingerprint (page .page-title missing: 0, dialog title mismatch: 0)`；全轮最紧 4.70:1。

**Q44. 举一个"报告里写没问题、其实根本没测到"的例子，后来怎么关掉的？**
- 考点：覆盖率与"跳过"的语义。
- 要点：`_c38` 弹窗轮长期稳定输出 `2 measured, 2 skipped`，SKIP 理由统一写"opener absent（`allowedActions` 决定，可能没数据）"。
  但"驳回建议单"的入口按钮在**建议单页签**下，而 `/alarm` 默认停在**告警页签**——那不是数据条件，是**少点了一次**；
  SKIP 把覆盖漏洞伪装成了数据条件。修法是给弹窗加 `preStep`（先点页签），并把 SKIP 分成**两种可区分的原因**
  （"opener 确实不在" vs "preStep 跑不动"）。改完立刻量到驳回弹窗里的输入计数器 `"0 / 200"` **3.08:1**。
  第二类例子是**只有主动构造状态才看得见的文字**：表单校验红字（`.el-form-item__error`，EP 用 `--el-color-danger` `#f56c6c` = **2.90:1**）
  只在规则失败时存在，扫 1936 个已渲染元素永远碰不到——做法是登录表单**空提交**（`onSubmit()` 会 `await validate()`，
  失败即 return），并断言**零请求**（CDP 数 `/admin/auth/login` 的次数，实测 0），即"我测的是安全状态"是**证据**不是承诺。
  首跑顺手又发现登录页提示条文案 **2.80:1**（`--el-color-info` 当文字色，批次38 标签那种写法的**第三个组件**）——
  登录页从来不在探针的路由列表里。
- 位置：`scripts/verify/batch31/_c38_ui_probe.mjs`（`preStep`/`titleAny`/校验态轮）、`document/block-records/批次43-门禁可红性实证.md` §8.2/§8.4。
- 数字：弹窗 1 → **2** 个实测；校验态 + 10 个告警变体进入门禁；`_c38` 文字元素 ≈1970、`hardFailures=0`。

**Q45. 条件渲染的组件（这里只有一种状态会被渲染出来），你怎么验证其它状态？**
- 考点：抽样偏倚 + "只为看得见的那一个变体验证过，是靠运气验证"。
- 要点：`el-alert` 有 5 类 × 明/暗两种效果，而应用里三个告警**全是条件渲染**（看板要 STATION 数据范围、订单要退款提示），
  真实页面最多只能看到登录页那一个。做法：把那个**真实告警克隆 10 份**（变体名写进标题文本，失败会自己报名），
  挂到一次性宿主里，**用门禁自己的 `probeExpression` 测量**（测的是产物 CSS 的真实级联，不是对样式的推演），
  实测 `10 variants, 10 measured, 0 below (worst 6:1 "success/light")`。边界如实说：这是**真实级联但不是真实实例**，
  它让"五个变体都可读"第一次成为**可检命题**。同批还给两条新检查补了负控（C6 把 EP 原色 `#e6a23c` 还原到 warning 浅底 →
  矩阵 **1/10 最差 2.04:1**；C7 把 `#f56c6c` 还原到校验红字 → **1/8 最差 2.9:1**），负控总数 12 → **21**。
- 位置：`scripts/verify/batch31/_c38_ui_probe.mjs`（`alertMatrixExpression`/`ALERT_MATRIX_SCOPE`，导出给负控复用）、`_c40_ui_negative_control.mjs`。
- 数字：10 变体 0 不达标（最差 6:1）；负控 21/21。

**Q46. 改一行 CSS 修对比度，为什么改完"看着对"却仍然没生效？**
- 考点：级联特异性 + 静默失效 + "验收标准是测量值"。
- 要点：输入计数器 `"0 / 200"` 用 `--el-color-info`（`#909399`）画，白底 **3.08:1**。第一版覆盖写成
  `.el-input__count{...}`（特异性 **(0,1,0)**），而 Element Plus 是 `.el-input .el-input__count`（**(0,2,0)**）——
  **特异性优先于顺序**，写在后面完全救不了；构建通过、产物里搜得到这行、位置也真的在厂商 CSS 之后（byte 361996 vs 180439），
  门禁复跑**仍然 3.08:1**，而且**没有任何报错**。修法：选择器对齐 EP 的权重；超限态 `.is-exceed` 保留"危险色"语义但换成站点红
  `#8f2b2b`，选择器**照抄 EP 的 (0,4,0) 形状**（否则会被自己的修复反杀）。**验收标准是门禁测量值变了，不是文件看着对**。
  同一个"静默成功"在部署侧也有一次：服务活着 + 200 不代表新包上线（见 Q42 补充）。
- 位置：`swap-web/src/styles/global.css`、`document/pitfalls/css-override-loses-to-element-plus-specificity.md`。
- 数字：计数器 3.08:1 → 达标（次级文字令牌，≈6.1:1）；校验红字 2.90 → **8.24:1**（探针实测样例）；告警文案 2.80 → 达标。

## 自测协议（执行方式）

1. **抽题**：随机抽 5 题（13 类各至少 1 题/周），不看代码、不看文档。
2. **口述四段**：设计动机 → 替代方案与否决理由 → 失败模式与兜底 → 关键数字（阈值/TTL/实测值）。
3. **录音复盘**：对照本题"答案要点/位置/数字"逐条打分（缺一条即未过）。
4. **回源核对**：未过的题打开对应文件核对，把错点写进错题本（含"我以为的 vs 实际"）。
5. **周期**：每周复测一次错题本；连续两次全对的题移出错题本。
6. **红线**：不允许"背话术"——要求能白板画出数据流（如分配的双层、事件的双守卫、缓存的三道防护），
   并能说出**每个数字的出处**（哪条命令/哪个 `_out.txt` 能复现它）。
