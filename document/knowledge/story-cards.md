## 卡 1 · 押金二次退款（资金安全，红队审查发现）

- **现象**：一条"合法调用序列"能把同一笔押金退两次：TAKE 缴押金 9900 → RETURN 退押金 → 再 TAKE → 管理端 `admin/refund` 又退 9900。资金账不平，但每一步单独看都"成功"。
- **定位**：退款口径与业务口径**双轨并存**——`RefundService.REFUNDABLE_TYPES` 把 `DEPOSIT` 列为可退类型（按 `payment_record` 流水累加可退额），而押金实际退回是由 RETURN 流程的 `WalletService.refundDeposit`（押金转余额 + DEPOSIT_REFUND 流水）完成的。两条路径都"有权"退同一笔钱。附带发现两个弱点：人工退款无订单状态约束（COMPLETED 单也能退）、退款无操作人留痕。
- **修复**：① `REFUNDABLE_TYPES` 移除 `DEPOSIT`——押金退回**只能**由 RETURN 业务路径触发（口径唯一化，注释与文档同时写明）；② `AdminRefundController` 加状态与金额约束：COMPLETED 单拒绝（指向正规重复退款流程）、可退金额为 0 拒绝（0 元退款单会污染对账）；③ 补 `RefundServiceTest`（口径矩阵：押金排除/累计上限）与 `AdminRefundControllerTest`（状态矩阵）。
- **防回归**：对账组 `completed-has-payment` / `settlement-conservation` / `statement-conservation` 守资金守恒；人工退款走 `@AdminLog` 审计（操作人/目标/结果可追）。
- **数字**：押金 9900 分；单次余额计费 300 分；IT-1 实测 RETURN 后押金 9900 → 0 且仅 1 条 DEPOSIT_REFUND 流水。
- **出处**：`document/fixes/deposit-double-refund.md`（S7 WP-0）。
- **可讲的通用教训**：资金类"可退额度"不能由流水表反推，必须由**业务事件**定义；同一笔钱出现两条退款路径＝必然被用出来。

## 卡 2 · Redis 无超时 → 全站瘫痪（混沌演练驱动）

- **现象**：kill Redis 后约 5 秒，平台 HTTP 口直接 `CONN_REFUSED`（连接被拒）；已建立的请求 60s 无响应；只有纯 DB 路径（admin reconcile）一度可用。一个"缓存/锁依赖故障"扩散成"全站不可用"。
- **定位**：① `spring.data.redis` 只配了 host/port/db，**没有配超时** → Lettuce 默认命令超时 60s；② Redis 丢失后，调度线程（看护/延迟轮询/扫描）与请求线程**同时阻塞**排队等命令返回；③ 100 个 Tomcat 线程 + accept 队列被占满 → 新连接在 TCP 层就被拒（表象像"端口/网络问题"，实为线程池耗尽）。
- **修复**：显式 `connect-timeout: 1s` + `timeout: 2s`；配合既有降级（缓存 fail-open 直读 DB、限流器 Redis 异常放行、任务锁 Redis 异常"宁可双跑不可停扫"）。
- **防回归**：混沌剧本 `_c21`（Redis 停机）11/11 PASS——断言 health 快速 503、下单 2s 内 500（快速失败而非挂死）、停机期间 DB 路径可用、恢复后 `rebuild-alloc` 回零差异。
- **数字**：60s（默认命令超时）→ 2s；Tomcat 线程 100；恢复后对账 total 回基线 0。
- **出处**：`document/pitfalls/redis-fault-cascade-no-timeout.md`、`scripts/verify/batch19/_c21_out.txt`。
- **可讲的通用教训**：显式超时与熔断同等重要（"无超时"等于把调用方线程池交给下游）；演练验收标准应是"**故障期间系统保持可响应/快速失败**"，而不是"故障恢复后系统恢复"；排障顺序先看线程池是否被阻塞耗尽，再怀疑网络。

## 卡 3 · dev reset 不收敛 → 台账孤占（数据一致性，压测尾轮发现）

- **现象**：写路径压测收尾偶发两组形式不一致的对账差异：`cell-battery-consistency`（cell 引用的电池 `cellId=null`，双向指针未对位）与 `transfer-ledger`（调拨台账与实物分布不一致）。**关键线索：差异条数每次 reset/压测都漂移**（观察到 2 条 → 尾轮实测 16+2；压测脚本内 baseline=8 / after=7）——同一命令不同结果。
- **定位**（中断实验：手工 reset 后差异 **18 → 8**，收敛不完全，三类残留）：
  1. **孤儿电池编号缺失被静默跳过**：`DevResetService` 按公式 `BAT-{柜序×每柜仓数+仓号}` 归位电池，但历史测试柜 `SWAP-T2-224621`（09-13 遗留，编号在 C 系列之后）对应的 `BAT-0121+` **根本不存在** → 代码 `if (battery == null) continue` **静默跳过**，cell 引用永远停在旧编号（3 条始终修不掉）；
  2. **交错引用图无法一次归位**：reset 是"逐仓 detach + 逐仓归位"，但压测并发 TAKE/RETURN 写出了交错引用（如 cell5 的电池应归 cell1，而 cell1 已被别的电池占据）→ 单轮扫描只能修一部分、还会**新产生**差异（cells 1/4/5 共 3 条）；
  3. 调拨台账 2 条为 09-13 历史遗留（与本次无关，但混在总数里掩盖了判断）。
- **修复**：① reset 改**两阶段收敛**——先全量 detach 建立"无引用中间态"，再按公式统一归位（消除交错依赖）；② 孤儿柜 `SWAP-T2-224621` 退役（历史数据清出对账口径）；③ 编号缺失从"静默跳过"改为显式记录（可观测）。
- **防回归**：`batch18` 防回归剧本 `_b18_reset_convergence.ps1`（构造交错引用图 → reset → 逐仓双向核验 + 对账 0 + 幂等重跑）PASS；DevSeeder 的绑定逻辑同步加固（仅在"电池确在仓"时补全绑定，反向自愈解除错绑——避免把用户已取走的电池硬绑回仓）。
- **数字**：对账 total **18 → 0**；单轮 reset 修复 13 条 / 新产生 3 条 / 始终未修 3 条 + 历史 2 条。
- **出处**：`document/pitfalls/dev-reset-nonconvergent-orphans.md`、`document/fixes/dev-reset-two-bugs.md`、`scripts/verify/batch18/`。
- **可讲的通用教训**："同一命令结果漂移"是数据交错依赖的信号，不是随机故障；修复脚本本身也会制造新差异（要看**净收敛**）；`continue` 静默跳过是数据修复类代码的头号敌人。

## 卡 4 · 堆压到 96m：吞吐 -21.5%、GC 暂停 20.8×（性能排障，可复现）

- **现象**：同一读路径负载（100 线程 / 45s 稳态），把堆从 512m 压到 96m：吞吐 **2,987/s → 2,344/s（-21.5%）**、平均延迟 **31ms → 40ms（+29%）**，**错误数仍为 0**。"没有报错就等于没问题"在这里是错的——劣化全在 GC 上。
- **定位**（同机同负载对比，GC log + jstat）：
  | 证据 | 96m | 512m |
  |---|---|---|
  | GC 暂停次数（45s） | **2,040** | 98（20.8×） |
  | GC 暂停总时长 | **3,996.7ms（占 8.9%）** | 277.0ms（占 0.6%）（14.4×） |
  | 最长单次暂停 | 20ms | 9.8ms |
  | jstat 老年代 | **63.4MB / 容量 52.1MB（~82%）**，YGC=85 CGC=30 FGC=0 | 余量充足 |
  → 结论：分配速率高 + 堆小 → 年轻代频繁回收（次数与总时长双升），老年代逼近满但尚未 FGC（再压一档就会出现长暂停）。
- **修复/处置**：容量口径固化（生产堆不按"能跑就行"取值）；把"GC 暂停占比"纳入压测报告必检项（不只看吞吐/错误率）；复现脚本化（同机同负载两档对比，一次跑出上表）。
- **防回归**：`_p03e_jvm_story.ps1` 一键复现两档对比；容量报告模板要求带方法论元数据（拓扑/预热/稳态窗口/堆/限流开关/数据基数）。
- **数字**：-21.5% 吞吐、+29% 延迟、20.8× 暂停次数、14.4× 暂停时长、8.9% vs 0.6% 时间占比；对照读路径正常档 3,230~3,526/s、p99 16~84ms、0 错误。
- **出处**：`document/fixes/jvm-gc-pressure-96m.md`、`scripts/verify/batch17/_p03e_out.txt`、原件 `diag-archive/p03e-jvm-*`。
- **可讲的通用教训**：GC 是"沉默的性能税"——错误率为 0 不代表健康；排障要拿"同机同负载两档对比 + GC log/jstat 双证据"，而不是猜。

## 卡 5 · 管理端密钥从明文到 env-only 收编（安全）

- **现象**：管理端静态 token / 联调 secret 曾以明文形态出现在仓库与运行日志中（S5 安全审查发现，随后做了密钥轮换）；一旦放行公网或分享仓库，等于把管理端 SUPER 权限一起交出去。
- **定位**：密钥来源不受控——配置文件里可直接写死、启动脚本里可见、日志会打印头部/参数；而静态 token 的权限极高（命中即映射 SUPER 全权限，审计用户名 `bootstrap`）。
- **修复**：① 全部密钥改 **env-only 注入**（`SWAP_ADMIN_TOKEN` / `SWAP_DEV_SECRET` / `SWAP_PAY_SECRET` / webhook secret），仓库零明文；② **未配置即启动失败**（fail-fast，不允许空密钥放行）；③ 本地密钥落 `.local/*.txt`（gitignored），临时密钥文件用后即删；④ 静态 token 收编进统一过滤器与权限码体系（不是绕过后门）：`AdminAuthFilter` 双轨合并（会话 token / 静态 token / 账号）→ `AdminContext` + `SecurityContext`，请求末尾统一清理防串号；⑤ 使用可追溯：token 身份的操作审计记 `username=bootstrap`，审计查询 `GET /admin/account/op-log` 仅 SUPER/bootstrap 可见。
- **防回归**：会话侧 BCrypt + 32hex 随机 token 存 Redis（TTL 12h，logout 删除）+ 登录 IP 限流 5/5s；`AdminSecurityConfig` 用 `securityMatcher("/admin/**")` 独立链（设备端/用户端/联调端路径不受影响）；工作区红线"密钥零明文（代码/文档/提交/聊天/记忆皆然）"。
- **数字**：会话 token 32hex、TTL 12h、登录限流 5 次/5s；权限码格式 `admin:{域}:{动作}`；角色 4 类（SUPER/OPS/FINANCE/SUPPORT）。
- **出处**：`document/knowledge/rbac-and-audit.md`、`document/knowledge/runbook.md` §4.5、roadmap P0-4 风险段（"secret 泄露教训在案：S5 修复 + 密钥轮换"）。
- **可讲的通用教训**：应急通道（break-glass）必须"收编"而不是"绕过"——同样过权限码、同样留审计、同样能轮换；fail-fast 比"空值放行"安全得多。

## 卡 6 · Micrometer Gauge 弱引用 → 全量偶发 NaN（测试稳定性）

- **现象**：`SwapMetricsTest.指标注册与取值` 偶发 `expected: 3.0 but was: NaN`；单独跑 20 次全绿、CI 也绿，只在**全量 356 个测试**跑时出现，且位置固定在 `swap.outbox.backlog`——典型"全局偶发 + 负载相关"flaky。
- **定位**：① Micrometer `Gauge.builder(name, obj, fn)` 对 `obj` 默认持**弱引用**（对象被回收即自动注销 meter）；② 测试里 `new SwapMetrics(registry, ...)` 是局部变量，**没有强引用**（生产环境由 Spring 容器持有，所以线上不会出问题）；③ 全量跑的内存压力触发 GC 回收该实例 → `Gauge.value()` 对空引用**返回 NaN 而不抛异常**（静默坏值）；④ 指标注册后，后续任何测试都可能触发——"沉默的坏值"比抛异常更难查。
- **修复**：双重收口——测试持强引用（把被测对象提升为字段，生命周期覆盖断言）+ 断言前显式校验 meter 存在性（NaN 立即失败并给出可读原因，而不是等值比较失败）。
- **防回归**：全量 `mvn clean test` 连跑验证（不再偶发）；把"弱引用型 API（Gauge/WeakHashMap/软引用缓存）在测试里必须持强引用"写入坑位文档。
- **数字**：356 个测试规模下复现；单跑 20 次 0 复现；修复后批次21 全量 356/356 绿。
- **出处**：`document/pitfalls/micrometer-gauge-weak-ref-flaky.md`。
- **可讲的通用教训**：flaky 的"负载相关性"往往指向 GC/弱引用/时序三类根因；库的"静默降级返回值"（NaN/null/-1）是测试中最难发现的一类失败。
