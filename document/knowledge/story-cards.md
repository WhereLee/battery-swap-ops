## 卡 1 · 押金二次退款（资金安全，红队审查发现）

- **现象**：一条"合法调用序列"能把同一笔押金退两次：TAKE 缴押金 9900 → RETURN 退押金 → 再 TAKE → 管理端 `admin/refund` 又退 9900。资金账不平，但每一步单独看都"成功"。
- **定位**：退款口径与业务口径**双轨并存**——`RefundService.REFUNDABLE_TYPES` 把 `DEPOSIT` 列为可退类型（按 `payment_record` 流水累加可退额），而押金实际退回是由 RETURN 流程的 `WalletService.refundDeposit`（押金转余额 + DEPOSIT_REFUND 流水）完成的。两条路径都"有权"退同一笔钱。附带发现两个弱点：人工退款无订单状态约束（COMPLETED 单也能退）、退款无操作人留痕。
- **修复**：① `REFUNDABLE_TYPES` 移除 `DEPOSIT`——押金退回**只能**由 RETURN 业务路径触发（口径唯一化，注释与文档同时写明）；② `AdminRefundController` 加状态与金额约束：COMPLETED 单拒绝（指向正规重复退款流程）、可退金额为 0 拒绝（0 元退款单会污染对账）；③ 补 `RefundServiceTest`（口径矩阵：押金排除/累计上限）与 `AdminRefundControllerTest`（状态矩阵）。
- **防回归**：对账组 `completed-has-payment` / `settlement-conservation` / `statement-conservation` 守资金守恒；人工退款走 `@AdminLog` 审计（操作人/目标/结果可追）。
- **数字**：押金 9900 分；单次余额计费 300 分；IT-1 实测 RETURN 后押金 9900 → 0 且仅 1 条 DEPOSIT_REFUND 流水。
- **出处**：`document/fixes/deposit-double-refund.md`（S7 WP-0）。
- **可讲的通用教训**：资金类"可退额度"不能由流水表反推，必须由**业务事件**定义；同一笔钱出现两条退款路径＝必然被用出来。

## 卡 2 · Redis 无超时 → 全站瘫痪（混沌演练驱动）

- **现象**：kill Redis 后约 5 秒，平台 HTTP 口直接 `CONN_REFUSED`（连接被拒）；已建立的请求 60s 无响应；只有纯 DB 路径（admin reconcile）一度可用。一个"缓存/锁依赖故障"扩散成"全站不可用"。
- **定位**：① `spring.data.redis` 只配了 host/port/db，**没有配超时** → Lettuce 默认命令超时 60s；② Redis 丢失后，调度线程（看护/延迟轮询/扫描）与请求线程**同时阻塞**排队等命令返回；③ 100 个 Tomcat 线程 + accept 队列被占满 → 新连接在 TCP 层就被拒（表象像"端口/网络问题"，实为线程池耗尽）。
- **修复**：显式 `connect-timeout: 1s` + `timeout: 2s`；配合既有降级（缓存 fail-open 直读 DB、限流器 Redis 异常放行、任务锁 Redis 异常"宁可双跑不可停扫"）。
- **防回归**：混沌剧本 `_c21`（Redis 停机）11/11 PASS——断言 health 快速 503、下单 2s 内 500（快速失败而非挂死）、停机期间 DB 路径可用、恢复后 `rebuild-alloc` 回零差异。
- **数字**：60s（默认命令超时）→ 2s；Tomcat 线程 100；恢复后对账 total 回基线 0。
- **出处**：`document/pitfalls/redis-fault-cascade-no-timeout.md`、`scripts/verify/batch19/_c21_out.txt`。
- **可讲的通用教训**：显式超时与熔断同等重要（"无超时"等于把调用方线程池交给下游）；演练验收标准应是"**故障期间系统保持可响应/快速失败**"，而不是"故障恢复后系统恢复"；排障顺序先看线程池是否被阻塞耗尽，再怀疑网络。

## 卡 3 · dev reset 不收敛 → 台账孤占（数据一致性，压测尾轮发现）

- **现象**：写路径压测收尾偶发两组形式不一致的对账差异：`cell-battery-consistency`（cell 引用的电池 `cellId=null`，双向指针未对位）与 `transfer-ledger`（调拨台账与实物分布不一致）。**关键线索：差异条数每次 reset/压测都漂移**（观察到 2 条 → 尾轮实测 16+2；压测脚本内 baseline=8 / after=7）——同一命令不同结果。
- **定位**（中断实验：手工 reset 后差异 **18 → 8**，收敛不完全，三类残留）：
  1. **孤儿电池编号缺失被静默跳过**：`DevResetService` 按公式 `BAT-{柜序×每柜仓数+仓号}` 归位电池，但历史测试柜 `SWAP-T2-224621`（09-13 遗留，编号在 C 系列之后）对应的 `BAT-0121+` **根本不存在** → 代码 `if (battery == null) continue` **静默跳过**，cell 引用永远停在旧编号（3 条始终修不掉）；
  2. **交错引用图无法一次归位**：reset 是"逐仓 detach + 逐仓归位"，但压测并发 TAKE/RETURN 写出了交错引用（如 cell5 的电池应归 cell1，而 cell1 已被别的电池占据）→ 单轮扫描只能修一部分、还会**新产生**差异（cells 1/4/5 共 3 条）；
  3. 调拨台账 2 条为 09-13 历史遗留（与本次无关，但混在总数里掩盖了判断）。
- **修复**：① reset 改**两阶段收敛**——先全量 detach 建立"无引用中间态"，再按公式统一归位（消除交错依赖）；② 孤儿柜 `SWAP-T2-224621` 退役（历史数据清出对账口径）；③ 编号缺失从"静默跳过"改为显式记录（可观测）。
- **防回归**：`batch18` 防回归剧本 `_b18_reset_convergence.ps1`（构造交错引用图 → reset → 逐仓双向核验 + 对账 0 + 幂等重跑）PASS；DevSeeder 的绑定逻辑同步加固（仅在"电池确在仓"时补全绑定，反向自愈解除错绑——避免把用户已取走的电池硬绑回仓）。
- **数字**：对账 total **18 → 0**；单轮 reset 修复 13 条 / 新产生 3 条 / 始终未修 3 条 + 历史 2 条。
- **出处**：`document/pitfalls/dev-reset-nonconvergent-orphans.md`、`document/fixes/dev-reset-two-bugs.md`、`scripts/verify/batch18/`。
- **可讲的通用教训**："同一命令结果漂移"是数据交错依赖的信号，不是随机故障；修复脚本本身也会制造新差异（要看**净收敛**）；`continue` 静默跳过是数据修复类代码的头号敌人。

## 卡 4 · 堆压到 96m：吞吐 -21.5%、GC 暂停 20.8×（性能排障，可复现）

- **现象**：同一读路径负载（100 线程 / 45s 稳态），把堆从 512m 压到 96m：吞吐 **2,987/s → 2,344/s（-21.5%）**、平均延迟 **31ms → 40ms（+29%）**，**错误数仍为 0**。"没有报错就等于没问题"在这里是错的——劣化全在 GC 上。
- **定位**（同机同负载对比，GC log + jstat）：
  | 证据 | 96m | 512m |
  |---|---|---|
  | GC 暂停次数（45s） | **2,040** | 98（20.8×） |
  | GC 暂停总时长 | **3,996.7ms（占 8.9%）** | 277.0ms（占 0.6%）（14.4×） |
  | 最长单次暂停 | 20ms | 9.8ms |
  | jstat 老年代 | **63.4MB / 容量 52.1MB（~82%）**，YGC=85 CGC=30 FGC=0 | 余量充足 |
  → 结论：分配速率高 + 堆小 → 年轻代频繁回收（次数与总时长双升），老年代逼近满但尚未 FGC（再压一档就会出现长暂停）。
- **修复/处置**：容量口径固化（生产堆不按"能跑就行"取值）；把"GC 暂停占比"纳入压测报告必检项（不只看吞吐/错误率）；复现脚本化（同机同负载两档对比，一次跑出上表）。
- **防回归**：`_p03e_jvm_story.ps1` 一键复现两档对比；容量报告模板要求带方法论元数据（拓扑/预热/稳态窗口/堆/限流开关/数据基数）。
- **数字**：-21.5% 吞吐、+29% 延迟、20.8× 暂停次数、14.4× 暂停时长、8.9% vs 0.6% 时间占比；对照读路径正常档 3,230~3,526/s、p99 16~84ms、0 错误。
- **出处**：`document/fixes/jvm-gc-pressure-96m.md`、`scripts/verify/batch17/_p03e_out.txt`、原件 `diag-archive/p03e-jvm-*`。
- **可讲的通用教训**：GC 是"沉默的性能税"——错误率为 0 不代表健康；排障要拿"同机同负载两档对比 + GC log/jstat 双证据"，而不是猜。

## 卡 5 · 管理端密钥从明文到 env-only 收编（安全）

- **现象**：管理端静态 token / 联调 secret 曾以明文形态出现在仓库与运行日志中（S5 安全审查发现，随后做了密钥轮换）；一旦放行公网或分享仓库，等于把管理端 SUPER 权限一起交出去。
- **定位**：密钥来源不受控——配置文件里可直接写死、启动脚本里可见、日志会打印头部/参数；而静态 token 的权限极高（命中即映射 SUPER 全权限，审计用户名 `bootstrap`）。
- **修复**：① 全部密钥改 **env-only 注入**（`SWAP_ADMIN_TOKEN` / `SWAP_DEV_SECRET` / `SWAP_PAY_SECRET` / webhook secret），仓库零明文；② **未配置即启动失败**（fail-fast，不允许空密钥放行）；③ 本地密钥落 `.local/*.txt`（gitignored），临时密钥文件用后即删；④ 静态 token 收编进统一过滤器与权限码体系（不是绕过后门）：`AdminAuthFilter` 双轨合并（会话 token / 静态 token / 账号）→ `AdminContext` + `SecurityContext`，请求末尾统一清理防串号；⑤ 使用可追溯：token 身份的操作审计记 `username=bootstrap`，审计查询 `GET /admin/account/op-log` 仅 SUPER/bootstrap 可见。
- **防回归**：会话侧 BCrypt + 32hex 随机 token 存 Redis（TTL 12h，logout 删除）+ 登录 IP 限流 5/5s；`AdminSecurityConfig` 用 `securityMatcher("/admin/**")` 独立链（设备端/用户端/联调端路径不受影响）；工作区红线"密钥零明文（代码/文档/提交/聊天/记忆皆然）"。
- **数字**：会话 token 32hex、TTL 12h、登录限流 5 次/5s；权限码格式 `admin:{域}:{动作}`；角色 4 类（SUPER/OPS/FINANCE/SUPPORT）。
- **出处**：`document/knowledge/rbac-and-audit.md`、`document/knowledge/runbook.md` §4.5、roadmap P0-4 风险段（"secret 泄露教训在案：S5 修复 + 密钥轮换"）。
- **可讲的通用教训**：应急通道（break-glass）必须"收编"而不是"绕过"——同样过权限码、同样留审计、同样能轮换；fail-fast 比"空值放行"安全得多。

## 卡 6 · Micrometer Gauge 弱引用 → 全量偶发 NaN（测试稳定性）

- **现象**：`SwapMetricsTest.指标注册与取值` 偶发 `expected: 3.0 but was: NaN`；单独跑 20 次全绿、CI 也绿，只在**全量 356 个测试**跑时出现，且位置固定在 `swap.outbox.backlog`——典型"全局偶发 + 负载相关"flaky。
- **定位**：① Micrometer `Gauge.builder(name, obj, fn)` 对 `obj` 默认持**弱引用**（对象被回收即自动注销 meter）；② 测试里 `new SwapMetrics(registry, ...)` 是局部变量，**没有强引用**（生产环境由 Spring 容器持有，所以线上不会出问题）；③ 全量跑的内存压力触发 GC 回收该实例 → `Gauge.value()` 对空引用**返回 NaN 而不抛异常**（静默坏值）；④ 指标注册后，后续任何测试都可能触发——"沉默的坏值"比抛异常更难查。
- **修复**：双重收口——测试持强引用（把被测对象提升为字段，生命周期覆盖断言）+ 断言前显式校验 meter 存在性（NaN 立即失败并给出可读原因，而不是等值比较失败）。
- **防回归**：全量 `mvn clean test` 连跑验证（不再偶发）；把"弱引用型 API（Gauge/WeakHashMap/软引用缓存）在测试里必须持强引用"写入坑位文档。
- **数字**：356 个测试规模下复现；单跑 20 次 0 复现；修复后批次21 全量 356/356 绿。
- **出处**：`document/pitfalls/micrometer-gauge-weak-ref-flaky.md`。
- **可讲的通用教训**：flaky 的"负载相关性"往往指向 GC/弱引用/时序三类根因；库的"静默降级返回值"（NaN/null/-1）是测试中最难发现的一类失败。

## 卡 7 · `@Transactional` 自调用失效 → 退款可双记（资金安全，独立审计发现）

- **现象**：一张退款单可能向用户钱包入账**两次**；而且事后从数据上看"一切正常"——退款单是 `SUCCESS`、`refundableAmount()` 按退款单扣减认为已退、对账不变量也全过。触发条件很朴素：**入余额已提交、状态 CAS 之前任何一步失败**（进程被杀、`payment_record` 写入遇死锁 1213、连接抖动）。单线程即可复现，不需要并发。
- **定位**：`refund()` → 私有 `doRefund()` → `this.apply(record)`——**同类自调用不经过 Spring 代理**，`apply` 上的 `@Transactional` 静默失效。于是"资金动作（入余额 + 记流水）+ 状态 CAS"根本不是原子的：加款先自动提交、CAS 后做；CAS 失败抛出的异常被 `catch` 成"延迟重投"，10 秒后重投**再次加款** → 双记。**关键不对称证据**：同一个 `apply` 还有第二条入口（延迟重投处理器）走代理、带事务——两条入口事务语义不一致，本身就说明"apply 必须有事务"是设计意图，只是在线路径没兑现。
- **为什么四层防线全没抓到**：单测全 Mock（看不见代理）；SpotBugs 不建模代理语义；覆盖率里那几行**确实被执行过**（只看跑没跑到）；剧本都跑在成功路径上。**只有故障注入才能让它显形。**
- **修复**：事务改为编程式（`TransactionTemplate` + 注入 `PlatformTransactionManager`）——对"谁来调"不敏感，两条入口语义一致；事务内只留资金三步（入余额 → 记流水 → CAS），站内信与分账冲正移出事务各自 best-effort（与 S7 "写失败不影响退款"的声明一致）；顺带修掉同源的 P1——命中既有 `WAIT` 单时**不再直接返回**而是重驱动（旧实现让失败单永久悬空：用户拿不到钱，而可退额已把它算作已退）。
- **防回归（三层 + 可红性）**：① 单测 4 例（成功→提交 / CAS 冲突→回滚且留 WAIT / WAIT 可重驱动 / SUCCESS 幂等不入账）；② **字节码级守卫** `TransactionalSelfInvocationGuardTest`——ASM 扫描全仓"非事务方法自调用 `@Transactional` 方法"（含内部类↔外层类），带探针自检与扫描规模下限，规则刻意收窄（事务方法调事务方法不报：`ChannelReconService#importBill→reconcile` 属良性）；③ CI 内的**故障注入 IT** `RefundAtomicityIT`——真 MySQL 事务 + 真钱包，在加款之后注入失败，断言**余额一分未动**，移除故障重驱动后恰好入账一次；④ **门禁可红性实证**：把 `@Transactional` 加回被自调用的方法 → 守卫 BUILD FAILURE，还原 → BUILD SUCCESS。
- **数字**：swap-server 单测 430 → 436（本批 server 侧 +6）；守卫扫描规模下限 ≥10 个含事务方法的类 / ≥20 个事务方法（防止目录定位失败导致空转）。
- **出处**：`document/pitfalls/tx-self-invocation-refund-double-credit.md`、`document/block-records/批次32-退款事务边界与自调用守卫.md`、`scripts/verify/batch32/_g32_out.txt`、`swap-server/src/test/.../it/RefundAtomicityIT.java`。
- **可讲的通用教训**：① **"注解在不在"不等于"机制在不在"**——凡靠代理生效的注解（`@Transactional`/`@Cacheable`/`@Async`/方法级 `@Valid`/同类 `@PreAuthorize`）自调用一律静默失效；② **资金动作与状态闸门必须同一事务**：顺序上"先 CAS 再动钱"与"同事务内先动钱再 CAS"都成立，唯独"先动钱自动提交、再 CAS"不成立——它把闸门放在了钱后面；③ 有中间态就必须回答"谁来把它推走"；④ 这类缺陷值得加**结构性门禁**，而不是加一条用例——用例只能守住你想得到的那个形状。

## 卡 8 · 数据穿过来了但屏幕上没有：SOC 数字从不显示（读组件源码定位）

- **现象**：换电柜详情页"仓位与电池"表的 SOC 列，6 个占用仓位**一个数字都不显示**——只有一条绿色进度条和一个对勾图标；6 个空闲仓位显示 `-`。接口是对的：`/admin/view/cabinet/SWAP-C-001` 对那 6 个仓位明确返回 `soc: 100`。
- **定位**：不是后端、不是绑定、不是权限。探针把该列的 DOM 量出来是"12 行可见为空、**DOM 文本 0 个字符**、子元素 10 个"——**有 10 个子元素却没有一个字**，说明渲染出来的东西是图形而不是文字。回读 `element-plus` 的 progress 组件源码：它导入了 `CircleCheck / CircleClose / WarningFilled`，并有 `STATUS_COLOR_MAP`——**一旦设了 `status` 属性，组件就用状态图标替换百分比文字**。而我们写的是 `:status="row.soc >= 90 ? 'success' : undefined"`，于是 6 行数据都成了"绿条 + 对勾"，数字被组件主动丢掉了。
- **修复**：把 `:status`（换图标）改成 `:color`（只换颜色），数字保留；颜色沿用同一套可达标色板（≥90 深绿、≥60 深琥珀、其余深红）。
- **防回归**：探针新增"整列是否渲染可见文字"的事实项，并且**同时取 `innerText` 与 `textContent`**——`innerText` 是浏览器真正排版出来的文字，`textContent` 是 DOM 里存在的文字。两者不一致恰恰就是"绑定了值但看不见"（CSS 隐藏、被替换、宽度塌陷），只有前者能抓住这类缺陷。

## 卡 9 · 门禁自己坏了，伪装成应用故障（测试可信度）

- **现象**：收口时按计划重跑浏览器剧本，一次出现 **PASS=16 / FAIL=9**，文档基线却写着 31/31。9 条失败里既有"点进详情没渲染"又有"路由守卫没跳转"——看起来像整个应用坏了；但截图只有 29–32 kB（列表页 92–129 kB），**页面根本还没导航过去**。
- **定位**（三个独立成因，同一症状）：① 抽出公共 CDP 客户端后 `waitFor(expression, timeoutMs)` 被按老签名传入**标签字符串**，`Date.now() + "work-order detail"` = `NaN` ⇒ `while (Date.now() < NaN)` 一次都不循环 ⇒ **9 项检查在 0ms 内全红**，且 FAIL 行不带任何诊断；② 同一次重构把 **6 条 `B goto <path> renders` 导航检查**一起删了（覆盖从 31 项掉到 25 项），而所有文档仍在写 31；③ 证据文件 `_c35_out.txt` 是当时**人工 tee 的一次性产物**，包装脚本只负责打印——所以"文件写 31、脚本只跑 25"这件事**没有任何命令能发现**。
- **修复**：① `waitFor` 对非法超时**直接抛错**（`must be a positive finite number`）——**错误类型不得伪装成断言失败**；② 恢复 6 条导航检查并改用显式 `(expression, label, timeoutMs)` 签名（标签只用于日志），25+6=31；③ 三个剧本改为**运行时自写证据**（`_c34` 用 `Emit`/`Save-Evidence`，`_c35`/`_c38` 由包装器落盘 UTF-8 无 BOM），从此"记录"与"产生记录的命令"不可能脱节。
- **防回归**：现在 `Select-String '^\s*check\(' 剧本` 的数量与 `_out.txt` 里的 PASS 数必须相符；`_c35` 包装器同时打印每张截图的**真实捕获尺寸**（下一条卡即由此发现）。
- **数字**：25 → 31 项检查；9 条 0ms 假失败 → 31/31 PASS；三个剧本全部自写证据。
- **出处**：`document/pitfalls/check-coverage-lost-in-refactor.md`、`document/roadmap/独立审计发现与处置.md` AUD-10、`scripts/verify/batch31/_c35_out.txt`。
- **可讲的通用教训**：① **断言辅助函数的参数类型必须校验**，尤其是"可选的第二个参数"；② 重构跨文件抽公共代码时**先数 check 数量**，改完再数一次；③ **有证据文件不等于跑过**——判据是"这条命令能不能重新生成它"；④ 门禁自己的失败也要能被区分出来，否则一次工具故障会被误读成九处业务缺陷。

## 卡 10 · 修完标签宣布收口，扩面后才发现病根是设计令牌（对比度，症状 vs 病根）

- **现象**：视觉复核把管理台的状态标签描述成"渲染成空白方块"。实测确认是真缺陷：Element Plus 默认浅色 tag 把**语义基色当文字**压在浅底上——success `#67c23a`/`#f0f9eb` = **2.08:1**、warning **2.04:1**、danger 2.61:1、info 2.80:1，dark 效果白字压基色 **3.08:1**；而标签字号 12px 属 WCAG 的"正常字号"，门槛是 **4.5:1**。

- **扩面（把自己声明的边界补上）**：把探针从"按固定选择器列表测"改成**遍历所有持有自身文本的可见叶子元素**，并按 WCAG 1.4.3 分级（默认 4.5:1，只有 ≥24px 或 ≥18.66px 加粗才允许 3:1；显式豁免 disabled 与 aria-hidden）。结果 10 条路由上**每页 7–12 处不达标、且重复同一批选择器**——失败根本不是标签特有的：
  - `--el-text-color-secondary` `#909399` = 2.87:1 / 3.08:1 → 副标题、`共 N 条`、提示语、时间线时间戳、**表格表头**、空态文案、`.text-muted`：**整个次要文字层**；

  - `--el-color-warning` 作文字 2.19:1；侧边栏自绘 `#5c6b7f` 在深底上 **2.57:1**（深底要**调亮**，方向与浅底相反）。
- **修复（令牌级，不逐组件打补丁）**：`secondary → #5d6269`、`primary → #1668c1`（相对亮度 ≤0.1833 让"文字压白底"与"白字压它"**同时** ≥4.5:1，实测双向 5.07:1）；`primary-light-3..9 / dark-2` 按 Element Plus 自己的公式重算（用 `light-9 = #ecf5ff` 反推验证过公式），否则会出现"新主色 + 旧浅色族"的脏配色；hover/active 单独压深（默认 hover 用 light-3，白字压上去只有 3.13:1）；语义按钮同样压深但**作用域限定在按钮**（语义色同时是图表填充色，全局改会改变图形语义）；自绘样式不再硬编码颜色，改引用令牌。
- **防回归**：`_c38` 新增硬门禁 `every text element reaches its WCAG threshold`——**1936 个文字元素 + 270 个标签、10 条路由、0 个不达标**。
- **数字**：标签 2.04–3.08:1 → 6.00–8.57:1；文字元素 7–12 处/页 → **0**；扫描规模 1936 个元素、单页最多 541（上限 800 未触顶）。
- **出处**：`document/pitfalls/tag-contrast-element-plus-default.md`、`document/block-records/批次39-设计令牌对比度收口.md`、`document/roadmap/独立审计发现与处置.md` AUD-8/AUD-11、`scripts/verify/batch31/_c38_report.json`。
- **可讲的通用教训**：① **测一个组件不代表整个组件库**——修完要问"还有谁在用同一套令牌"，否则就是把症状当病根；② 门禁的**覆盖面本身就是结论的一部分**，"我测了什么"必须和"我宣布了什么"对齐；③ 阈值取**标准值**（4.5:1）而不是"看起来还行"（3:1 会放过 2.8:1 的灰字）；④ 修对比度要**保色相**（用户靠颜色识别状态），只压深度；⑤ 主动把"未覆盖的部分"写进文档，是下一轮能补上的前提。

## 卡 11 · 自己的迁移把读路径删掉了：靠服务器统计而非读代码发现（数据库/索引）

- **现象**：所有门禁全绿（单测 520、契约 59、浏览器 31、覆盖率、SpotBugs），但订单详情那条
  `SELECT ... FROM payment_record WHERE order_id = ?` 每次都在**全表扫描**。查得慢、结果对，
  没有任何断言会红——这类缺陷能穿过全部四层防线。
- **怎么发现的（关键在不靠读代码猜）**：问 MySQL 自己。`performance_schema.events_statements_summary_by_digest`
  逐语句记录了"执行次数 / 是否用到索引 / 扫了多少行"：
  **54,647 次执行中 5,068 次 `SUM_NO_INDEX_USED`，累计扫 40,641,477 行，只返回 6,629 行**
  ⇒ 每次全表扫 ~8,090 行换 1 行（表 7,875 行）。`EXPLAIN` 复核：`type=ALL possible_keys=NULL rows=7875`。
- **根因（本仓库自己造成的）**：批次35 为修"同一订单第二笔部分退款台账漏记"（AUD-6），
  把 `uk_order_type(order_id, payment_type)` 换成了生成列唯一键 `uk_payment_idem(idem_key)`。
  那个唯一键当时担了**两个职责**：①资金动作幂等闸（唯一性）②`WHERE order_id = ?` 的**唯一**访问路径（可访问性）。
  改 ① 的时候 ② 被一起删掉了。**旁证**：同形状但走索引的另一支 digest `LAST_SEEN = 2026-09-17 10:26`，
  此后只有全表扫那一支在跑——访问路径消失的时间线看得见。
- **修复**：`db/19` 补 `idx_order_id(order_id)`，**刻意非唯一**——退款多笔语义已由
  `refund_record(order_id, reason)` 与 `uk_trade_no` 保证，幂等闸已收窄到 `uk_payment_idem`；
  重建唯一键等于把 AUD-6 退回来（"恢复访问路径"与"恢复唯一约束"是两件事，只做前者）。
  同批审计还修了两处：`alarm` 缺 `create_time` 前导索引导致管理台"全部"页签
  （`handled=undefined` 使过滤条件消失）全表 + filesort；`swap_order` 缺 `(status, complete_time)`。
- **防回归（三层，含因果证明）**：新增门禁 `_c39_index_audit.ps1`（14/14 PASS）——
  ①审计清单（按表大小与每次扫描行数分 `REAL-GAP`/`benign`/`unclassified`，"看不出"与"没问题"分开报）；
  ②`EXPLAIN` 断言 + **索引前导列存在性**的 schema 断言（正是本次缺陷的形状，不依赖优化器当下选择）；
  ③**因果证明**：读计数器 → 打真实 HTTP 流量 → 再读，断言"执行数涨、无索引次数不涨、每次扫行数塌到约等于返回行数"。
- **数字**：payment_record **8,090 → 1 行/次**；alarm"全部"页签 **4,032 → 20 行/次**（=LIMIT 行数）；
  两次测量均 `no_index_used +0`。门禁全程只读（不 truncate performance_schema、不改服务器变量）。
- **出处**：`document/pitfalls/dropped-index-also-served-read-path.md`、
  `document/block-records/批次40-索引访问路径审计.md`、`document/roadmap/独立审计发现与处置.md` AUD-12、
  `scripts/verify/batch40/_c39_out.txt`、`db/19-index-audit-fixes.sql`。
- **可讲的通用教训**：① **唯一键兼职访问路径时，删它之前先查"谁在读这条路径"**——
  `WHERE <唯一键首列> = ?` 是最容易被忽略的一类查询；② **"我的索引清单"与"我实际跑的查询"要双向验证**：
  前者回答"为什么有这个索引"，后者回答"这条查询有没有索引"，是两个不同的问题；
  ③ **计数器是累计值，不能直接当判据**——要"读 → 打流量 → 再读"取差值，才叫证明修复生效；
  ④ **小表全扫是正常设计**（10 行的柜表、61 行的电池表），审计必须按表大小过滤噪音，
  否则会为了"清零指标"给每张表都加索引；⑤ 修复的价值一半在 `ALTER TABLE`，一半在证据。

## 卡 12 · 我怎么知道我的门禁不是摆设（negative control）

- **动机**：项目 56 个剧本、多道硬门禁**几乎只被观察到绿色**。而"从没红过的门禁"是关于作者乐观程度的陈述，
  不是关于系统的陈述——仓库自己吃过一次亏：`_c35_out.txt` 写 31/31 而同批脚本只跑 25 项检查（重构静默删了 6 条导航检查）。
  于是给新门禁补"**可红性实证**"。
- **做法**：同一页面**先测干净基线**（判据必须为假）→ 注入一类缺陷 → 判据必须为真 → 移除后必须**重新测得干净**
  （证明探针是"对注入反应"，不是"脏了就粘住"）。四类注入：标签对比度、单元格裁切、页面横向溢出、表头错列。
  索引侧同理：`DROP INDEX idx_order_id`（复现缺陷形状）→ 审计必须红 → 重放 `db/19`（幂等，放在 `finally`）→ 必须绿。
- **关键纪律**：负控**必须用门禁自己的判据代码**（`import { probeExpression }`，不复制不重写；为此把探针改成可导入）。
  否则"负控通过"只证明**另一份代码**能发现问题——那从来不是疑问所在。
- **负控立刻抓到的门禁盲区（最有价值的部分）**：表头错列**首跑没红**。我注入的是 `th .cell{transform:translateX(30px)}`，
  而检查比较 `th`/`td` 的 `getBoundingClientRect()`——**子元素上的 transform 不会移动父元素的盒子**，
  于是"表头文字被画到别人列上"完全躲过检查。而这项检查的由来正是视觉模型两次抱怨"表头整体错位"：
  它当时能证明"盒子没错位"，却证明不了"文字没跑到别处"。
- **修法（两处缺一不可）**：① 判据加强——逐列同时比较**外层盒**（`th` vs `td`）与**内层 `.cell` 盒**（新增 `deltaCellLeft`）；
  ② 注入改成布局级（`th{transform}`），因为原注入形态在真实页面里并不存在，负控要复现的是**真实缺陷形状**。
- **回测假阳性**（不能省）：判据加强后真实页面仍 `0 misaligned`（89 列 `deltaLeft=0 / deltaCellLeft=0`），门禁 `PASS`。
  **"为了让它能红"很容易只是把它变敏感**。
- **数字**：`_c40` 10/10（注入后 70 个标签低于 4.5:1、最差 **1.05:1**；20 个裁切；溢出 `true`；11 列错位）；
  `_c41` 9/9（红：`type=ALL key=NULL rows=7875` + 6 条 FAIL，**与批次40 记录的缺陷签名完全一致**；绿：`GATE-INDEX PASS`）。
- **出处**：`document/block-records/批次43-门禁可红性实证.md`、`scripts/verify/batch31/_c40_out.txt`、`scripts/verify/batch40/_c41_out.txt`。
- **可讲的通用教训**：① **没红过的断言不算断言**，尤其"沉默型"缺陷（结果正确、只是慢/只是看不清）的守卫；
  ② 负控要用**被测系统自己的判据**；③ 负控能反过来发现**判据本身的盲区**（本例是 `getBoundingClientRect` 与 CSS transform 的语义差异），
  写正向用例永远发现不了；④ 加强判据后**必须回测假阳性**；⑤ 危险操作放进 `finally` 还原，让中断也不留下破坏状态。
- **同批续（负控 12/12 → 21/21）**：给两条新增检查补了负控并各自当场变红——C6 把 Element Plus 原色
  `#e6a23c` 还原到 warning 浅底 → 变体矩阵报 **1/10 最差 2.04:1**；C7 把 `#f56c6c` 还原到表单校验红字 →
  **1/8 最差 2.9:1**。两条负控都需要**未登录**的登录表单（守卫会把已登录会话的 `/login` 弹回 `/dashboard`），
  于是在一次性 profile 里删掉 token key（服务器看不到任何登出），跑完再登回来——**构造状态的手段本身也要交代清楚**。

## 卡 13 · "没跑到"和"没问题"在报告里长得一模一样（覆盖漏洞）

- **动机**：门禁报"0 个问题"时，必须先能回答"你到底看了什么"。批次41/43 申报过两处盲区，
  本批逐个关掉——**每关一个就当场抓到一个真缺陷**，说明它们不是理论风险。
- **三个真实例子**：
  1. **SKIP 是覆盖漏洞最好的伪装**：`_c38` 弹窗轮长期稳定输出 `2 measured, 2 skipped`，
     理由统一写"opener absent（`allowedActions` 决定，可能没数据）"。但"驳回建议单"的入口按钮在
     **建议单页签**下，而 `/alarm` 默认停在**告警页签**——那不是数据条件，是**少点了一次**。
     给弹窗加 `preStep`（先点页签）后，驳回弹窗立刻进入测量面，并报出输入计数器 `"0 / 200"` **3.08:1**。
     现在 SKIP 分两种原因（"opener 确实不在" vs "preStep 跑不动"），**不能互相冒充**。
  2. **只有让表单失败才看得见的一层文字**：`.el-form-item__error`（Element Plus 用 `--el-color-danger`
     `#f56c6c` = **2.90:1**）只在规则失败时存在，扫 1936 个已渲染元素永远碰不到它。做法：登录表单**空提交**
     （`onSubmit()` 会 `await validate()`，失败即 return），并断言**零请求**——用 CDP 数 `/admin/auth/login`
     的请求数，实测 `0 login POSTs during the empty submit`。即"我测的是一个安全状态"是**证据**，不是承诺。
     首跑抓到两处：校验红字 2.90:1、**登录页提示条文案 2.80:1**（`.el-alert--info.is-light{color:var(--el-color-info)}`
     ——批次38 标签那种"基色当文字色"的写法，在**第三个组件**上重现）。
  3. **只为登录页那一个变体验证过的修复，是靠运气验证的**：`el-alert` 有 5 类 × 明/暗两种效果，
     而应用里三个告警全是条件渲染（看板要 STATION 数据范围、订单要退款提示）。于是把登录页那个**真实告警克隆 10 份**
     （变体名写进标题文本，失败会自己报名）挂到一次性宿主，**用门禁自己的 `probeExpression` 测量**：
     `10 variants, 10 measured, 0 below (worst 6:1 "success/light")`。
- **让"零"带上置信区间**：新增 `worstText`（本次测量中比值最低的那个文字元素），页面级/校验态/变体矩阵各报一次，
  汇总再报**全轮最紧一处**——实测 `4.7:1 (needs 4.5) "::placeholder \"订单号（模糊）\""`。
  口径与批次43 的 `scopeElements` 一致：**知道看了什么、最紧到什么程度，"零问题"才有意义**。
- **数字**：`_c38` 10 页 + **2** 弹窗 + 校验态 + 10 告警变体，`hardFailures=0`（文字元素 1936+9+7+8+10≈1970、标签 270、
  全轮最紧 4.70:1）；`_c40` 21/21；`_c35` 31/31。
- **出处**：`document/block-records/批次43-门禁可红性实证.md` §八、`scripts/verify/batch31/_c38_out.txt`。
- **可讲的通用教训**：① 覆盖率不是"脚本跑了多久"，而是"**哪些状态被真正构造出来过**"；
  ② SKIP/跳过必须有**可区分的原因**，否则它会把漏洞伪装成数据条件；③ 错误态、超限态、禁用态这类
  "**瞬时/条件状态**"必须主动构造才能测；④ 报告里除了"发现几个问题"，还必须有"看了多少、最紧多少"。

## 卡 14 · 看着改好了、其实没生效：CSS 特异性与部署指纹（两次"静默成功"）

- **现象**：门禁报输入计数器 `"0 / 200"` 3.08:1（Element Plus 用 `--el-color-info` `#909399` 画它）。
  于是按惯例写覆盖：`.el-input__count { color: var(--el-text-color-secondary) }`——**构建通过、产物里搜得到这行、
  位置也确实在厂商 CSS 之后**，重新跑门禁：**仍然 3.08:1**。
- **原因**：Element Plus 的规则是 `.el-input .el-input__count`（特异性 **(0,2,0)**），我的是 **(0,1,0)**——
  **特异性优先于顺序**，写在后面完全救不了。产物自证（字节偏移可复现）：我方规则 byte 361996、厂商 byte 180439，
  顺序没问题、权重不够。**没有报错、没有告警**。
- **修法与验收**：选择器对齐 EP 权重（`.el-input .el-input__count` / `.el-textarea .el-input__count`）；
  超限态 `.is-exceed` 保留"危险色"语义但换成站点红 `#8f2b2b`，选择器**照抄 EP 的 (0,4,0) 形状**，否则会被自己的修复反杀。
  **验收标准是门禁的测量值变了，不是文件内容看着对**——这条差别就是"改样式"这件事的全部风险。
- **同一批的第二次"静默成功"在部署侧**："200 OK"区分不了新旧包。批次42 是**人工**比三重指纹
  （资产同名/令牌值/覆盖顺序）；批次43 把它固化成**部署脚本的硬断言**：`deploy-web.ps1` 把本地构建 css 的
  **md5 传给远端** `rollout-web.sh`，**先验后发**（staging md5 不匹配就在快照/迁移/换 jar/重启**之前**退出，
  一个字节都不动），发布后再校验"线上字节 == staging 字节"且"`index.html` 确实引用该资产"
  （防"200 的 HTML + 404 的 bundle"）。实测三方一致：`index-DS8f1Y5V.css` md5 `c82cc305f20a54dc376bc308a86c9c97`。
- **给部署断言也做负控**：传错误 md5 → 拒绝（exit 1），且**三个不变量都没变**：线上 CSS 字节、服务启动时间（没被重启）、
  库 schema（迁移没跑）。首版负控"通过"得毫无意义——当时 staging 已被上次部署清掉，脚本以 `127 not found` 退出，
  **失败原因不是断言**；重做时把 staging 真实重建，并额外断言"拒绝原因那一行"必须出现。
- **出处**：`document/pitfalls/css-override-loses-to-element-plus-specificity.md`、`document/block-records/批次43-门禁可红性实证.md` §8.3/§九、
  `scripts/cloud/rollout-web.sh`、`scripts/cloud/deploy-web.ps1`。
- **可讲的通用教训**：① 覆盖第三方组件样式前先确认**谁赢了级联**（看 Computed/产物，不靠"我写在后面"）；
  ② **静默失效**（语法正确、位置正确、就是不生效）只有测量能发现；③ 部署验证要验**身份**（字节/哈希），
  "服务活着 + 200"只证明有东西在响应；④ 新断言同样要有能红的记录，而且"能红"要细到**拒绝发生在改动之前**。
