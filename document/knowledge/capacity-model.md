# 容量模型与业务量级换算（P0-3c）

> 目的：把"3,5xx QPS"换算成"对应什么业务规模、余量多少"。
> **假设口径**：行业锚点暂缺公开权威数字的部分，一律标注"自设"；有实测的标注来源。
> 证据：`scripts/verify/batch16/_p03_out.txt`（读路径方法论复测）+ `batch7/_load_out.txt`（旧冒烟，已标注被取代）。

## 1. 业务假设（自设，待业务方校准）

| 参数 | 取值 | 口径 |
|---|---|---|
| 城市/站点规模 | 12 站（规划 10~15，取中） | 自设（阶段计划） |
| 每站柜数 | 10 柜 | 自设（与 DevSeeder/压测一致） |
| 每柜仓数 / 满电保有 | 12 仓 / 6 满电 | 实测（种子结构） |
| 单柜日均换电次数 | 200 次/柜/日 | **自设**（骑手高频场景的乐观档；需按实际运营数据校准） |
| 峰时集中系数 | 18% 日单量集中在峰值 1 小时 | 自设（早晚双峰，保守） |

## 2. 换算

- 全网日均单量 = 12 站 × 10 柜 × 200 = **24,000 单/日**（约 0.28 单/s 均值）
- 峰时下单 QPS = 24,000 × 18% ÷ 3600 ≈ **1.2 单/s**
- 每单伴随客户端读请求（站点/库存列表、钱包、订单轮询、券/消息等）保守取 8 次
  → 峰值读 QPS ≈ **10 次/s**

## 3. 与实测容量对照（读路径，2026-09-16）

| 档位 | 吞吐 | p95 / p99 | 错误 |
|---|---|---|---|
| 20 线程 | 3,230.3/s | 15ms / 16ms | 0 |
| 50 线程 | 3,305.7/s | 41ms / 48ms | 0 |
| 100 线程 | 3,525.4/s | 78ms / 84ms | 0 |

- 条件：JDK17 / 512m 定堆 / 限流关 / JMeter+平台+MySQL+Redis 同机（保守口径）；
  预热 75s + 每档 195s 稳态（含 15s ramp）；登录每线程一次（稳态只算读接口）。
- **结论**：本业务量级（峰时 ~10 读 QPS）对当前实现余量 **>300 倍**；20 线程即近饱和
  （3,230/s），50→100 线程吞吐不再增长、延迟上升 → 饱和点约 3.3k~3.5k QPS（同机口径）。
- 瓶颈线索（供深聊）：`/user/stations` 延迟随并发上升最明显（13→70ms）；
  Redis 命令量高（token 校验 + 看护/延迟任务轮询）；MySQL 连接池 20 见顶（Threads_connected≈21）。

## 4. 旧数字更正

- `batch7` 的 **465.5/s** 系压测端假象：JMeter 未开 keep-alive + 每轮登录导致客户端
  ephemeral 端口耗尽（`BindException: Address already in use`），并非服务端容量。
- 修正方式：keep-alive + 每线程登录一次 + 稳态窗口，见 `batch16/jmeter/swap-ops-read.jmx`。
