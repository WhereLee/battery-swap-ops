# 知识：资金终态仲裁（支付回调乱序与"最后一秒"）

> 场景：取消/关单与支付回调、成功与失败回调乱序到达时的唯一裁决规则。
> 代码：`PayOrderService.handleCallback` / `tryAcceptSuccess`（S3.4 初版，S3.8 增补仲裁）。

## 规则（资金优先，网关实收为准）

1. **SUCCESS 是唯一入账权**：`WAIT→SUCCESS` 的 CAS 命中者执行入账；
   并发/重复 SUCCESS 只有一个赢家，其余幂等返回（不双记）。
2. **FAIL 只在 WAIT 生效**：`WAIT→CLOSED`；若当前已 SUCCESS，FAIL 是"伪失败"，忽略不回退。
3. **迟到的 SUCCESS（单据已 CLOSED）必须补记**：`CLOSED→SUCCESS` CAS 再入账——
   钱在网关侧已实收，拒绝入账=用户损失；仍由 CAS 保证只补记一次。
4. **未知/中间态冲突**：拒绝并留 error 日志，交对账人工（不猜测）。
5. 失败回调的重复到达 = 幂等返回 CLOSED，不报错（防网关无限重试）。

## 为什么不用"先到先得"（FAIL 关闭后拒绝 SUCCESS）

- 支付系统的资金事实在**渠道侧**，平台状态只是投影；投影与事实冲突时，事实优先。
- "先到先得"会把晚到的实收资金变成挂账（渠道已扣、平台不认），对账时仍需人工冲正，
  规则更复杂且用户体验差（钱扣了余额不到）。
- 与之相对，**库存/资源**的仲裁是平台侧事实优先（谁先 CAS 谁得），因为资源在平台手里。

## 订单级支付的扩展规则（若未来从"钱包充值"扩展到"下单即扣费"）

- 取消/关单必须先条件检查"是否存在已受理的支付"：`pay_order(order_id, status IN (WAIT,SUCCESS))`；
- 已 SUCCESS → 取消接口拒绝（引导退款）；已 WAIT → 取消需同步关闭支付单，
  两者用同一把"订单+支付"联合 CAS 决定，输的一方走补偿（退款），不出现"订单取消但钱收了"。
- 该扩展未实现（当前充值不绑订单），规则先落档，S4 若做收费前置直接采用。
