## 卡 1｜消息中间件：RocketMQ vs Kafka vs RabbitMQ

| 项 | 内容 |
|---|---|
| 选它 | **RocketMQ 5**（`rocketmq-client-java` 5.2.2，gRPC 客户端） |
| 备选 | Kafka（生态最大、吞吐最高）；RabbitMQ（最易上手）；不用 MQ（HTTP 直连） |
| 为什么不用 Kafka | 本项目事件量级是"每柜每秒数条"（10 柜量级），Kafka 的分区/副本调优、消费组再平衡与运维成本换不来收益；且本项目需要**按设备保序**的语义，Kafka 要靠分区键自己保证，RocketMQ 的 message group 直接给了 |
| 为什么不用 RabbitMQ | 队列语义够用，但"同柜保序 + 失败分级 + 死信"要自己搭；且本项目已经在用 RocketMQ 的**事务/延迟**语义之外的特性（message group、property 透传 traceId） |
| 为什么必须上 MQ（而不是线程池/阻塞队列） | 三个理由：①**跨进程重启不丢**（队列在 broker，进程重启后继续消费）；②**削峰**（设备离线重连时会补送事件，见 `_g5_outage`）；③**多实例竞争消费**天然支持水平扩展（批次24 双实例演练 `_c29`） |
| 代价（如实） | 云上 4G 内存机器装不下 RocketMQ（默认 JVM 参数吃内存），所以**云上走 HTTP 通道**（`SWAP_DEVICE_MQ_ENABLED=false`）；这是"部署形态降级"，已在 runbook 的通道矩阵里写明 |
| 何时该换 | 事件量到十万级/秒、或需要跨机房副本 → Kafka；只需要"单个消费者、允许丢少量" → 直接 HTTP + 重试更省 |
| 证据 | `document/plans/S0.3-设备协议v1.md` §7；`DeviceEventMqConsumer`（并发度/分级 ack/死信）；`_c28`/`_c29`；runbook 通道矩阵 |

## 卡 2｜并发扣减：Redis 分布式锁 vs 数据库乐观锁（CAS）

| 项 | 内容 |
|---|---|
| 选它 | **两者都用，但职责分明**：Redis Lua 做"分配弹仓"的原子抢占（性能层），DB 条件更新（`WHERE lock_order_id IS NULL`）做**最终判官**（正确性层） |
| 备选 | 只用 Redis 锁（Redisson）；只用 DB 悲观锁（`SELECT ... FOR UPDATE`）；只用乐观锁版本号 |
| 为什么不能只用 Redis 锁 | 锁会失效（TTL 到期、Redis 重启、网络分区），一旦锁失效，超卖就真的发生了——**锁是性能优化，不是正确性保证** |
| 为什么不用悲观锁 | 下单是高频短动作，`FOR UPDATE` 会在热点柜上排队；而且本项目**用行锁的地方是刻意的**（月卡日限判定，批次34）——因为它要保护的是"读-判断-写"的临界区，不是单行自增 |
| 代价（如实） | 双层意味着**两条路径都要维护**，且偶发"Redis 抢到但 DB 条件更新失败"要能自愈（本项目做法：DB 失败即视为未抢到，释放 Redis 锁并重试/返回库存不足） |
| 何时该换 | 单机部署且 QPS 低 → 直接 DB 条件更新即可（去掉 Redis 层）；热点极端集中 → 分桶/排队（Redis 队列 + 串行 worker） |
| 证据 | `AllocationService`（Lua + DB 兜底）、`_g3_concurrency.ps1`（并发占仓）、`AllocationOversellIT`（CI 内的零超卖集成测试） |

## 卡 3｜缓存：本地 Caffeine vs 纯 Redis vs 不缓存

| 项 | 内容 |
|---|---|
| 选它 | **两级**：L1 Caffeine（进程内，30s）+ L2 Redis（300s）+ Pub/Sub 失效广播 + TTL 抖动兜底 |
| 备选 | 只用 Redis（每次读一次网络往返）；只用本地缓存（多实例不一致）；不缓存 |
| 为什么加 L1 | 站点列表/套餐目录这类"读多写少、容忍秒级陈旧"的数据，L1 把 QPS 从 Redis 卸掉；本项目读路径容量实测 3.2k~3.5k/s（`_p03_read_capacity`），L1 命中率与 Hikari/Redis 指标都在 `/admin/cache/stats` 可查 |
| 为什么必须有失效广播 | 多实例各自有 L1，写路径单靠 TTL 会出现"实例 A 已更新、实例 B 还在返回旧值"的窗口 → Pub/Sub 广播失效 + 延迟双删 |
| 代价（如实） | 缓存只用在**展示/字典类读**；资金与状态判断一律不走缓存（订单状态、库存、"可退金额"都直读 DB/Redis 权威结构）。这条边界写进了 `TwoLevelCacheService` 的使用说明 |
| 何时该换 | 实例数少且 QPS 低 → 只用 Redis 更简单；强一致要求 → 取消缓存或改成"读主库 + 变更订阅" |
| 证据 | `common/cache/TwoLevelCacheService`、`_c1_cache.ps1`、`CacheAdminController`（命中率/命中数） |

## 卡 4｜部署形态：Docker + systemd/nginx vs Kubernetes

| 项 | 内容 |
|---|---|
| 选它 | **单机 systemd 双服务 + nginx 同源反代**（云上 4G/4 核轻量服务器） |
| 备选 | Docker Compose；K8s（或 k3s）；Serverless |
| 为什么不上 K8s | 规模不兑现：1 台机器、2 个 Java 进程、10 柜设备量。K8s 带来的能力（自愈、滚动发布、HPA）在这个规模下**用 systemd 的 `Restart=on-failure` + 手工发布就够**，而代价是"多一层需要维护的控制面 + 排障路径变长"。这个规模下的合理选择是"能看懂、能一个人运维" |
| 为什么用 nginx 而不是让后端开 CORS | 同源：`dist` 静态 + `/api` 反代，浏览器只有一个 origin ⇒ 不需要 CORS（不需要预检、不需要凭据模式），也顺手拿到 gzip、静态缓存与安全头。配置见 `scripts/cloud/nginx-swap.conf` |
| 为什么中间件仍给了 compose | 复现门槛：外部人要跑起来需要 MySQL/Redis/RocketMQ，`docker-compose.middleware.yml` 让他们 5 分钟起环境（本机 Windows 无 Docker，故 compose 未在本机实测，已如实标注） |
| 代价（如实） | 发布是"停服务→换包→起服务"（有秒级中断），没有滚动发布；云上 HTTP 通道而非 MQ 形态；ufw 只开 22，公网演示靠隧道/录屏（暴露面是用户拍板项） |
| 何时该换 | 多机多实例、需要滚动发布与自动扩缩 → 上 K8s/k3s；只想隔离依赖 → Docker Compose 就够（比 K8s 更划算） |
| 证据 | `scripts/cloud/*`（deploy/rollout/probe/nginx conf/service unit）、`document/knowledge/runbook.md`、批次31/33 的云上探针输出 |

## 卡 5｜可观测性：OpenTelemetry/SkyWalking vs traceId + 结构化日志 + 少量指标

| 项 | 内容 |
|---|---|
| 选它 | **traceId 全链路贯穿 + 结构化日志 + 少量关键指标（Prometheus 6 项业务指标）** |
| 备选 | 全链路 APM（SkyWalking/OTel Collector + 后端存储）；只看服务器指标 |
| 为什么不上全链路 APM | 中小规模的真实约束是"**监控也要算 ROI**"：链路追踪存的是 trace 明细，机器与存储成本随流量线性增长，而这个规模的排障路径 90% 是"按 traceId 捞日志"。本项目把 traceId 做成了**贯穿 HTTP 头 → MDC → MQ property → 消费端 MDC** 的一条线，一次 grep 就能拉出整条链路 |
| 指标只留关键项 | 6 项业务指标（outbox 积压/死信、未处理告警、延迟任务积压、对账差异、可分配满电仓），都是"**能直接指向动作**"的量；堆 CPU/内存这类机器指标交给云厂商 |
| 代价（如实） | 没有火焰图/跨服务拓扑；排查"某接口慢"要靠日志耗时字段与 `/admin/cache/stats` 一类自建视图 |
| 何时该换 | 服务数 > 5、跨团队排障、需要 SLA 归因 → 上 OTel + 采样（采样率与保留期是成本旋钮） |
| 证据 | `TraceIdFilter`、`SwapMetrics`、`_c24_metrics.ps1`、`grafana-dashboard.json`、runbook"监控接入"节 |

## 表设计与索引依据（挑最值得讲的 4 张）

> 讲法：**先讲这张表要承担什么不变量，再讲索引怎么服务它**——索引不是"给查询加个索引"，而是不变量的执行器。

### 1. `swap_order`（订单）

| 设计点 | 为什么 |
|---|---|
| `active_user_key` 生成列 + `uk_active_user` | 业务不变量"**一人一活跃单**"。生成列把"活跃态"编码进唯一键（`IF(status IN (1,2,3,4), user_id, NULL)`，终态为 NULL ⇒ 不约束），并发下单由**数据库**保证唯一，而不是靠"先查再插"的竞态 |
| `uk_order_no` | 对外单号（雪花）唯一，幂等与对账都以它为准 |
| `uk_idem_key`（db/02 补） | 下单幂等闸：同 key 重放返回同单（用户重复点击的正面答案） |
| `idx_user_time(user_id, create_time)` / `idx_cabinet_time(cabinet_id, create_time)` | 用户端"我的订单"与柜详情"进行中订单 + 按时间倒序"两条最热查询；**最左前缀**让"某用户"与"某用户某时间窗"共用一条索引 |
| `idx_open_command_seq(cabinet_id, open_command_seq)`（db/10 补） | 设备事件靠 `commandSeq` 找回订单（`OrderEventService.findBySeq`），没有它会走全表扫 |
| `idx_order_status(status)` + `idx_order_create_time(create_time)`（db/10 补） | 扫超时任务每 5s 按状态扫、管理端列表按创建时间倒序分页（此前 filesort） |

### 2. `payment_record` / `refund_record`（资金流水）

| 设计点 | 为什么 |
|---|---|
| `uk_trade_no` | 每笔资金动作的唯一凭证；对账以它跟渠道账单对齐 |
| **`uk_payment_idem`（生成列 `idem_key`，db/18）** | 幂等闸，但**按资金动作语义分型**：扣费类"每单每类一次"，退款类不受约束（退款是多次事件，幂等由 `refund_record` 的 `(order_id, reason)` 与 `uk_trade_no` 各自保证）。这条是批次35 根据真实缺陷改的——旧的 `(order_id, payment_type)` 会把**第二笔合法部分退款**吞掉（钱包对、台账漏） |
| `refund_record.uk_refund_order_reason(order_id, reason)` | 同订单同原因只退一次（防双通道双退） |
| 金额一律 `INT` 分 | 不让浮点碰钱；分账用 long 运算后取整，`platform = base - agent` 保证不丢分 |

### 3. `work_order`（工单）

| 设计点 | 为什么 |
|---|---|
| 状态机 `status` + `uk_wo_no` / `uk_wo_alarm` | 状态推进一律 CAS 条件更新（`WHERE status = from`），并发下只有一方成功；`uk_wo_alarm` 保证**一条告警只派生一张工单**（幂等由 DB 保证）；流转日志表留下"谁在什么时候把状态从哪推到哪" |
| `sla_deadline` + `sla_breached` | 超期是**业务可查询字段**，不是"每次查询时算一遍"——扫描任务据此告警，列表据此标红 |
| `station_id` + `idx_station_create`（db/17 补） | 数据范围过滤需要可过滤列（冗余归属列，创建时按 `device_no → 柜 → 站` 解析），并把 NULL 视为无归属 ⇒ 受限身份 fail-closed |
| `idx_wo_status_time(status, create_time)` | 列表默认按状态筛选 + 时间倒序 |

### 4. `outbox_event`（跨域事件）

| 设计点 | 为什么 |
|---|---|
| `uk_outbox_event_key(event_key)` | 幂等：同一业务事件只入队一次 |
| 状态 CAS（`NEW → SENT`） | 多实例并发中继只有一方能标记成功，避免重复投递 |
| `idx_outbox_status_retry(status, next_retry_time)` | 中继任务只扫"待发且到点"的行——这是它能在小机器上每几秒跑一轮的前提 |
| `attempts` + `DEAD` 状态 | 投递失败有界重试，超限转死信并告警（`OUTBOX_DEAD`），不无限打转 |
