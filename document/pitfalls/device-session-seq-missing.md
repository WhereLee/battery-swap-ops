# 坑位：设备事件未回带开门会话 commandSeq → 事件到达但订单不推进

> 状态：已修复（2026-09-17，批次26）| 证据：`scripts/verify/batch26/_c30_out.txt`（二跑 14/18 → 修复后 25/25）、设备日志 `BATTERY_OUT … commandSeq=`（空）

## 现象

- 异构设备端上报 `BATTERY_OUT` **平台已受理**（http=200、设备台账 lastEventSeq 推进、电池出仓）；
- **但订单停在 OPENED 永不完成**；随后 RETURN 下单被拒 400（"存在进行中订单"）；
- 表面看"事件链路全通"，业务链路全断——最迷惑人的一类。

## 根因链

1. 契约 §5 会话关联：同一次开门会话内的 `BATTERY_OUT/BATTERY_IN` 必须**回带该次 OPEN_CELL 的 commandSeq**
   （"设备无需知道 orderId，订单域据此精确推进"）；
2. 设备端实现 `local_remove/local_insert` 直接 `enqueue_event(...)`——**没有回带 commandSeq**（字段为 null）；
3. 平台收到无 commandSeq 的事件：更新设备事实（台账/仓态），但**无法关联订单**——订单停在 OPENED；
4. 错误完全静默：两侧日志都没有"失败"，只有业务不动——**"事件能到平台"≠"业务能推进"**。

## 修复

- 设备端补开门会话语义（对齐 Java sim 参考实现，`CabinetSim.sessionSeq/sessionAt`）：
  - `handle_cmd` 受理 OPEN_CELL 时记会话：`cellNo -> (commandSeq, 时刻)`；
  - `local_remove`：取会话（**不终结**——"一次开门会话最多一取一还"）；
  - `local_insert`：取会话后**终结**；
  - 保鲜窗 5 分钟（超窗不再回带，防陈旧关联；契约与 sim 同口径）。

## 可复用教训

- **契约要逐字段对照实现**：协议"语义层"的字段（commandSeq 会话）比"传输层"的字段更容易漏——
  事件发出去了、200 回了，不代表业务字段都在；
- **排障顺序**：先看"业务状态机为什么不动"（订单 status），再顺着状态机的驱动条件（会话关联）
  反查事件字段，而不是从"网络/日志有没有报错"开始；
- 异构实现（第二实现）是契约完备性的最强检验：**它会把参考实现里"约定俗成"的部分全部暴露成显式要求**。
