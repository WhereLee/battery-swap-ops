# 坑位：一个索引担两个职责，按其中一个职责删掉它，另一个会被静默破坏

> 发现：批次40（索引审计）｜ 影响面：**所有"用唯一键兼职查询访问路径"的表设计**
> 一句话：`uk_order_type(order_id, payment_type)` 既是资金动作幂等闸（唯一性），
> 又是 `WHERE order_id = ?` 的唯一访问路径（可访问性）。为修前者的语义问题删掉它，
> 后者的查询**全部退化成全表扫描**——结果依然正确，没有任何测试会红。

## 现象（服务器侧实测，不是推断）

```
语句: SELECT ... FROM payment_record WHERE ( order_id = ? )
实测: 54,647 次执行，其中 5,068 次 SUM_NO_INDEX_USED，累计扫 40,641,477 行，返回 6,629 行
每次: 全表扫 ~8,090 行换 1 行（表 7,875 行）

EXPLAIN（修前）: type=ALL  possible_keys=NULL  key=NULL  rows=7875
```

旁证（同一条 SQL，两个 digest 的时间线）：

| digest | 执行次数 | 无索引次数 | FIRST_SEEN | LAST_SEEN |
|---|---|---|---|---|
| 走索引的那一支 | 14,240 | **0** | 2026-09-11 17:54 | **2026-09-17 10:26** |
| 全表扫的那一支 | 54,647 | 5,068 | 2026-09-14 19:42 | 至今（仍在跑） |

走索引的一支在某个时间点**停止被执行**，此后只有全表扫 —— 这就是"访问路径消失"的形状。

## 根因

`db/18`（批次35 / AUD-6）为修"同一订单第二笔部分退款台账漏记"，把
`uk_order_type(order_id, payment_type)` 换成了生成列上的 `uk_payment_idem(idem_key)`。

那个唯一键当时承担**两个职责**：

1. **唯一性**：每单每类资金动作只记一次（幂等闸）——db/18 要改的正是它（REFUND 需要允许多笔）；
2. **可访问性**：`WHERE order_id = ?` 的**唯一**索引前导列——删掉它，这个谓词就没有任何索引可用。

改 ① 的时候，② 被一起删掉了。**MySQL 不会报错**：查询继续返回正确结果，
只是从"1 行"变成"全表 7,875 行"。项目当时四层校验全绿（单测/契约/浏览器/覆盖率），
`_c37`（批次35 的台账剧本）也全过——因为它验证的是**语义**（第二笔退款能否落台账），不是**代价**。

## 修法

```sql
-- db/19-index-audit-fixes.sql
ALTER TABLE payment_record ADD KEY idx_order_id (order_id);   -- 非唯一
```

**刻意不用唯一键**：退款多笔语义已由 `refund_record(order_id, reason)` 唯一键与
`payment_record.uk_trade_no` 各自保证，幂等闸已收窄到 `uk_payment_idem`；
重建 `(order_id, payment_type)` 唯一键等于把 AUD-6 退回来。
**"恢复访问路径"与"恢复唯一约束"是两件事，只做前者。**

实测效果：`type=ALL rows=7875` → `type=ref key=idx_order_id rows=1`；
打 20 次真实请求：执行数 +20、无索引次数 **+0**、扫行数 **+20**（修前会扫约 161,800 行）。

## 怎么发现这类问题（可复用的三步）

1. **问服务器**，别问代码：

   ```sql
   SELECT DIGEST_TEXT, COUNT_STAR, SUM_NO_INDEX_USED, SUM_ROWS_EXAMINED, SUM_ROWS_SENT
   FROM performance_schema.events_statements_summary_by_digest
   WHERE SCHEMA_NAME = 'swap_app' AND SUM_NO_INDEX_USED > 0
   ORDER BY SUM_ROWS_EXAMINED DESC;
   ```
2. **用表大小过滤噪音**：10 行小表全扫是正常设计，5,000 行表每次扫 4,000 行才是缺陷。
   阈值口径要写进脚本（本仓库：>200 行/次 且 表 >1000 行）。
3. **用因果差值结案**：计数器是**累计**的，含修复前历史，不能直接当判据。
   正确做法：读计数器 → 打真实流量 → 再读 → 断言"执行数涨、无索引次数不涨、每次扫行数塌到约等于返回行数"。

## 防回归

`scripts/verify/batch40/_c39_index_audit.ps1`（14/14 PASS）三层断言：
审计清单 + `EXPLAIN`/索引前导列断言 + 打流量的因果差值。
其中**索引前导列断言**针对的就是本坑位的形状——它不依赖优化器当下的选择，
而是直接问"这个谓词要用的访问路径，作为索引存在吗"。

## 通用规则

- **唯一键兼职访问路径时，删它之前先查一遍"谁在读这条路径"**：
  `WHERE <唯一键首列> = ?` 是最容易被忽略的一类查询；
- **改索引前先跑一次 `SUM_NO_INDEX_USED` 审计**，改完再跑一次对比；
- **把"我的索引清单"与"我实际跑的查询"两边的方向都验证一遍**：
  前者回答"为什么有这个索引"，后者回答"这条查询有没有索引"——两个问题不一样；
- **修复要与验证同批**：本次修复的价值一半在 `ALTER TABLE`，一半在"打流量读差值"的证据；
  没有后者就只是"我加了个索引"。
