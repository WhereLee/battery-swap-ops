# 批次24 — P0-2 水平扩展：分片保序 + 双实例演练

> 日期：2026-09-16 ~ 09-17
> 范围：swap-server（MQ 消费端 + 配置）、swap-sim（MQ 发送端 + 配置）、spike/剧本、契约与架构文档
> 结论：**完成**。① spike 实测拿到 FIFO message group 的真实语义（含一条反直觉结论）；
> ② 两端改造落地（发送端按柜设组、消费端按柜分片：同柜串行 / 跨柜并行）；
> ③ 分片剧本 `_c28` 15/15 PASS（含线程级并行证据与两层守卫拒绝证据）；
> ④ 双实例 30 分钟演练 `_c29`（结果见 §五）。

## 一、背景与目标

改造前的事件通道是"单 topic 单队列 + 消费并发度=1"：保序最强，但吞吐天花板＝单线程处理能力，
且"多实例互斥"只有设计从未双实例跑过。roadmap P0-2 要求：① 技术验证 spike（RocketMQ 5 gRPC
FIFO message group）；② 分片版剧本（乱序/重放注入）；③ 双实例演练（同库同 Redis 两份 server，
连续 30 分钟，断言任务不重复执行、无锁冲突雪崩）；④ 更新契约 §7 与 architecture。

前置事实：项目已用 `rocketmq-client-java` 5.2.2（gRPC 客户端），本地 RocketMQ 5.3.1
（namesrv 9876 / broker 10911 / proxy 8081）——**具备 FIFO message group 的客户端条件，无需换栈**。

## 二、spike：FIFO message group 实测（`FifoMessageGroupSpike`）

运行方式：`mvn -pl swap-server test -Dtest=FifoMessageGroupSpike`（类名不匹配 surefire 的 `*Test`
include，CI 不触发；本地手动跑）。前置：`mqadmin updateTopic -c DefaultCluster -t swap-spike-fifo -a +message.type=FIFO`。

| # | 验证项 | 实测结果 | 对设计的含义 |
|---|---|---|---|
| A | FIFO topic 接受 `setMessageGroup` | 成功 | 通道形态可用 |
| A' | **NORMAL topic 也接受** `setMessageGroup` | 被接受（broker 未强校验 messageType） | 业务 topic 可**平滑迁移**：先改发送端再迁 topic 属性也不断流 |
| B | 同柜（同 group）到达序 | 3 柜各 `[1,2,3,4,5]`，跨柜交错不影响柜内序 | **保序不变量可从"全局"降为"每柜"** |
| C | 同柜首条未 ack 时后续是否被 hold | **不 hold**：一次 receive 批量里同柜 3 条全部可见 | **反直觉结论**：服务端只保证"投递序"，不保证"消费串行" → 柜内串行**必须由消费端实现**，不能依赖 broker |
| D | 未 ack 消息的恢复路径 | `changeInvisibleDuration(3s)` 后到期重投，正是未 ack 那条 | 处理超时/消费者崩溃 → 重投；重复投递由业务幂等（序守卫 + CAS）吸收 |
| 附 | 空队列 `receive` 行为 | 返回空集合，不抛异常 | 现有"异常才重建 consumer"的逻辑无误（空轮不会触发重建风暴） |

证据：`scripts/verify/batch24/_spike_fifo_out.txt`（3/3 绿，36.86s）。

**这条 C 结论是本批最重要的收获**：若照"服务端 FIFO 会自动串行"的想当然实现，消费端并行处理同柜
消息就会把柜内序打乱（序守卫会拒掉本该受理的事件＝真丢数据）。因此改造采用"服务端保证投递序 +
消费端保证柜内串行"的双保险，且后者是**必需项**而非优化项。

## 三、主代码改造

### 发送端（swap-sim）
- `MqEventReporter.buildMessage`：`fifo-group=true` 时 `builder.setMessageGroup(cabinetNo)`
  ——同柜消息进同队列、柜内严格 FIFO 投递；`false` 即回退"单队列全局序"形态（回退开关）。
- 保序铁律不变：单发送线程 + 有界队列 + **失败队首持留**（绝不跳过重排——同柜后续更大 seq 先到
  会被平台序守卫当旧序拒＝真丢数据）+ 退避重试 + producer 懒重建/回收 + 优雅关闭补发。
- 配置：`SimProperties.Mq.fifoGroup`（默认 true）、`application.yml` 显式化。

### 消费端（swap-server）
- `DeviceEventMqConsumer` 从"单线程 `receive(1)` → 处理 → ack"改为：
  1. `receive(batchSize=16, invisible=30s)` 批量拉取；
  2. **按柜分片**：`shardKey(message)` 优先取 FIFO message group，回退 `X-Device-No` property；
     `workerIndexFor(key, n) = Math.floorMod(key.hashCode(), n)` → 同柜恒定同一 worker（柜内串行），
     跨柜落到不同 worker（并行度 = `consumer-threads=4`）；
  3. worker 内处理完再 `ack`；`Semaphore(2×batch)` 限在途未 ack 数量（防拉取远快于处理造成
     invisible 到期重投风暴）；
  4. 停机：`running=false` → 拉取线程退出 → worker `shutdown()`（在途处理完）→ 未 ack 由 broker 重投。
- 不变的部分：验签/编排复用（不绕开既有逻辑）、毒消息分级 ack 丢弃、瞬时异常不 ack 等重投、
  consumer 懒构建 + 5s 重建、traceId 经 MDC 透传。
- 配置：`DeviceChannelProperties.Mq` 新增 `consumerThreads=4` / `batchSize=16` / `invisibleSeconds=30`
  （invisible 从原 15s 提到 30s，给同柜排队留余量），`application.yml` 显式化并写明分片语义。

### 环境侧
- 业务 topic 迁移 FIFO 属性：`mqadmin updateTopic -n 127.0.0.1:9876 -c DefaultCluster -t swap-device-event -a +message.type=FIFO`
  → `TopicConfig[... attributes={+message.type=FIFO}]`（8 读/8 写队列）。spike A' 已证明迁移前后都能发，
  切换无断流窗口。
- 形态切换：平台以 MQ 通道运行（`.local/start-server-mq.ps1`），sim 以 `event-channel=mq` 上报
  （`.local/start-sim-mq.ps1`）——这是契约 §7 的终态形态；HTTP 通道保留为降级。

## 四、分片剧本 `_c28`（15/15 PASS）

注入器 `ShardOrderingSpike`（Java，MQ 客户端 + JDK HttpClient，动态基线可重复跑）+ PowerShell 编排
（前置检查 / 调用注入器 / 平台日志断言 / 台账复核）。事件类型用 `DOOR_CLOSED`（只推进设备台账、
不动订单与仓/电池——纯序守卫验证）；柜用 SWAP-C-003 / C-004（sim 走 MQ 时也占这些柜，故剧本前置要求
sim 停止，避免 HTTP/MQ 双路推进台账干扰断言）。

| 场景 | 注入 | 断言 | 结果 |
|---|---|---|---|
| S1 同柜乱序 | 同 bootId 先发 `base+5` 再发 `base` | 台账停在 `base+5`、bootId 不变；日志有序守卫拒绝行 | PASS |
| S2 跨代重放 | 新代际推到 `base+50` 后，用**已见旧 bootId** 发 `base+100`（更大 seq） | 台账与当前代际均不变；日志有代际重放 WARN 行 | PASS |
| S3 多柜并发 | 两柜各 20 条递增事件交错注入 | 两柜台账都到 `base+19`、bootId 各自独立（不串柜） | PASS |
| 并行证据 | — | 平台日志出现 ≥2 个不同 `platform-mq-worker-N` 线程处理事件（实测 worker-0 与 worker-3） | PASS |
| 消费形态 | — | 启动行 `workers=4 batch=16` | PASS |

合计 15 项检查全 PASS（`scripts/verify/batch24/_c28_out.txt`、注入器输出 `_c28_injector.log`、
spike 输出 `_spike_fifo_out.txt`）。S2 同时证明"两层守卫互补"：序守卫按代际放行（bootId 变了就接受），
代际守卫拦历史重放——只有序守卫时，携带更大 seq 的历史代际事件会污染台账。

## 五、双实例演练 `_c29`（30 分钟）

拓扑：node1 `:8400`（workerId=0）+ node2 `:8401`（workerId=1），**同 MySQL、同 Redis、同 consumer group**，
sim 以 MQ 通道上报 10 柜。窗口 00:04:11 起，6 轮 × 300s 流量（交替打两实例）+ 尾部静默期补足 30 分钟。

每轮流量（`_c29_traffic.ps1`，全部成功、零 UNREACHABLE）：
- 两实例 health；
- 用户登录 + **下单后故意不取电**（preempt 120s 超时 → 延迟任务必须取消，且只能取消一次）；
- 用户报障（生成工单 → 工单 SLA 扫描有活）；
- 在**另一实例**上触发管理端对账 + 看板读（job 锁竞争 + 读一致性）。

断言口径（`_c29_dual_instance.ps1`）：
1. 30 分钟后两实例仍 UP（无崩溃/无 OOM）；
2. workerId 租约互异（Redis 租约 owner=ip:port），窗口内无 `WorkerIdRegistry` ERROR（续租失败）；
3. 6 轮流量全部落在两实例上（各自成功调用 ≥6），零失败；每轮对账 total=0；
4. **6 笔未取电订单全部 `closeReason=PREEMPT_TIMEOUT`**（延迟队列 ZREM 原子领取生效；
   若重复领取，第二次会被 CAS 吸收，但会留下状态/台账不一致 → 由第 7 项兜底裁判）；
5. MQ 事件被**两个实例都消费到**（同 consumer group 的 broker 侧负载均衡），两侧都有分片 worker 活动；
6. 无 `JobLockService` 降级行（Redis 锁未失效）、无连接拒绝风暴、ERROR 行数有界；
7. **最终裁判**：演练结束后跑一次全量对账，14 组不变量 total=0（重复执行必然破坏守恒）。

**结果：PASS 18/18**（`scripts/verify/batch24/_c29_out.txt`；窗口 2026-09-16 23:57:22 起满 30 分钟）：

| 断言组 | 实测 |
|---|---|
| 存活 | 30 分钟后 node1/node2 双 UP（无崩溃/无 OOM） |
| 租约 | workerId=0 / 1 互异（Redis 租约 owner=ip:port）；窗口内零 WorkerIdRegistry ERROR |
| 流量 | 6 轮全部落在两实例（成功调用各 15）；零 UNREACHABLE；每轮对账 total=0,0,0,0,0,0 |
| 延迟任务 | 6 笔未取电订单全部由超时任务关闭：PICKUP_TIMEOUT×4 + PREEMPT_TIMEOUT×2（均 status=7） |
| **零重复铁证** | 每笔订单**只在其中一个实例的日志中关闭一次**（node1 执行 1 笔 / node2 执行 5 笔，无重叠） |
| MQ | 事件被两实例都消费（node1=2 / node2=3 行；broker 侧负载均衡）；两侧分片 worker 均有活动 |
| 锁与错误 | 零 JobLockService 降级行；ERROR 0/1 有界；零连接拒绝风暴 |
| **最终裁判** | 全量对账 14 组不变量 **totalViolations=0**（重复执行必然破坏守恒） |

## 七、踩坑

1. **想当然的服务端 FIFO 语义**：以为"同柜未 ack 则后续不可见"（那样消费端并行就天然安全）。
   实测证伪 → 消费端必须自己按柜串行。教训：**分布式语义要实测，不要读文档标题就下结论**。
2. **注入器 seq 固定值不可重复跑**：首版用 100000+/200000+ 固定基线，第二轮跑时台账已高于注入值 →
   全被序守卫拒。改为动态基线（`baseFor()` = max(当前台账)+1000）后剧本幂等可重复。
3. **PowerShell `$PSScriptRoot` 层级算错**：剧本在 `scripts/verify/batchN/`（三级深），
   `..\..` 只到 `scripts/` → 密钥与日志路径全错（表现为管理端调用 NPE + 日志写不进去）。
   教训：路径基准要么硬编码仓库根，要么按脚本实际深度数清楚；关键前置加 fail-fast 校验（token 为空即 throw）。
4. **`mvn verify` 撞运行中的 jar**：spring-boot `repackage` 要把 jar 改名 `.original`，被运行中的
   平台进程锁住 → BUILD FAILURE（不是代码问题）。纪律：verify/package 前先停服。
5. **多模块跑单个测试类**：`-Dtest=Xxx` 在无匹配测试的模块（swap-contract）会直接失败 →
   需加 `-Dsurefire.failIfNoSpecifiedTests=false`。

## 八、结论

P0-2 完成：扩展性问题有了正面答案——**保序不变量从"全局"降到"每柜"**（业务语义不变，序守卫本就按柜判定），
消费端从单线程串行变为按柜分片并行（workers=4，可配），并有 spike 实测、分片剧本（15/15）、
双实例 30 分钟演练三层证据；多实例互斥（job 租约锁 + ZREM 原子领取 + workerId 租约）从"设计"变成"跑过"。
