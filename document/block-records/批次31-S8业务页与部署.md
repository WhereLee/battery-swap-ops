## 二、后端交付

### 31a 能力位补全（`common/action/ActionsSupport`）

| 状态机 | 新增能力位 | 动作码 → 端点 | 语义依据 |
|---|---|---|---|
| 结算单 | `settlement(status)` | `confirm` → `/admin/settlement/{id}/confirm`；`paid` → `/{id}/paid`；PAID 无动作 | 打款不可逆；迟到流水进下一期，不是改这张单 |
| 订单资金 | `order(status, refundableFen)` | 可退额>0 时：已完成单给 `reversal`，其余给 `refund` | 已完成单资金已结算入账（含分账），只能走冲正；**通道二选一必须留在服务端**——押金二次退款事故的同类风险就是"前端按状态自己挑通道" |

同时新增 `settlement/enums/SettlementStatus`（GENERATED/CONFIRMED/PAID）：此前 1/2/3 字面量散在 service、SQL、
前端标签三处；补枚举后 `ActionsSupport` 用 switch 覆盖全部枚举值，**新增状态时编译失败**（与 `WorkOrderStatus` 同纪律）。

### 31b 新增 4 个 BFF 视图端点（合计 11 个 `/admin/view/**`）

| 端点 | 返回 | 权限码 | 数据范围 |
|---|---|---|---|
| `GET /admin/view/order` | `PageResult<OrderListItemVO>` | `admin:order:read` | `@DataFilter("view-order-page")`（站点范围） |
| `GET /admin/view/cabinet` | `PageResult<CabinetVO>` | `admin:asset:read` | `@DataFilter("view-cabinet-page")`（站点范围） |
| `GET /admin/view/settlement` | `PageResult<SettlementVO>` | `admin:settlement:read` | 无（代理维度=全局口径，见方案 §4.8） |
| `GET /admin/view/settlement/{id}` | `SettlementDetailVO`（单头+分账流水） | `admin:settlement:read` | 同上 |

**为什么订单列表也要视图层**：域端点 `/admin/order` 返回 `PageResult<SwapOrderEntity>`，把 `idemKey`（雪花幂等键）、
`openCommandSeq`、`userPlanId`、`couponId` 一并下发给浏览器。视图层收口后 `_c34` 有两条机器断言专门守这件事
（响应体与 TS 接口都不得出现这四个字段名）。

**防 N+1（三处，均一次批量查询）**：订单列表的柜号、订单列表的可退金额、结算列表的代理名。

### 31c 可退金额批量口（`RefundService.refundableAmounts`）

列表一行一个 `refundableAmount(id)` 就是 2×N 次查询。新增批量口后**加减规则与单订单口径共用同一个
`accumulate()` 私有实现**——两个入口一个口径，杜绝"列表显示可退 3 元、详情显示 5 元"。单订单方法行为不变
（原有 3 条口径单测未改一行仍绿）。

`SettlementService` 另补 `pageStatements`（真分页：COUNT+LIMIT 由拦截器注入）与 `statementById`（视图层读取口）。
结算单列表**不再用"拉 200 条截断"冒充分页**——那正是批次30 假分页缺陷的形态。

## 三、前端交付（8 个业务页）

| 路由 | 页面 | 关键点 |
|---|---|---|
| `/work-orders` + `/:id` | 工单列表 + 详情 | 五步动作链（分诊可改严重级、派单必填处理人、其余可附备注）；流转日志时间线；SLA 超期行标红；设备号可钻取到柜详情 |
| `/orders` + `/:orderNo` | 换电订单 + 详情 | 状态/订单号/用户三维筛选；可退金额与退款通道来自服务端；详情含时间线 + 支付/退款流水 |
| `/cabinets` + `/:cabinetNo` | 换电柜 + 详情 | 心跳年龄（服务端算）；柜详情 4 块：仓位与电池（SOC 进度条）、未处理告警、进行中订单、最近指令流水 |
| `/settlements` + `/:id` | 结算单 + 详情 | confirm→paid 两次二次确认（打款不可逆已写进弹窗文案）；分账流水含**负数冲正行**（标红 + 符号在货币符号前） |

**统一的 UI 纪律**（沿用批次30）：
1. 按钮先由后端 `allowedActions` 决定，再由 `v-access` 按权限码过滤（`display:none` 是 UX，后端才是安全边界）；
2. 金额一律整数分，页面**不做任何加减**（唯一例外是结算详情的"守恒校验"展示标签，且明确写"只做展示层断言"）；
3. 时间一律 epoch millis 交 `formatTime`；比率一律 0..1 交 `formatPercent`。

`utils/format.ts` 一处修正：`formatFen` 负数改为 `-¥3.00`（原 `¥-3.00` 在分账冲正行上像笔误）。

## 四、部署形态（nginx）

- `scripts/cloud/nginx-swap.conf`：`root /opt/swap/web` + SPA `try_files` 兜底 + `/assets/` 30 天 immutable +
  `index.html` no-store（防部署后客户端钉在旧 bundle）+ `/api/` 反代 8400 + gzip + 三个零成本安全头。
- **后端不开 CORS**（方案 §4.7）：同源反代让浏览器只有一个 origin，也就不存在 CORS 面与预检开销。
- `vite.config.ts` 补 `preview.proxy`：`vite preview` 托管的是**构建产物**，是最接近 nginx 的本地形态，
  但 `server.proxy` 不作用于 preview——批次31 前它没有 proxy，所以 `_c35` 只能靠 dev server，证据强度更低。
- `scripts/cloud/deploy-web.ps1` + `rollout-web.sh`：快照 → db/16,17 → 换 jar → 发布 dist → 装 nginx 站点 → 同源冒烟。
  **不动 ufw**：公网暴露面仍是用户拍板项（方案 §6 P0-4 遗留）。

### 关于 `_c35` 的诚实边界

1. **截图我没有用眼睛看过**：本轮执行环境是纯文本模型，无法读取 PNG。页面的正确性证据是
   **DOM 级断言**（标题、卡片数、表格行数、菜单项、横向溢出、占位符扫描）+ 零控制台错误，
   **不是视觉评审**。截图留档是给用户/面试官看的，不是我的判定依据。
2. `_c35` 走的是 `vite preview`（构建产物 + 本地反代），**不是 nginx 本人**；nginx 形态的验收在云上做（§六）。
3. 权限差异（OPS/FINANCE/SUPPORT 看不同菜单）仍由 `_c32` 的接口级断言覆盖，浏览器轮只跑 SUPER 身份
   ——原因：受限身份需要额外账号，且接口层已证明过滤生效。这条边界在方案 §7 有同类声明。

## 七、过程与坑

1. **`_c35` 首跑 2 条 FAIL 全是我自己的断言写错**（不是产品缺陷）：
   ① el-tabs 非活动 pane 仍在 DOM，按 `.el-table__row` 全表计数把告警页 20 行读成 35 行（批次30 §六.6 记过同一个坑，

   改为只扫 `.el-table` 的表内文本。
2. **`Start-Process node ... vite preview` 与健康检查地址不一致**：vite 默认绑 `localhost`（本机解析到 `::1`），
   而检查用的是 `127.0.0.1` → 首跑直接 `preview did not come up`。加 `--host 127.0.0.1` 后两者一致。
   （AGENTS.md 已记"工具报 unknown 可能是假失败"——这次是**真失败但原因在检查侧**，属同类教训的镜像。）
3. **`_c34` 的 F10 首跑 8 条 FAIL**：正则写成 `"文件名"`（含前引号），而 router 里是 `"../views/文件名"`，
   前引号永远匹配不上 → 去掉前引号。教训：**断言失败先怀疑断言**，这批两次都如此。
