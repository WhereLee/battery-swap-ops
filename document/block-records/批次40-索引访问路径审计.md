# 批次40 · 索引与访问路径审计（把"没做全量审计"变成服务器侧实测）

> 日期：2026-09-19 ｜ 性质：**补一个从未做过的验证维度**（此前 `选型卡与表设计依据.md` 自己写着"本项目没做索引全量审计"）
> 结论：用 MySQL 自己的 `performance_schema` 逐语句统计做审计，抓到 **1 处由本仓库自己的迁移造成的读路径退化**
> 与 **2 处缺失访问路径**；三处修复后以"打流量 → 读计数器差值"的方式**因果证明**（不是"EXPLAIN 看起来好了"）。
> 新增门禁 `scripts/verify/batch40/_c39_index_audit.ps1`（14/14 PASS）。

## 一、为什么做

单测、契约门禁、浏览器门禁、覆盖率、SpotBugs 全绿，**都不能发现"少了一个索引"**：
查询结果完全正确、只是慢。而"表索引"在中小厂面经里是高频题（9 篇命中）。
此前的文档口径是"每个索引都能指向一条真实查询"——那只回答了"为什么有这个索引"，
没回答"**真实查询有没有访问路径**"。本批把这个方向补上。

## 二、方法：不靠读代码猜，用服务器侧的实测统计

```sql
-- 真实流量统计（MySQL 自己记录的每类语句：执行次数、是否用到索引、扫了多少行）
SELECT DIGEST_TEXT, COUNT_STAR, SUM_NO_INDEX_USED, SUM_ROWS_EXAMINED, SUM_ROWS_SENT,
       FIRST_SEEN, LAST_SEEN
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = 'swap_ops' AND SUM_NO_INDEX_USED > 0;
```

**关键设计：不要直接拿计数器当判据。** 它是"自 MySQL 启动以来累计"，含修复前的历史，
所以本批分三层取证据：

| 层 | 判据 | 为什么需要 |
|---|---|---|
| ① 审计 | `SUM_NO_INDEX_USED > 0` 的语句 × 表行数 × 每次扫多少行 | 找出**值得看**的对象；用阈值把"10 行小表全扫"（正常）与"5,000 行表全扫"（缺陷）分开 |
| ② 计划 | `EXPLAIN` 当前计划：`type != ALL` 且 `key != NULL`；外加**索引前导列**的 schema 断言 | 状态式判据，可重复、不受历史计数污染；前导列断言正是这次缺陷的形状 |
| ③ 因果 | 读计数器 → **打真实 HTTP 流量** → 再读 → 断言"执行数涨了、无索引次数没涨、每次扫的行数塌到约等于返回行数" | 证明修复**生效**，而不是"我加了个索引" |

## 三、抓到的问题（三处，全部实测）

### 1. `payment_record.order_id` 的访问路径消失了（**本仓库自己的迁移造成**）

| 项 | 数值 |
|---|---|
| 语句 | `SELECT ... FROM payment_record WHERE ( order_id = ? )` |
| 实测 | 54,647 次执行，其中 **5,068 次无索引**，累计扫 **40,641,477 行**，只返回 6,629 行 |
| 每次 | 全表扫 ~8,090 行换 1 行（表 7,875 行） |
| EXPLAIN（修前） | `type=ALL`、`possible_keys=NULL`、`key=NULL`、`rows=7875` |
| 机制 | db/18（批次35 / AUD-6）为修"第二笔部分退款台账漏记"删掉了 `uk_order_type(order_id, payment_type)`——**那个唯一键同时是 `WHERE order_id = ?` 的唯一访问路径** |
| 旁证 | 同形状但走索引的 digest（`no_idx=0`，14,240 次）`LAST_SEEN = 2026-09-17 10:26`，此后只有全表扫那一支在跑 |
| 修法 | `db/19`：补**非唯一** `idx_order_id(order_id)`（不用唯一键——退款多笔语义已由 `refund_record` 唯一键与 `uk_trade_no` 保证，幂等闸已收窄到 `uk_payment_idem`；重建唯一键等于退回 AUD-6） |

**这是一条有代表性的教训**：一个索引担两个职责（唯一性 + 可访问性）时，
按其中一个职责删掉它，另一个职责会被**静默**破坏——没有测试会红。

### 2. 告警"全部"页签只能全表排序（用户点一下就到）

| 项 | 数值 |
|---|---|
| 语句 | `SELECT ... FROM alarm ORDER BY create_time DESC LIMIT ?` |
| 实测 | 8 次执行全无索引、每次扫 4,032 行；另有 2 次无 LIMIT 形态每次扫 7,708 行 |
| EXPLAIN（修前） | `type=ALL`、`possible_keys=NULL`、`Extra=Using filesort` |
| 机制 | `alarm` 上两个索引（`idx_alarm_handled_time(handled, create_time)`、`idx_device_type_time(device_no, alarm_type, handled, create_time)`）**都不以 `create_time` 打头**；带 `handled` 过滤时走前者且是 `Backward index scan; Using index`（覆盖，很好），但管理台"全部"页签传 `handled=undefined` ⇒ 条件消失 ⇒ 只剩 ORDER BY ⇒ 全表 + filesort |
| 修法 | `db/19`：补 `idx_alarm_create_time(create_time)`；**代价如实记录**：alarm 是持续写入表，多维护一个索引 |

### 3. `swap_order` 对账计数窗口没有可用索引

| 项 | 数值 |
|---|---|
| 语句 | `SELECT COUNT(*) FROM swap_order WHERE ( status = ? AND complete_time >= ? )` |
| 实测 | 32 次执行中 30 次无索引、每次扫 5,296 行（表 5,177 行） |
| EXPLAIN（修前） | `type=ALL`、`possible_keys=idx_order_status` 但 `key=NULL`（status 选择性太低，优化器判断"走索引再回表"更贵——**这个判断是对的**） |
| 修法 | `db/19`：补 `idx_status_complete(status, complete_time)` |

**这条要如实说清一个反直觉点**：在本机数据分布下（`status=5` 占 5,681/5,842 ≈ 97%），
优化器**仍然不选**这个复合索引——因为"状态=5 且完成时间≥很久以前"没有任何可收窄的区间。
它是在**有界时间窗**（对账任务真正的形态）下才被选中：

```
EXPLAIN SELECT COUNT(*) FROM swap_order WHERE status = 5 AND complete_time >= <最近 1 小时>
→ type=range  key=idx_status_complete  rows=2  Extra=Using index   （覆盖索引）
```

所以门禁断言的是**有界窗口那个形态**，而不是本机退化的形态；这条差异写进了脚本注释与本文档。

## 四、修复的因果证明（不是"看起来好了"）

门禁自己打流量、自己读差值：

```
W1 payment_record WHERE order_id = ?:   drove 20/20 requests;
   delta execs=+20  no_index_used=+0  rows_examined=+20   (1 行/次；修前 ~8,090)
W2 alarm 无 handled 过滤（全部页签）:    drove 20/20 requests;
   delta execs=+20  no_index_used=+0  rows_examined=+400  (20 行/次；修前 ~4,032)
=== C39 summary: PASS=14 FAIL=0 ===   GATE-INDEX PASS
```

`rows_examined` 的增量分别等于"返回行数"和"LIMIT 行数"——这是索引生效的直接特征
（修复前每次都等于整表行数）。

## 五、审计同时给出"不是问题"的结论（避免把正常全扫当缺陷）

| 对象 | 实测 | 判定 |
|---|---|---|
| `cabinet` 全扫 | 27,316 次、每次 10.6 行 | **正常**：表只有 10 行（柜子数量固定） |
| `battery` 全扫 | 272 次、每次 61 行 | 正常：61 行小表 |
| `plan` / `user_coupon` / `cell` 全扫 | 每次几十~几百行 | 正常：小表；`cell` 的 `battery_id IS NOT NULL` 扫描随柜数增长，非热点 |
| `alarm WHERE handled = ?`（未处理/已处理页签） | 1,745 次中仅 45 次无索引 | 正常：走 `idx_alarm_handled_time` 的覆盖索引反向扫描 |
| `swap_order ORDER BY create_time DESC LIMIT n`（无过滤的订单分页） | 57 次、每次约 19 行 | 正常：`idx_order_create_time` 存在，优化器在 5.8K 行表上选全扫是合理的代价判断 |

同时新增一条**事实项**：审计会把"FROM 子句落在 digest 截断窗口之外"的语句标成
`unclassified` 而不是默默当良性——"看不出"与"没问题"必须分开，否则审计会骗自己。

## 七、边界与如实申报

1. **审计口径依赖 digests 表**：`events_statements_history_long` 默认关闭（本机 `ENABLED=NO`），
   所以拿不到"带真实参数值的完整 SQL"；本批用 digest 形状 + `EXPLAIN` + 流量差值代替，
   **没有**开 `general_log`、**没有**改服务器变量。要定位"某次具体执行的参数"需要开
   `history_long` 或 `general_log`（属配置变更，留待用户决定）。
2. **审计清单取 TOP 15**（按 `SUM_ROWS_EXAMINED` 降序），不是全量 666 条 digest；
   阈值口径（>200 行/次 且 表 >1000 行）写在脚本里可调。
3. **门禁只覆盖 3 类热点路径**（payment_record 两形 + alarm 列表 + swap_order 窗口），
   不是"所有查询都有索引"的证明；新增热点查询时应加进 `$hotPaths`。
4. **未做**：索引冗余度分析（哪些索引可以合并/删除）、写入放大的量化（新增 3 个索引对 INSERT 的影响未测）、
   联合索引列序的最优性证明（当前依据是"谓词 + 排序 + 覆盖"三条经验）。

## 八、补记（同批收口）：无界读审计——把"追查某条语句"换成"守住这一类"

第一轮审计留了一条未归属的语句：`SELECT <全部列> FROM swap_order ORDER BY create_time DESC`
（6 次执行、每次返回 5,832 行、无 `WHERE` 无 `LIMIT`）。**三处搜索都没能定位调用方**：
Java 源码（`orderByDesc(getCreateTime)` 只有 2 处，且都带条件）、`scripts/`、`.local/`。

**处置选择**：对一个**已经停止**的语句继续做考古是错的取舍；正确做法是加一道
**守类**的门禁，让它一旦回来立刻显形、不必再查第二次。新增第 4 段判据：

```
规则：应用 schema 里既无 WHERE 又无 LIMIT 的 SELECT，且每次返回 >500 行 ⇒ 结构上无界
      · 最近 30 分钟内出现过 ⇒ FAIL（正在发生）
      · 更早的 ⇒ INFO（历史）
```

首跑立即报出**两条**（不是一条）：

| 语句 | 次数 | 每次返回 | 最后出现 | 判定 |
|---|---|---|---|---|
| `SELECT <全部列> FROM swap_order ORDER BY create_time DESC` | 6 | 5,832 行 | 2026-09-19 02:01（≈21.8h 前） | 历史 |
| `SELECT <全部列> FROM alarm ORDER BY create_time DESC` | 2 | 3,854 行 | 2026-09-19 02:51（≈20.9h 前） | 历史 |

两条形状一致（全列 + 按时间倒序 + 无界），且最后出现都落在 02:00–03:00 那个窗口——
正是本批之前做容量/压测与演示脚本的时间段。**如实说明**：仍未归属到具体调用方，
当前代码里找不到能产生该形状的路径（`AdminWorkflowViewService` 与 `SwapOrderService.pageOrders`
都带条件，且分页拦截器会补 LIMIT）；合理猜测是当时运行的**负载/诊断脚本或旧 jar**
（批次30 之前的"分页拦截器缺失"正是这个形状），但**这是猜测，不是结论**。
门禁的判据不依赖这个猜测：只要它再次出现且落在 30 分钟窗口内，`_c39` 就会红。

> 这条补记本身也是本轮的方法论收获：**审计发现的价值不只在"修好了什么"，
> 还在于把"需要持续追查的问题"转换成"不需要追查的守类判据"。**

门禁最终：`=== C39 summary: PASS=15 FAIL=0 ===  GATE-INDEX PASS`
（0 条 active 无界读、2 条 historical）。
