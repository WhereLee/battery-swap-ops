## 5. 设计要点与踩坑（根因 → 处置，接手必读）

1. **JMeter keep-alive**：JMX 必须显式 `HTTPSampler.use_keepalive=true` + `implementation=HttpClient4`。否则每请求新建连接 → Windows 动态端口（~14k）耗尽 → `BindException` 假故障。**旧读数 465.5/s 的根因就是这个**（已在 batch16 更正）。
2. **每线程唯一用户**：写路径登录用 `${__longSum(13800000000,${__threadNum})}`。随机用户会让多线程共用人（进行中订单互斥）→ TAKE create 400 级联。
3. **还电后电池不会自动满电**：平台 `BATTERY_IN` 恒置 CHARGING（只有 `SOC_REPORT` 才转 FULL）→ 满电池逐渐枯竭。处置：新增 sim `POST /sim/battery/soc` 模拟 BMS 满电上报，JMX 每轮还电后补一步（`W-SIM-soc`，soc=100）。
4. **定时器语义**：JMeter 线程组级 `ConstantTimer` 作用于**每个请求**（多个定时器叠加）。写路径实际是"单定时器 2300ms = 每步节流"（这也是一次完整脚本 ~8 分钟的主因）；不要按"每轮一次"理解。
5. **定长循环优于 duration 截止**：`ThreadGroup.scheduler=false` + `LoopController.loops=8` + `continue_forever=false`。用 duration 截止会在停止瞬间留"在途单"，污染对账基线。
6. **sim 与 DB 双重置**：平台 `POST /api/dev/device/reset` 只重置 DB；sim 内存态（仓/电池/seq/bootId）需 `POST /sim/reset`（批次15 新增，轮换 bootId + 重建柜）。缺一不可。
7. **JVM 故事脚本执行怪癖**：`_p03e_jvm_story.ps1` 内部用 `cmd /c` 调 .bat 起进程时，本机 opencode shell 包装会因句柄继承等待/被杀（子进程其实已起）。本次是"按脚本同款步骤**手工分步执行**"产出证据；若要脚本一键化需改后台起法（`start` 分离/new console）。
8. **GC log 参数格式**：`-Xlog:gc:file="C:\...\gc.log":time,uptime` 必须带引号；写成裸 `file=C:\...` 会解析失败并生成垃圾文件 `,uptime`。
9. **jstat 路径**：不在 PATH 时必须全路径 `D:\java\bin\jstat.exe`。
10. **对账门禁设计取舍**：脚本硬门禁 = 资金类检查（completed-has-payment / settlement-conservation / statement-consistency / settlement-coverage / arrears-integrity）+ 本档 SQL 断言（零超卖/恰一次）；非资金类（cell-battery 等）差异**WARN + follow-up**，不阻断（原因见 §6.2）。
11. **warmup 段容错**：预热紧接重置运行，残留状态可能致错；脚本将 warmup 的错误计为"容忍/丢弃"（方法论上预热段本就不入结论）。
12. **大 JTL 解析耗时**：单档 jtl 12~23MB，PowerShell `Import-Csv` + 排序解析数秒到十几秒；证据原件放 `diag-archive/` 不入 git。

### 6.2 台账孤占（follow-up，非资金类）
- 现象：压测后偶发 2 个仓 `cell.battery_id` 指向的电池呈 `CHARGING + cellId=null`（引用悬挂）；对账 `cell-battery-consistency` 可检出。
- 重要性：**不动钱、不动库存计数**——零超卖与计费恰一次均通过；属"派生状态未对齐事实"类噪音。
- 已观察两次（cells 4/5，SWAP-C-001），与 sim 异步事件（single-thread executor）+ 平台并发事件处理 + 定时重启/复位时序的交互有关。
- 建议排查方向：给 sim 的 `devTake/devPut/devSoc` 增加"事件送达确认"或在 JMX 中对 SIM 步骤后加**单次状态轮询**（等订单到终态再进下一步），是最小成本的收敛手段。

### 6.3 其他
- JVM 故事脚本一键化（§5.7）。
- JVM 故事未制造 OOM（96m 被 CGC 兜住）；如需更强信号可降到 ~64m（不必要）。
- 同机压测口径：读/写/JVM 全部同机（JMeter 与平台互抢资源），数字用于**相对对比与余量判断**，不是绝对容量。
