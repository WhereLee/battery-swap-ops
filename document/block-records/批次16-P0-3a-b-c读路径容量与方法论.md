## 1. 结论（先给数字）

| 档位（20/50/100 线程） | 吞吐 | avg / p95 / p99 | 错误 |
|---|---|---|---|
| 20 | **3,230.3/s** | 6ms / 15ms / 16ms | 0 |
| 50 | **3,305.7/s** | 14ms / 41ms / 48ms | 0 |
| 100 | **3,525.4/s** | 27ms / 78ms / 84ms | 0 |

- 条件：JDK17 / `-Xms512m -Xmx512m` / 限流关 / JMeter+平台+MySQL+Redis **同机**（保守口径）；
  预热 75s（丢弃）+ 每档 195s 稳态（含 15s ramp）；登录每线程一次（稳态只计读接口）。
- 饱和判断：20 线程已近饱和（3,230/s），50→100 吞吐不增、延迟线性上升 → 饱和点 ≈ 3.3k~3.5k QPS（同机口径）。

## 2. 关键修正：旧 465.5/s 是压测端假象

- 现象：首轮参数化复跑出现 60~80% 错误，`responseCode = Non HTTP response code: java.net.BindException`
  （`Address already in use: connect`），且 `TIME_WAIT` 6,122 个、Windows 动态端口仅 13,953 个。
- 根因：**JMeter 未开 keep-alive**（JMX 缺 `HTTPSampler.use_keepalive`）+ 每轮循环重新登录，
  每请求新建连接 → 压测端 ephemeral 端口耗尽；**服务端 keep-alive 正常**（实测响应 `Connection: keep-alive`）。
- 修正后：50 线程 25s 冒烟 **3,696/s、0 错误**；完整三档 0 错误。
- 口径修正：`batch7` 的 465.5/s（5.156s 窗口、每轮登录、无 keep-alive）不作容量结论；
  README 与 `capacity-model.md` 已更新，历史 `batch7/_load_out.txt` 保留作过程证据。

## 3. 资源画像（每档快照差分）

- **缓存**：稳态 20 线程 L1 命中 +62.97 万（`plans`/`stations` 两个列表接口几乎全部命中 L1；L2 命中仅 33）；
  `/user/plans` 平均 1ms、`/user/wallet` 3ms（未缓存，走 DB）、`/user/stations` 13~70ms（缓存重建 + 序列化）。
- **MySQL**：每档 Queries 增量 ≈190 万（20 线程档）/195s ≈ 9.7k QPS；`Threads_connected≈21`（池上限 20）；
  `Innodb_row_lock_waits` 全程无新增。
- **Redis**：命令量高（每请求 token 校验 + 看护/延迟/扫描任务轮询）；`instantaneous_ops_per_sec` 采样 1.9k~3.1k。
- **GC**：512m 定堆，19 次/分钟量级（每档约 360 次)、单档总暂停 ~0.65s、最大 9.6ms；无 Full GC。
- 瓶颈线索：`stations` 延迟随并发上升最明显；Redis 与 MySQL 池为共享资源，同机口径下互相争抢。

## 4. 业务量级换算（摘要，全文见 `document/knowledge/capacity-model.md`）
