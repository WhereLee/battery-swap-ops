## 三、验证：为什么"16/16 PASS"还不够

`probe-web.sh` 只能证明"HTTP 层面这个站点是活的"。**旧的坏包同样会返回 200、同样引用带 hash 的资产**，
所以它无法区分"修复后的产物"与"批次31 的产物"。补三重指纹校验（只读）：

| 判据 | 实测 |
|---|---|
| ① 资产指纹 | 线上 `index.html` 引用 `index-txfpfQmx.css` = **本地批次41 构建的同名文件**（旧包是 `index-BHCRSDmS.css`）；`index.html` sha256 `8c23094b842b4c68…` |
| ② 令牌值 | 线上 CSS 含 `5d6269`（次级文字）/`6f747c`（占位符）/`1668c1`（主色）各 1 次 |
| ③ **覆盖顺序** | 厂商默认在 byte **1997/3508/3542**，我方覆盖在 byte **362041/362076/362113** ⇒ `ORDER OK`。**这条才是修复生效的充要条件**——CSS 优先级打平时靠"后出现者胜"，顺序反了整个修复静默失效（与 `global.css` 里的注释、`_c38` 门禁同一件事） |

## 四、边界与如实申报

1. **没有在云上跑 `_c35`/`_c38` 浏览器门禁**：它们要真实登录，而云上管理员口令是**服务器本地生成**（在 `swap.env` 里），
   刻意不出服务器、也不进本地。因此云上的渲染正确性证据是"**产物指纹**（同 hash 的 CSS）+ 覆盖顺序 + 16 项 HTTP 冒烟"，
   **不是**"在云上量过 DOM"。要在云上跑浏览器门禁，需要先决定"是否把云上管理端口令取到本地"（属凭据策略，留给用户）。
2. **`assets/` 目录权限导致的假计数**在脚本注释里已有记录，本轮再次复现（`find` 报 Permission denied），
   修法仍是 `sudo find`；本轮只读排查脚本因此把 `assets` 列表判为"看不到"而非"不存在"。
3. **ufw 仍未改动（仅 22）**：本次没有触碰暴露面，演示路径仍是 `ssh -L 80:127.0.0.1:80`；
   公网放行依旧是用户拍板项。
4. **云上仍然是 HTTP 通道**（未上 RocketMQ，内存成本考虑），与 `document/knowledge/` 的既有申报一致。
5. **本次 jar 与上次功能等价**（批次37-41 未改 Java），重传 89MB 的价值在于"部署即最终代码"这句话可由 hash 复述，
   而不是省一次上传；如实记录这个取舍。
6. **临时脚本已删**（连接文档要求）：本机 `.local/check-cloud-*.sh`、`verify-cloud-*.sh` 仅作排查留档（`.local` 不入 git），
   服务器 `/tmp` 下的三个脚本已清理。
