## 三、实机联调抓出的存量缺陷：分页拦截器缺失（本批最重要产出）

**发现路径**：`vue-tsc` 与 `vite build` 全绿后，用浏览器实机登录 → 告警页显示"共 0 条"却渲染了数百行。

**实测取证**（`.local/probe-page.ps1`，修复前）：

| 端点 | 请求 | 修复前 | 修复后 |
|---|---|---|---|
| `/admin/view/alarm` | `limit=5` | `total=0`，返回 **3854 行** | `total=3854`，返回 5 行 |
| `/admin/view/alarm` | `page=2&limit=5` | `total=0`，返回 3854 行（与第 1 页相同） | `total=3854`，5 行，offset 生效 |
| `/admin/view/work-order` | `limit=5` | `total=0`，17 行全表 | `total=17`，5 行 |
| `/admin/work-order`（域，对照组） | `limit=5` | `total=0`，17 行全表 | `total=17`，5 行 |

**根因**：`selectPage()` 只声明分页意图，`LIMIT`/`COUNT` 由 `PaginationInnerInterceptor` 在执行期注入；
本项目**从未注册该拦截器**，且不抛异常、HTTP 照常 200、`page`/`limit` 字段照常回显 → 静默全表。

**影响面**：openapi.json 里 **13 个分页端点 / 10 处 `selectPage`** 全部受影响。按本地库实测行数，
修复前每次列表请求分别在序列化：`op-log` **21491 行**、`order` **5842 行**、`view/alarm` **3856 行**、`cell` 120 行。
审计日志与订单只增不减 ⇒ **响应体随运行时间线性膨胀**，属拖库级缺陷，非体验问题。

**为什么四层防线全都没抓到**：单测 mock `selectPage`（不经 SQL 链）；剧本只断言 `code=0` + 字段存在 +
业务值（**从未断言 `rows <= limit`**），且当时多数表只有十几行，全表返回也"看起来对"；SpotBugs 看不见运行时装配；
jacoco 里那行**是被执行的**，只是语义不对。→ 详见 `document/pitfalls/mp-pagination-interceptor-missing.md`。

**处置**：新增 `config/MybatisPlusConfig.java`——`PaginationInnerInterceptor(DbType.MYSQL)` +
`maxLimit=PageParams.MAX_LIMIT(200)` + `overflow=false`，并按官方顺序追加 `BlockAttackInnerInterceptor`
（加之前已核实全仓 `update/delete` 均带 `.eq(...)`，无合法全表写）。
`maxLimit` 是必要的第二道防线：`SwapOrderService`/`AssetAdminService` 直接 `new Page<>(pageNum,size)`，**绕过了 `PageParams`**。

**同类风险自查**：`@Version`/`@TableLogic`/`@EnumValue`/多租户同属"声明了但需拦截器才生效"——全仓 grep **零匹配**
（乐观锁一律走显式 CAS 条件 UPDATE）。故分页是唯一一处，不存在第二个静默失效点。

**回归网（两层，缺一不可）**：
1. `MybatisPlusConfigTest`（7 测，`MybatisPlusConfig` **8/8 行覆盖**）：装配存在性 + 方言 + `maxLimit==PageParams.MAX_LIMIT` +
   `overflow=false` + 防全表写存在 + 顺序正确。**这是 CI 里唯一能挡住回归的一层（CI 不连 DB）**。
2. `_c33_paging.ps1`：13 个端点 × 5 类断言（`limit` 生效 / `total>=rows` / **不出现"有行但 total=0"的静默特征** /
   第 2 页首行 ≠ 第 1 页 / `limit=100000` 封顶 200）+ 前端契约 3 项 ⇒ **81 PASS / 0 FAIL / 1 SKIP**
   （SKIP=`/admin/transfer` 表为空、行数不足以证明 offset，如实标注不硬凑）。

## 四、关键决策与如实申报

1. **路由守卫用静态表 + `beforeEach` 校验，未用方案 §4.3 写的 `addRoute` 动态注入**：路由表本就是静态的，
   `addRoute` 只增加首跳时序复杂度（需 `next({...to, replace:true})`）而不增加安全性——判权集中在同一处守卫。
   属实现细节偏离，安全性等价，此处申报。
2. **看板"周转率"显示为 `0.00` 次/块而非百分比**：后端口径是 `今日完成单 / 在役电池`，标成百分比会误导；
   卡片文案已写明口径。
3. **Element Plus 全量引入 + `manualChunks`，chunk 体积警告故意不掩盖**：拆包后主入口
   **1117.67 kB → 64.43 kB**（gzip 25.23），`vue` 111.95 kB，`element` 940.44 kB（gzip 302.63）。
   按需引入需再加两个构建插件、且命令式组件（`ElMessage`/`ElMessageBox`）样式易漏；内网管理台对首屏不敏感，
   收益不兑现。提高 `chunkSizeWarningLimit` 属"把信号调静音"，不做。
4. **告警类型 `alarmType` 保留英文枚举，Agent `actionType` 加中文映射**：前者有 `content` 字段承载中文描述、
   且运维按类型码检索；后者是白名单（仅 4 值、明确封闭），映射收益确定。中文标签 + tooltip 保留原文（契约值）。
5. **`onMounted` 预加载两个 Tab 数据**：多一次请求换 Tab 切换即时响应；建议单是 S6 Agent 闭环的核心入口，值得。

## 六、过程中的问题（含我自身的操作失误）

1. **动作端点参数形态逐个核实**（避免"点了就 400"）：`from-alarm` 的 `severity`、`reject` 的 `remark` 均为
   `@RequestParam`（走 query 而非 body）；`handle`/`confirm` 无参；`Idempotency-Key` 头**只作用于 `propose`**，
   confirm/reject 不需要（其幂等由 CAS 保证）。另核实 `from-alarm` 的权限码是 `admin:work-order:manage`
   （不是 `admin:alarm:handle`），按钮 `v-access` 按此配。
2. **后台跑 `mvn clean verify` 期间改了源文件 ⇒ jacoco class-id 不匹配**（我的操作失误）：
   首次 verify 报 `Execution data for class .../MybatisPlusConfig does not match`，该类被记为 0/8 行覆盖，
   导致 server covered 行数与批次29 完全相同（5400，本该 +8）。**教训：Maven 在跑时不得编辑同模块源码**；
   重跑一次干净 verify 后为 5408/7560、该类 8/8 覆盖、警告消失。
   （同类工具纪律已记录：PS 管道接常驻 JVM 会阻塞。）
3. **`npm create vite` 卡死**：`| Select-Object -Last 12` 的缓冲吞掉交互提示并阻塞 ⇒ 改为完全手写脚手架
   （src 下 18 个 + 根部 5 个配置/入口文件，共 23 手写；`node_modules`/`dist`/`schema.d.ts`/`*.log` 均 gitignored，
   已用 `git add --dry-run` 核实入仓仅 24 个文件）。
4. **`noUnusedLocals` 抓到死变量**：`AlarmView` 里 `suggestionLoaded` 声明后未用（预加载策略改动后遗留）→ 删除。
5. **Element Plus 弃用告警**：`el-pagination` 的 `small` 属性 → 改 `size="small"`，消除每次加载的 2 条 warn。
6. **el-tabs 两个 pane 同时在 DOM**：未做可见性作用域隔离时按全表 `tr` 计数会把 20 行读成 35 行
   （自动化脚本需注意）；非缺陷，未改。
7. **端口口径纠正**：`AGENTS.md` 写"平台 8200"，实际 `application.yml` 为 **8400**（`context-path: /api`）。
   proxy 按 8400 配置正确；工作区文档待同步。
