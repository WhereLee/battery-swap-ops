# 批次34 · 月卡日限落地（dailyLimitTimes）

> 日期：2026-09-19 ｜ 性质：**独立审计驱动的缺口补齐**（AUD-4）
> 结论：S0.1 领域模型声明的 `dailyLimitTimes` 此前**只有建表/表单/校验、从未参与计费**；
> 本批把它接进计费判定，并给出并发下的正确性做法与代价。

## 一、缺口（回源确认）

| 位置 | 现状 |
|---|---|
| `document/plans/S0.1-领域模型.md:53` | Plan 模板声明 `dailyLimitTimes（可空）` —— **设计文档里有** |
| `db/01-swap-schema.sql:77` | `plan.daily_limit_times INT` 建列 |
| `PlanAdminForm` / `PlanEntity` / `PlanService.validatePlanForm` | 表单字段、实体字段、**"日限次需 >0（可空=不限）"的配置校验** |
| `BillingService:87`（修改前） | `// 月卡：有效期内即权益（日限在创建时已校验）` —— **注释不成立**：创建时校验的是配置合法性，不是使用次数 |
| 全仓 | **无任何按日计次的查询或扣减** |

后果：配了"每日 1 次"的月卡当天可以无限次换电 → 套餐权益超额发放（收入损失），且运营侧看不到任何异常。

**判定**：这是"设计声明了但实现漏了"，不是"有意留后"（若有意留后，S0.1 会标注"v1 仅记录"，
而它没有；同类"v1 仅记录"的写法见 `agent.settlementCycle`）。故按缺口补齐处理。

## 二、实现

```java
// BillingService.charge 的月卡分支
if (plan.getRemainingTimes() == null) {
    planCharged = !monthlyDailyLimitReached(plan, completeTime);   // 日限用满 → 回落余额计费
} else {
    planCharged = planService.deductTimes(plan.getId());           // 次卡：CAS 扣次
}
```

`monthlyDailyLimitReached` 的四个要点（都写进了代码注释）：

1. **口径**：读套餐模板 `daily_limit_times`（空/≤0＝不限）；按**自然日**（`ZoneId.systemDefault()`，
   与看板"今日完成单"同一口径）统计；
2. **先加行锁再数**：`planService.lockUserPlan(userPlanId)` = `SELECT ... FOR UPDATE`。
   月卡日限是"数今日单量 → 决定放不放行"的先检查后动作；同一用户在两台柜上并发的两笔完成事件
   是两个事务，互相看不见对方未提交的行，会各自放行 ⇒ 日限被突破。行锁把这段判定变成同一张卡的临界区。
   **代价**：月卡订单的计费路径多一次行锁（只锁同一张卡，不影响其他用户）。
3. **只数 `payType=PLAN` 的单**：日限约束的是"月卡权益"；被限流后回落余额的单不该再占额度，
   否则一次超限会连锁吃掉当天剩余次数；
4. **超限的后果是"回落常规计费"而不是拒单**：换电服务已经交付（事件是事实源），计费只能选通道；
   余额不足自然走既有的欠费化路径（S7 韧性补丁 G1），不需要新机制。

新增 `PlanService.findPlan(Long)`（读模板）与 `PlanService.lockUserPlan(Long)`（行锁）。

## 四、边界与如实申报

1. **没有实机剧本**：跑通"月卡 + 跨日多次换电"需要造跨自然日数据或改系统时钟，成本高于收益；
   本批以单测覆盖判定分支，并用既有 `_g2/_g3` 保证正常计费链路没被改坏。这是**证据强度的取舍，已申报**。
2. **行锁只在本项目的事务边界内有效**：计费在事件事务内执行（`DeviceEventService.handle`），
   所以 `FOR UPDATE` 能真正串行化；若将来计费被移出事务，这条保证会静默失效
   ——与批次32 的教训同类，故在注释里写明依赖前提。
3. **仍然是"近似严格"**：若同一张卡在同一毫秒内被两个**不同用户**（不可能，卡属于用户）或
   跨实例并发使用，行锁在数据库层仍然成立（锁是 DB 的，不是进程内的），所以这里不是近似而是严格。
4. 本批只改月卡分支，未改次卡/余额/押金/超时费逻辑。
