# 批次43 · 门禁可红性实证（"我怎么知道门禁不是摆设"）

> 日期：2026-09-20 ｜ 性质：**验证手段自身的验证**（negative control）
> 结论：给两道新门禁各做了一次"故意注入缺陷 → 必须判红 → 还原 → 必须判绿"的实证：
> `_c38` 界面门禁（4 类缺陷全部被检出，10/10）与 `_c39` 索引审计（丢掉访问路径后精确复现批次40 的缺陷签名，9/9）。
> **并且负控立刻发现了一处门禁盲区**——这是我修完两轮都没意识到的问题。

## 一、为什么做

项目里现有的门禁几乎**只被观察到绿色**。而"从没红过的门禁"是关于作者乐观程度的陈述，不是关于系统的陈述——
仓库自己已经吃过一次亏：`_c35_out.txt` 写着 31/31，而同批脚本只跑 25 项检查
（`document/pitfalls/check-coverage-lost-in-refactor.md`）。项目对两道 CI 门禁有过"可红性实证"的做法，
本批把同样的纪律推广到新门禁上。

**设计要点**：负控必须**用门禁自己的判据代码**，否则"负控通过"什么也证明不了。
为此把 `_c38_ui_probe.mjs` 改成可导入（`main()` 加直接执行判断 + `export { probeExpression, TAG_CONTRAST_MIN }`），
负控 `import` 同一份 `probeExpression`——不复制、不重写。

## 二、界面门禁负控（`_c40_ui_negative_control.ps1`）

对同一页面先测"干净基线"（该判据必须为假），再注入一类缺陷，再测（该判据必须为真）：

| 注入 | 手段 | 干净基线 | 注入后 |
|---|---|---|---|
| C1 标签对比度 | `--el-tag-text-color: #eeeeee` | 0 个标签低于 4.5:1 | **70 个**，最差 **1.05:1** |
| C2 单元格裁切 | 首列 `.cell` 限宽 40px | 0 个裁切 | **20 个** |
| C3 页面横向溢出 | 插入 3000px 宽块 | `false` | **`true`** |
| C4 表头错列 | 表头整体右移 30px | 0 列错位 | **11 列** |

```
=== C40 summary: PASS=10 FAIL=0 ===   GATE-NEGCTL PASS
（含最后一条：移除全部注入后页面重新测得干净 —— 证明探针是"对注入反应"，而不是"一旦脏了就粘住"）
```

## 三、负控立刻抓到一处门禁盲区（本批最有价值的发现）

**C4 首跑没有红**：注入了 `th .cell{ transform: translateX(30px) }`，而门禁报告"0 列错位"。
原因：`getBoundingClientRect()` 作用在 `<th>` 上，**子元素上的 transform 不会移动 `<th>` 的盒子**，
于是"表头文字被画到别人列上"这种形态**完全躲过了检查**——而这项检查的由来，
正是视觉模型两次抱怨"表头整体错位"；也就是说：**它当时能证明"没错位"，但证明不了"文字没跑到别处"**。

修法（两处，缺一不可）：
1. **判据加强**：逐列同时比较**外层盒**（`th` vs `td`）与**内层 `.cell` 盒**（`deltaCellLeft`），
   门禁对两者任一超差都判错位；
2. **注入改成布局级**（`th{transform}`），因为原注入的形态在真实页面里不存在（应用不用 transform 排列表头），
   负控要复现的是**真实缺陷形状**。

加强后复跑：负控 C4 检出 **11 列**；真实页面门禁依然 **`0 misaligned`**（89 列 `deltaLeft=0 / deltaCellLeft=0`）——
**加强判据没有带来假阳性**，这一点必须回测，否则"为了让它能红"可能只是把它变敏感了。

## 六、边界与如实申报

1. **负控只覆盖静态渲染类缺陷**：对比度/裁切/溢出/错列。**不覆盖**弹窗作用域为空、hover/focus 态、
   `el-message` 与表单校验红字（后三者本来就不在门禁覆盖内）。
2. **批次41 记录的"弹窗作用域可能为空导致假绿"已在本批 §七 修掉**：`_c38` 新增"作用域非空"自检
   （`scopeElements > 0`），并给它配了负控 C5（指向空 div 必须被判空作用域）。**但作用域非空只是必要条件**：
   指到一个"非空但无关"的子树仍会报绿，要再进一步需要"作用域指纹"，列为后续。
3. **索引负控只针对 `idx_order_id` 一条访问路径**：其余两条（`idx_alarm_create_time`、`idx_status_complete`）
   的失败模式同型，未逐条做负控（成本/收益考虑，如实记录）。
4. **负控是本地脚本、不进 CI**：它需要有平台在跑与可写数据库；CI 里跑的是 `_c38`/`_c39` 的正向门禁。
5. **负控注入不落盘**：只在一次性浏览器 profile 里往页面注入 `<style>`/元素，跑完即随进程销毁；
   **不改应用源码、不改构建产物、不改数据**（索引那条除外，且立刻还原并自证）。

## 七、补记（同批收口）：堵住"作用域为空 ⇒ 零问题 ⇒ 看起来全绿"

批次41 与批次43 §六.2 两次申报过同一个风险：**探针按表达式解析弹窗作用域，表达式写错就会去测一个空子树，
而所有字段都是"问题计数"，于是全部返回 0 —— 与"干净页面"完全同形**。这是门禁最危险的一种形态：
它会持续报绿，且没有任何征兆。本批把它堵掉。

**修法（两层）**：

1. **判据自检**：`probeExpression` 的返回值新增 `scopeElements`（量到了多少个元素：标签样本 + 文字样本 +
   对齐列 + 裁切格 + 表格 + 空列）。门禁对**每个页面作用域与每个弹窗作用域**都断言 `scopeElements > 0`，
   为 0 判 FAIL；汇总行 `every measurement scope contained elements (N empty)` 也计入硬失败。
2. **给自检本身做负控（C5）**：新建一个空 `div`，把作用域表达式指向它，**必须**被判为"空作用域"。
   没有这一条，`scopeElements` 自检就只是一句没被验证过的断言——而这正是本批的主题。

```
--- C5 empty measurement scope on /dashboard ---
INFO  baseline (no injection): scopeElements=22
INFO  after injection:         scopeElements=0
PASS  C5 empty measurement scope: injected defect is DETECTED (scopeElements=0)
=== C40 summary: PASS=12 FAIL=0 ===   GATE-NEGCTL PASS
```

真实门禁复跑（10 页各报实际量到的元素数，弹窗亦然）：

```
PASS  measurement scope is non-empty (22/26/35/37/44/70/80/90/93/111 elements measured ...)
PASS  every measurement scope contained elements (0 empty)
=== C38 summary: pages=10 dialogs=1 hardFailures=0 ===   GATE-UI-PROBE PASS
```

**这一步的意义**：把"我测了"从**布尔假设**变成**可观测事实**。此前报告里只有"发现了几个问题"，
现在同时有"看了多少东西"——只有后者非零，前者的零才有意义。

**仍未覆盖**（保持申报）：作用域非空只是必要条件，不是充分条件——**测错了一个非空但无关的子树**
（例如把作用域指到页面里另一个 `.el-dialog` 包装层）仍会报绿。要再进一步需要"作用域指纹"（例如断言
作用域内必须包含标题文本/表单控件），列为后续。

### 8.1 作用域指纹：把"非空"升级为"是它"

§七 堵掉了"作用域为空 ⇒ 零问题 ⇒ 看起来全绿"，但留下一条：**指到一个非空但无关的子树**仍会报绿。
本批补上层指纹，两条都进硬失败：

- 页面作用域必须包含 `.page-title`（`scopeHasPageTitle`）；
- 弹窗作用域的 `innerText`（前 160 字，`scopeSignature`）必须包含该弹窗自己的标题；
  动态标题用 `titleAny` 容纳（订单弹窗按行数据是"退款"或"冲正"）。

```
PASS  every measurement scope matched its fingerprint (page .page-title missing: 0, dialog title mismatch: 0)
```

**边界**：指纹是"包含标题文本"的子串判断，不是身份判断——理论上仍可构造一个含同样标题的错子树。
它把"测错作用域"从**静默**变成**需要刻意构造**，但没有数学上的排他性，如实记录。

### 8.2 弹窗轮的 SKIP 曾经是覆盖漏洞的伪装

`_c38` 弹窗轮此前稳定输出 `2 measured, 2 skipped`，SKIP 理由统一是"opener absent（`allowedActions` 决定，可能没数据）"。
但"驳回建议单"的入口按钮在**建议单页签**下，而 `/alarm` 默认停在**告警页签**——这不是数据条件，是**少点了一次**。
修法：给每个弹窗加 `preStep`（先点页签），且 preStep 自身失败时用**不同理由**的 SKIP 输出。

修完首跑即量到此前从未进入测量面的驳回弹窗：
`low text 3.08:1 (need 4.5) "0 / 200" span.el-input__count color=rgb(144, 147, 153)`。
（剩余 2 条 SKIP 是退款/分诊按钮，确认属于数据条件。）

### 8.3 计数器：一次"看着改好了其实没生效"的 CSS 特异性事故

Element Plus 用 `--el-color-info`(#909399) 画输入计数器 → 白底 3.08:1。
第一版修法写成 `.el-input__count { color: var(--el-text-color-secondary) }`（特异性 (0,1,0)），
**源码看着对了、门禁仍报 3.08:1**：EP 自己的规则是 `.el-input .el-input__count`（(0,2,0)），
**特异性赢过顺序**——我方规则在构建产物里确实排在后面（byte 361996 vs 180439），照样无效。

修法与自证：
- 选择器对齐 EP 的权重（`.el-input .el-input__count` / `.el-textarea .el-input__count`）→ 实测 0 不达标；
- 超限态 `.is-exceed` 保持"危险色"语义，但换成站点自己的红 `#8f2b2b`，选择器照抄 EP 的 (0,4,0) 形状；
- 产物自证：我方规则在 byte 361980 / 362155，均落在 EP 的 178070 / 180439 / 184206 之后。

坑位单独归档：`document/pitfalls/css-override-loses-to-element-plus-specificity.md`。

### 8.4 新通道：只有"让表单失败"才看得见的一层文字

表单校验红字（`.el-form-item__error`）只在规则失败时存在，所以**无论把已渲染页面扫多少遍都看不到它**——
批次39 扫了 1936 个文字元素、批次41 补了占位符，都没碰到它。

做法（`_c38` 新增"校验态"轮，在登录之前跑）：
1. 打开 `/login`，**空表单直接点登录**：`onSubmit()` 会 `await validate()` 并在失败时提前 return；
2. 断言两件事——**错误文字确实渲染**、且**没有发出任何请求**
   （CDP `Network.requestWillBeSent` 计数 `/admin/auth/login`，实测 `0 login POSTs during the empty submit`）。
   即"我们测的是一个安全状态"是**证据**，不是承诺；
3. 以 `.login-card` 为作用域测量（并带非空 + 指纹自检）。

首跑结果（一次比一次深）：
- 校验红字 `#f56c6c` = **2.90:1** → 修为站点红 `#8f2b2b`（探针实测样例 8.24:1）；
- 顺手发现**登录页提示条文案 2.80:1**：`.el-alert--info.is-light{color:var(--el-color-info)}`——
  批次38 标签那种"用基色当文字色"的写法，在**第三个组件**上重现；
- 因此把 `el-alert` 也按标签同一套色板收口（浅底深字 6.0–7.8:1；深底白字 6.6–8.6:1，均为按 WCAG 公式计算值）。

**为什么此前没被发现**：应用里三个 `el-alert` 全是条件渲染（看板要 STATION 数据范围、订单要退款提示），
而**登录页从来不在 `PAGES` 里**。不是"没人看"，是"没有任何一条路径会去看它"。

### 8.5 变体矩阵：只为登录页那一个变体验证过的修复，是靠运气验证的

`el-alert` 有 5 类 × 明/暗两种效果，真实实例全是条件渲染。于是把**登录页那个真实告警克隆 10 份**
（变体名写进标题文本，失败会自己报名），挂到一次性宿主里，**用门禁自己的 `probeExpression` 测量**：

```
PASS  alert variant matrix rendered (10/10 clones: 5 types x light/dark)
PASS  alert variant matrix measured (10 text elements, one per variant)
PASS  every alert variant is readable (0 below, worst 6:1 (needs 4.5) "success/light")
```

**边界**：这测的是**产物 CSS 的真实级联**（类名就是 EP 打在根元素上的那几个），不是 10 个真实业务弹窗；
它让"五个变体都可读"第一次成为**可检命题**，但不替代真实实例测量。

新增检查若只被观察到绿色，就重复了本批要批判的错误。补两个负控，且**用门禁导出的同一个矩阵构造代码**

### 8.7 顺手补的一条报告纪律：`worstText`

"0 个不达标"本身不含余量信息。本轮给 `probeExpression` 增加 `worstText`（本次测量中比值最低的那个文字元素），
门禁在页面级、校验态、变体矩阵各报一次，并在汇总里报**全轮最紧一处**：

```
INFO  closest call anywhere in this run: 4.7:1 (needs 4.5) "::placeholder \"订单号（模糊）\"" input::placeholder
```

口径同 §七 的 `scopeElements`：**只有知道"看了什么、最紧到什么程度"，"零问题"才有意义**。

### 8.9 边界（更新，替换 §六.1 的旧口径）

1. **仍未测**：hover / focus / disabled 态；`el-message`（瞬时消失，未做暂停与截获）。
2. **"超限计数器"实测不可达**：EP 的 `.is-exceed` 需要 `show-word-limit` 且**不设** `maxlength`，
   本仓库两处都设了 `maxlength`（200）。样式按"防御性一致"改了，但**没有实测证据**——如实申报，不当作已验证。
3. **非文本边界仍不设门禁**（WCAG 1.4.11 已测量 175 处、15 处低于 3:1，口径不变）。
4. **变体矩阵只覆盖 `el-alert`**（见 §8.5 边界）；`el-tag` 是页面真实渲染（270 个，非矩阵）。
5. **索引负控**仍只覆盖 `idx_order_id`（口径不变）。
6. **负控不进 CI**（需平台在跑 + 可写库），CI 跑的是正向门禁。

## 九、云上同步：把"人工比对指纹"升级成部署脚本的硬断言

批次42 的教训是"repo 修好了、演示站点还是坏的"，当时的验证方法是**人工**比对三重指纹
（资产同名 / 令牌值 / 覆盖顺序）。本轮 CSS 又改了（计数器、校验红字、告警文案），于是：
先 rollout 上云，再把那次人工比对**固化成脚本断言**——否则下一个批次还会重演同一幕。

### 9.1 改了什么

| 位置 | 改动 |
|---|---|
| `deploy-web.ps1` | 计算本地 `dist/assets/index-*.css` 的 md5，作为参数传给远端 `rollout-web.sh` |
| `rollout-web.sh`（脚本开头） | **先验后发**：staging 里的 css md5 必须等于传入值，否则 `FATAL` 退出——此时快照/迁移/换 jar/重启**一个都没做** |
| `rollout-web.sh`（step3 之后） | 发布后校验：线上 css 名与 staging 同名、**字节相同**，且 `index.html` 确实引用该资产（防"200 的 HTML + 404 的 bundle"） |

### 9.2 实测证据（真机 rollout）

```
local bundle:    index-DS8f1Y5V.css md5=c82cc305f20a54dc376bc308a86c9c97
staged bundle:   index-DS8f1Y5V.css md5=c82cc305f20a54dc376bc308a86c9c97 expected=c82cc305…
deployed bundle: index-DS8f1Y5V.css md5=c82cc305f20a54dc376bc308a86c9c97
bundle identity verified: index.html -> index-DS8f1Y5V.css, md5 c82cc305…
=== cloud console probe summary: PASS=16 FAIL=0 ===   GATE-CLOUD PASS
```

三方 md5 一致（本地构建 == staging == 线上），比批次42 的"同名 + 令牌 + 顺序"更强。
线上 CSS 里新规则也在（逐条 `grep -c` 均为 1）：`.el-input .el-input__count`、
`.el-form-item__error{color:#8f2b2b`、`.el-alert--info.is-light`；覆盖顺序仍正确
（厂商 `.el-input .el-input__count` byte 180431 < 我方 362256）。

### 9.3 给新断言做负控（同批纪律：新增判据必须有红过的记录）

传一个错误 md5 跑真脚本，断言"拒绝发生在**任何改动之前**"——判据不能只看"退出码非 0"，
要看站点是否被动过：

```
before: css=c82cc305… server_started=Sun 2026-09-20 01:05:19 CST idx_order_id=1
exit=1
FATAL staged css is not the bundle built on the workstation; nothing has been changed
after:  css=c82cc305… server_started=Sun 2026-09-20 01:05:19 CST idx_order_id=1
NEGCTL-DEPLOY PASS: the real assertion refused the payload before any change
```

三个不变量都没变：**线上 CSS 字节**、**服务启动时间**（没被重启）、**库 schema**（迁移没跑）。

首次负控其实"通过"得毫无意义——当时 staging 已被上一次部署清掉，脚本以 `127 not found` 退出，
即"失败原因不是断言"。这与本批 §8.2 的"SKIP 是覆盖漏洞的伪装"是同一类错误，故重做时
把 staging 真实重建、并额外断言**拒绝原因那一行**必须出现。

### 9.4 边界

1. 云上仍未跑 `_c35`/`_c38`（需要真实登录，而云上管理员口令刻意不出服务器）——演示站点只跑
   `probe-web.sh`（16/16，含登录 + 8 个聚合接口 + 限流 + 安全头），**界面级门禁仍是本地实测**。
2. 断言的输入是"本地构建产物"，不是"本地源码"：若忘了 `npm run build`，推出的就是**旧的正确产物**，
   断言会通过（它证明的是"推上去的和构建出来的一致"，不是"构建的是最新源码"）。
   `deploy-web.ps1` 因此只要求 `dist/index.html` 存在，不做源码新鲜度判断——如实记录这个边界。
3. `deploy-web.ps1` 经 PowerShell 包装运行时，ssh 的 stderr 会让包装命令返回 1；**判定用
   `remote rollout exit=` 与 `GATE-CLOUD PASS`，不用包装层退出码**。

**AUD-20 值得单独记一笔**：它是**两路独立审计同时命中**的同一条缺陷（资金路径那路从"幂等闸只按

1. **复核不是走过场**：本轮每条 P0/P1 我都回读源码；并发那路**主动推翻**了另一路对 AUD-7 的判断

4. **"修了"必须能被重新测量**：4 个范围/闸门修复各自带结构或行为断言（`FOR UPDATE` 早于插入、

## 十一、同批第五段：实机探针抓到"一个端点坏了很久"，并把它变成静态守卫

### 11.1 现象

给 dev 端点加本机闸门后做**实机回归**（重启平台 + 逐条打请求），发现 `POST /api/dev/device/reset`
**恒 500**——与我的改动无关：

```
### Error updating database.  Cause: MybatisPlusException: Prohibition of table update operation
### The error may involve com.swapops.server.device.dao.BatteryDao.update
```

`DevResetService` 里有**三条"只有 SET、没有 WHERE"的全表语句**（电池脱仓、钱包重置、套餐重置），
而批次30 给 MyBatis-Plus 挂了 `BlockAttackInnerInterceptor`（防误操作全表 UPDATE/DELETE）——
于是这个被 `_p0_demo`/`_c18`/`_c20`/`_b18`/`_p03` 等多个剧本依赖的联调端点，
**从批次30 起每次必然 500**。同文件里其它全表清理（欠费/券/站内信/结算单）都写了 `.gt(id, 0)`，
唯独这三条漏了：**"加了拦截器"这件事没有回归到所有既有语句上**。

### 11.2 处置（治标 + 治本）

1. **治标**：三条语句各补恒真条件（`.gt(id, 0L)`），并在注释里写明为什么需要它。
2. **治本**：新增静态守卫 `MapperPredicateGuardTest`——扫描 `src/main/java` 里所有
   `LambdaUpdateWrapper`/`LambdaQueryWrapper` 语句块，要求每块至少含一个条件方法；
   否则 `mvn test` 直接红，并打印 `文件:行号 + 语句原文`。这是本仓库既有做法
   （`AdminEndpointGuardTest`、`TransactionalSelfInvocationGuardTest` 同型），代价低、进 CI 每次跑。
   守卫自身带**覆盖率自检**：扫到的语句数必须 > 20，否则"这道守卫就是摆设"。

### 11.3 负控（新守卫同样必须能红）

按本批纪律给守卫做负控：**临时把 `.gt(BatteryEntity::getId, 0L)` 注释掉** → 守卫必须红。
**首跑没红**——因为豁免/谓词判定用的是"块里是否出现 `.gt(`"，而注释掉的 `.gt(...)` 也算命中：
一条**注释掉的 WHERE 当然不是 WHERE**。修法：匹配前先剥行注释与块注释（豁免标记改为在原文上判定），
再跑负控：

```
exit=1（期望红）
Tests run: 1, Failures: 1
com\swapops\server\dev\DevResetService.java:109 -> batteryDao.update(null, new LambdaUpdateWrapper<BatteryEntity>() .set(...) ...);
```

还原后复跑 → 绿。**这是本批第三次"负控反过来暴露判据本身的缺陷"**（前两次：表头错位只比外层盒、
`.el-input__count` 特异性、现在是"注释骗过正则"）。

### 11.5 附带记录（既有映射口径，未改）

用 GET 打 `@PostMapping` 端点时返回的是 **500**（不是 405）：`RRExceptionHandler` 的兜底
