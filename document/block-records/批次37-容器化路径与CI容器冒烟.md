# 批次37 · 容器化路径打通（Dockerfile + CI 容器冒烟）

> 日期：2026-09-19 ｜ 性质：**补齐已知未验证承诺**（P0-4 遗留的 compose 路径）
> 结论：镜像可构建、容器可运行、compose 起中间件即完成全量迁移、容器内外健康与业务请求全通；
> 这条路径**每次 push 都由 CI 真跑一遍**（此前开发机无 Docker，只能靠文档承诺）。

## 一、为什么做

P0-4 的验收里有一条**从未兑现**的承诺：
"有 Docker 的机器按 compose 从零到 `health UP`；README 增'有 Docker：5 分钟起环境'路径"。
当时如实标注为"compose 未本机实测（开发机无 Docker）"。同时调研结论显示"部署/打包/Docker"在中小厂
面经里是**必问项**（命中 10 篇），而"能跑起来的证据"排在有说服力证据的第 1 位。
CI 的 ubuntu runner 自带 Docker —— 这就是验证它的地方。

## 二、交付

| 文件 | 内容 |
|---|---|
| `Dockerfile` | 运行时镜像（非多阶段，理由写在文件头：jar 由 Maven 先构建，builder 阶段只会重复下载依赖）；非 root 用户（uid 10001）；`HEALTHCHECK` 打与 systemd 部署同一个健康端点；`-XX:MaxRAMPercentage=70` 让堆跟容器限额走而不是跟宿主机走；**零密钥烘焙**，全部环境变量注入 |
| `.dockerignore` | 只留 `swap-server/target/*.jar` 需要的东西，排除 `.git`/`.local`/`diag-archive`/`swap-web/node_modules` 等 |
| `scripts/cloud/ci-container-smoke.sh` | CI 内跑：compose 起中间件（`--wait` 等 healthcheck）→ 校验 `swap_ops` 表数 → 构建镜像 → `--network host` 起平台 → 等健康 → 打印 `docker inspect` 的 healthcheck 状态 → 容器外登录并调用 BFF 视图端点；失败时打印容器与中间件日志 |
| `.github/workflows/ci.yml` | 新增 `docker` job（package → 冒烟脚本；失败时上传两侧日志） |
| `README.md` | 新增"容器化（有 Docker 的机器）"三段可复制命令 + 新增"五分钟看到东西（面试现场最短路径）"（起平台→演示脚本→管理台 dev→自动化验收→云上隧道） |

## 四、首跑失败与根因（值得讲的一条）

**首跑（run 35440753236）在 step7 失败**：`FATAL admin login failed`。
排查：容器日志显示 Tomcat 已启动、`/actuator/health` 返回 UP、**DevSeeder 仍在逐柜播种**
（日志里 1→10 号柜"联调种子就绪"逐条刷出），而**引导管理员账号是种子流程的最后一步**——
我的一次性登录与种子赛跑，拿不到 token。

修法：登录改为每 3s 轮询、最多 20 次（1 次/3s 远低于登录限流 5 次/5s），实测**第 2 次**成功。

**教训（已写入脚本注释与本节）**：**健康 ≠ 就绪**。`/actuator/health` 只证明进程与 Web 上下文活着，
不代表业务数据可用；冒烟脚本的等待条件应对齐"业务可用"而不是"端口可连"。
这条对生产同样成立（本项目生产 `swap.dev.enabled=false`，无种子问题，但任何"启动即预热/迁移/回填"的服务都有同类窗口）。

另有一条**正面结论**：compose 的 `./db` → `/docker-entrypoint-initdb.d` 挂载让**全量 19 个迁移脚本在首次启动时自动执行**，
实测建出 **33 张表**——"5 分钟起环境"这句话现在有机器证据，而不是文档承诺。

## 五、边界与如实申报

1. **镜像只跑平台（swap-server）**：`swap-sim`（模拟器）与 `swap-agent` 仍按 `.local/*.bat` 跑。
   容器化的目标是"复现门槛"，不是"把演示全套塞进容器"；要全容器化应再补两个 Dockerfile 与一份 compose（列为可选后续）。
2. **容器冒烟用 `--network host`**（Linux runner 可用）：好处是直连 compose 暴露的 3306/6379 且不需额外网络配置；
   代价是它不验证"容器网络 + 服务名解析"这条更贴近生产的路径。生产（云上）走的是 systemd 而非容器，故此取舍可接受，已申报。
3. **Docker 与云上部署无关**：云上是 systemd + nginx（见《服务器连接文档.md》§十）。容器路径服务于"别人拿到仓库 5 分钟跑起来"。
4. 镜像未做漏洞扫描（Trivy 等），也未指定 digest 固定基础镜像版本（用的是 `17-jre-jammy` 浮动 tag）；
   要上生产私有仓库时应补这两项。
