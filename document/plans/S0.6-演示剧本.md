## 2. 剧本 1（S1 门禁）细则

**前置**：MySQL `swap_ops` 就绪；平台 8400 + 模拟器 8500 已启动；登记 1 站点/1 柜/12 仓/12 电池（含满电）。

**步骤与断言**：
1. 模拟器启动，柜心跳到达 → 平台 `swap:online:{cabinetNo}` 存在（在线）；
2. 管理端/测试接口发起开仓（cellNo=3）→ `command_log` 生成 PENDING（seq=1）；
3. 模拟器执行开门 → 上报 `DOOR_OPENED`（commandSeq=1）；
4. 断言：`command_log` → ARRIVED；`cell` 状态不变（门开不改物理态）；日志含同一 traceId；
5. 重复上报同一事件（同 bootId+eventSeq）→ 序守卫拒绝（幂等）；
6. 模拟器重启（bootId 变化）后再上报 → 接受并重置基线（S3 加"已见代际"加固）。

**证据**：`scripts/verify/batch1/_g1_open_loop.ps1` + `_g1_out.txt`（关键行：command_status、事件计数、拒绝计数）。

## 3. 剧本 2（S2 门禁）细则

1. 用户 A（有效套餐）POST `/api/user/order`（SWAP）→ 返回 orderNo/cellNo/batteryNo；
2. 模拟器按指令开门 → 上报 `BATTERY_OUT`（满电取出）→ 上报 `BATTERY_IN`（亏电放入）→ `DOOR_CLOSED`；
3. 断言：订单 COMPLETED；取出的电池 LOANED 且 holder=A；放入的电池 CHARGING 且 cellId=原仓；
   套餐剩余次数 -1（PaymentRecord 恰 1 条）；
4. 重复投递完成事件 → 订单不二次迁移、扣费不重复（C7 唯一键）。

**证据**：`scripts/verify/batch2/_g1_swap_e2e.ps1` + `_out.txt`。

## 4. 剧本 3（S2 门禁）细则

1. 同柜满电电池（实测种子：每柜 6 满电），20 个用户并发下单（PowerShell 并发脚本）；
2. 断言：成功订单 ≤ 满电库存；每块电池只被一个订单持有；每仓锁定唯一；
   失败请求 400（无可用电池/仓）；无 5xx；
3. 预占超时（模拟不执行开仓）→ 预占释放后，同一电池可被再次分配（S3 前用定时/手动触发释放验证）。

**证据**：`_g2_concurrency.ps1` + `_g2_out.txt`（成功/失败计数、DB 校验 SQL 输出）。

## 5. 剧本 4（S3 门禁）细则

| 场景 | 注入 | 断言 |
|---|---|---|
| 乱序 | 先发 eventSeq=5 再补 3 | 3 被拒（幂等），台账不被回退 |
| 重放 | 重发已接受事件 | 拒绝且无副作用 |
| 跨代际重放 | 重启柜后用旧 bootId 重发 | 拒绝（已见代际集合） |
| 事件丢失 | 丢 `BATTERY_IN` | 超时对账（QUERY_STATE）发现，按实况补记/告警 |
| 指令超时 | 柜不响应开仓 | 重试分层 → 超限告警；预占释放 |
| 离线恢复 | 停模拟器 > TTL | OFFLINE 告警；恢复后心跳关告警 |
| 对账 | 日终对账任务 | 订单-事件-电池三方零差异 |

**证据**：`scripts/verify/batch3/_g3_*.ps1` + `_out.txt`；JMeter 原件入 `diag-archive/`。

## 6. 容量与 GC（S5）

- JMeter：心跳 80rps × 100s、事件洪峰（单柜高频 + 多柜并行）、抢电池并发；
- JVM 采样：jstat/jstack/CPU（沿用范例 B4 方法）；指标：YGC 次数/停顿、FGC=0、老年代曲线、p99；
- 批处理：日终对账按流式读取（防 OOM）——证据为修复前后内存曲线对比。
