### 1.3 风险与约束

- **Redis 依赖加深**（延迟队列/锁/代际集合）：沿用既有"降级哲学"——限流/守卫类组件 fail-open+warn，资金/状态类 fail-fast（不吞错）。
- **MQ 客户端选型**：`rocketmq-client-java:5.2.2`（gRPC），与本地 broker 5.3.1 的兼容已由范例实证；sim 独立进程也需该依赖。
- **多实例**：本项目不真起双实例部署，但**所有定时/延迟任务按多实例安全设计**（Redis 租约锁），并单测覆盖锁语义；文档如实声明"未做双进程联调"。
- **本地 env**：RocketMQ 三进程 + `--dir F:\Redis` 启动 Redis（RDB 可写）为前提。

## 二、S3.1 跨代际重放守卫

**设计**（对照范例 `DeviceBootGenerationGuard`，本项目落在 device 域）：
- 新增 `server/device/config/DeviceBootGenerationGuard`：
  - `swap:boot-current:{cabinetNo}` = 当前代际；`swap:boot-history:{cabinetNo}` SET = 已见代际（TTL 30 天）；
  - `isReplay(cabinetNo,bootId)`：与当前一致→false（稳态直通，零额外历史查询）；换代际→SISMEMBER；Redis 异常 fail-open+WARN；
  - `register(cabinetNo,bootId)`：SET current + SADD history（TTL 仅首写）。
- `DeviceEventService.handle` 在序守卫前调用；命中重放 → warn + return false（不推进台账/流水/订单）。
- 契约 `S0.3 §5` 补"跨代际重放拒绝"实测语义；Redis 键族更新 `SwapRedisKeys`。

**验收**：单测 4 例（稳态直通/新代际接受并登记/历史代际拒绝/Redis 异常放行）；剧本 `_g4_replay`（重启 sim 后用旧代际报文重放 → 402? 断言 200 但事件被拒、台账不变）。

## 三、S3.2 超时对账（QUERY_STATE）+ 重试分层 + FAULT 中断

**设计**：
- `DeviceCommandService`（新，或 `CommandDispatchService` 扩展）`queryState(cabinetNo)`：POST `/cmd/query`（canonicalQuery 签名 + traceId），解析 `state/cells/bootId/eventSeq/lastCommandSeq`；失败返回 null 与"查到非目标态"区分。
- `CommandLogService` 新增：`findTimeoutPending(timeoutSeconds)`、`markRetried(id)`、`markRetryExceeded(id)`、`markSuperseded(id)`（S1 已留 CAS 骨架）。
- 新增 `MonitorReconcileTask`（S3.3 调度器驱动，替代裸 @Scheduled）：对超时 PENDING 指令：
  1. `queryState` 失败 → 重试路径；
  2. 设备 `lastCommandSeq >= seq` → 指令已被执行（事件丢失）→ 按证据销账（cell 快照判定状态；订单域补记/异常）；
  3. 设备动作中（cell 仍有电池且订单未推进）→ 不抢，下轮再看；
  4. 明确未执行/设备拒绝 → 同 seq 重试（设备幂等）；被拒 → SEND_FAILED；达上限 → RETRY_EXCEEDED + 告警；存在更新 seq → SUPERSEDED。
- **FAULT 中断（G3）**：`CABINET_FAULT` 事件与查询到 FAULT 时：该柜在途 PENDING 指令 → `EXEC_FAILED`（新增按柜批量 CAS 方法）+ 告警 `CABINET_FAULT`；订单域将活跃订单转 `EXCEPTION`（人工）。
- 订单侧对账：PENDING_OPEN/OPENED 订单超时且设备快照显式相反 → 订单 `EXCEPTION`（不再静默 TIMEOUT）。

**验收**：单测（重试/超限/被拒/取代/实况已到位销账/FAULT 全断）；剧本 `_g5_outage`。

## 四、S3.3 延迟任务调度器 + 逾期迁移

**设计**：
- `DelayQueueService`（Redis ZSET，多实例安全）：
  - 入队 `zadd swap:delay:{topic} score=executeAt member={taskId:payloadJson}`；取消 `zrem`；
  - Worker：`SET swap:delay-lock:{topic} token NX PX lease` 抢租约（到期续租/释放），到期任务取出 → 分发 handler → 成功删除 / 失败按退避重投（attempt 计数存 member 或 hash）→ 超限移入 `swap:delay:dead:{topic}` + 告警 `DELAY_DEAD`。
  - at-least-once + handler 幂等（订单 CAS/支付唯一键天然幂等）。
- 业务接入：
  - 下单成功 → `ORDER_TIMEOUT`（preemptExpireTime 到期：未开仓/未取还 → TIMEOUT_CLOSED+释放；`OrderSweepTask` 保留为兜底扫描）；
  - 取电完成（SWAP）→ `ORDER_OVERDUE`（takeTime+24h：TAKEN→OVERDUE + 告警 `ORDER_OVERDUE`；归还时清任务）；
  - 现有 `OrderSweepTask` 保留为"扫描对账"（延迟器故障兜底），双机制互不冲突（CAS 幂等）。
- `OrderStatus.OVERDUE` 首次被写入；逾期费口径不变（完成时计算，S3.4 后可退）。

**验收**：单测（ZSET 入队/到期分发/租约互斥/死信）；剧本 `_g5_outage` 覆盖逾期迁移（可用 dev 缩短 TTL）。

## 五、S3.4 模拟支付幂等回调 + 退款补偿

**设计**：
- 迁移 `db/03-s3-payment.sql`（幂等：information_schema 检查）：
  - `pay_order`：trade_no（唯一）、user_id、amount_fen、purpose（RECHARGE）、status（WAIT/SUCCESS/CLOSED）、channel（MOCK）、callback_time、create/update；
  - `refund_record`：refund_no（唯一）、order_id（可空，唯一约束按 (order_id, reason) 复合）、user_id、amount_fen、reason、status、create/update；
- 用户端：`POST /user/wallet/recharge`（创建 WAIT 充值单，返回 tradeNo + mock 支付页地址）；
- 网关回调：`POST /api/pay/callback`（mock 网关；校验 `sign=HMAC(paySecret, tradeNo|result)`）：
  - CAS `WAIT→SUCCESS` 才入账（余额+）+ `payment_record(RECHARGE)`；重复回调直接返回成功（幂等）；状态非 WAIT 返回已处理；
- 退款：`RefundService.refund(orderId, reason, amount)`：
  - 幂等闸 `refund_record(order_id, reason)` 唯一；
  - 触发点：①订单 `EXCEPTION`（有已收基础费/押金）→ 补偿任务自动退款并关单说明；②管理员 `POST /admin/refund/{orderNo}`（人工）；
  - 退款金额优先冲减应收（服务费/超时费），押金原路退回余额。
- `PaymentType` 增补 RECHARGE/REFUND；`BillingService` 不变（内部账），外部资金入口走 pay_order。

**验收**：单测（回调幂等/重复回调/坏签名拒绝/CAS 冲突/退款幂等）；剧本 `_g5_outage` 附充值回调用例。

## 六、S3.5 MQ 可靠通道 + 日终对账

**设计**：
- 依赖：server/sim pom 加 `org.apache.rocketmq:rocketmq-client-java:5.2.2`。
- sim：`MqEventReporter`（单发送线程、有界队列 500、失败队首持留、退避 1~5s、超限 5s 节拍、优雅关闭）+
  `ChannelRouterEventReporter`（`sim.event-channel=mq|http|dual` fail-fast）——HTTP 报道保留为降级。
- 平台：`DeviceEventMqConsumer`（topic `swap-device-event`/group `platform-device-event`，**并发度=1 保序**）：
  验签复用 `DeviceChannelAuthenticator`、编排复用 `DeviceEventService`；毒消息（验签失败/未登记/协议垃圾/信封不一致）**ack 丢弃**，
  瞬时异常不 ack 等重投（retryMaxTimes=3 → `%DLQ%`）；property 携带 `X-Device-No/X-Device-Sign/traceId`，keys `{cabinetNo}-{eventSeq}`。
- 契约 `S0.3` 增 §7（MQ 适配层：信封/property/保序/失败分级），与范例 `PROTOCOL-V2 §7` 同构。
- **日终对账 `DailyReconcileTask`**（每日 02:00，可手动触发 `POST /admin/reconcile/run`）五组不变量：
  ① 无隔日卡滞的 PENDING_OPEN/OPENED/TAKEN；② `battery.cell_id ↔ cell.battery_id` 双向一致；
  ③ SWAP/TAKE 完成单必有对应支付流水；④ 持有人唯一且与 LOANED 一致；⑤ command_log 无超龄 PENDING；
  输出计数报告（日志+Redis 最近一次结果）+ 差异升级 `RECONCILE_ERROR` 告警。

**验收**：单测（消费分级/信封不一致/毒消息 ack/对账规则）；剧本 `_g6_mq`（同 traceId 双端对照、停 broker 队首持留、重启续消费、毒消息进 DLQ/丢弃计数）；
剧本 `_g7_reconcile`（日终零差异 + 差异注入后告警）。

## 七、S3.6 告警治理 + 任务看护 + Agent 接缝①

**设计**：
- `AlarmService.raise(deviceType,deviceNo,type,content)`：SETNX 去重（TTL 窗口）+ DB 时间窗兜底 + per-type ZSET 限速（超限只日志）+
  批量离线合并（>=阈值一条 BATCH_OFFLINE）；`markRecovered`（事件到位）/`markOnlineRecovered`（心跳恢复）自动关；
  `handle(alarmId,userId)` CAS 0→1；管理端 `GET /admin/alarm`（默认未处理）+ `POST /admin/alarm/{id}/handle`。
- `AlarmType`：OFFLINE / BATCH_OFFLINE / CABINET_FAULT / CELL_FAULT / RETRY_EXCEEDED / SUPERSEDED_BY_RULE? / ORDER_OVERDUE / RECONCILE_ERROR / JOB_STALLED / DELAY_DEAD。
- 离线扫描 `OfflineScanTask`（30s，租约锁）：`swap:online:*` 缺失且状态≠NOT_CONNECTED → OFFLINE/合并；心跳到达 → 关 OFFLINE。
- 任务看护 `TaskWatchdog`：每个定时任务成功写 `swap:job-last:{name}`；连续错过 N 周期 → `JOB_STALLED` 告警；恢复自动关。
- **Agent 接缝①**：`AlarmEventPublisher` → topic `swap-alarm`（1 队列）；信封
  `{alarmId,alarmType,deviceType,deviceNo,content,handled,handler,createTime,traceId}`；人工关闭事件同样发布（审计）；
  topic 创建脚本/文档（`mqadmin updateTopic -t swap-alarm -w 1 -r 1`）。

**验收**：单测（去重/限速/合并/恢复/看护）；剧本 `_g7_reconcile` 覆盖批量离线合并与风暴限速。

## 十、与参考基准的对应

- 序守卫/代际重放、MQ 消费分级/保序、告警去重限速合并、任务看护、延迟任务：参照范例（`DeviceRecordServiceImpl`/`DeviceEventMqConsumer`/`DeviceAlarmServiceImpl`/`BarrierMonitorTask`/`BarrierAutoTask`）；

- 对账任务：ThingsBoard/JetLinks 的"周期性对账告警"思想 + 本项目四不变量口径。
